# Frontier Insight — capability reference

What this doc is: a feature index for people evaluating FI or looking
for a specific knob to twist. README is the elevator pitch; USAGE.md
is the YAML schema; this file is the breadth catalogue.

## The 21-node graph

> Simplified happy path below — see ``core/engine.py:_build_graph``
> for the authoritative edge set. Conditional branches that aren't
> drawn: the design→implement vs design→auto_collect_data fork (no-
> simulation mode), and the ``broaden_lit`` arc from cross_check back
> to literature when analyze asks for a wider sweep.

```
START → clarify → ideate → literature ←─────┐ (broaden_lit)
                                │             │
                                ↓             │
                          select_skills       │
                                │             │
                                ↓             │
                              design ─────────┘
                                │
            ┌───────────────────┴───────────────────┐
            ↓ (computational)                       ↓ (no_simulation)
     implement_outline                       auto_collect_data   ‡ survey: design ──→ web_figures (skips
            ↓                                        ↓              auto_collect_data … web_plots) ──→ analyze
            ↓                                        ↓
        implement ──→ execute ──┐               wait_for_data
                                │                    ↓
                          execute_reflect ←─(retry)  data_load
                                │                    ↓
                                │                 web_plots
                                │                    ↓
                                ↓ (proceed)       web_figures
                              analyze ←───────────────┘
                                ↓
                          cross_check ──┐ (re_experiment → design)
                                │       │ (broaden_lit → literature)
                                ↓
                          evidence_gate ─┐ (broaden → literature)
                                │ (write)
                                ↓
                              write
                                ↓
                          claim_check
                                ↓
                              review ──→ human_feedback ──→ END (accept)
                                │
                                ↓ (revise → design)
```

Feedback loops in this diagram: `execute_reflect → execute` (retry),
`cross_check → design` or `cross_check → literature` (analyze re-
route), `evidence_gate → literature` (broaden), `review → design`
(revise). `evidence_gate` (between cross_check and write) weighs
assembled evidence before any paper is written; `claim_check` (between
write and review) grounds the paper's claims. The `human_feedback`
gate, when enabled, sits between review and END.

The design fork has a **third branch, `survey`** (‡ in the diagram), for a
descriptive history / overview synthesised purely from the literature — no
experiment and no dataset. It is a stronger form of no-simulation: after
`design` it routes straight to `web_figures` (license-clean illustrative
images) → `analyze`, skipping the experiment (`implement`/`execute`) **and**
the whole data-collection chain (`auto_collect_data` → `wait_for_data` →
`data_load` → `web_plots`). `analyze` synthesises the reviewed sources
directly. Survey mode turns on from `engine.survey_mode: true`, from the
"Literature synthesis" research approach in the interview, or automatically
when the clarify step classifies the topic shape as `survey` (a "history of
X" / "evolution of X" / overview topic).

Feedback loops:

| Loop | Trigger | Bound by |
|---|---|---|
| `execute_reflect → execute` | Script crashed (rc != 0 or no `RESULT_JSON`), a result broke its declared bounds, or (once per quest) a saved figure has a legend drawn over its data or a title over a panel title | `engine.exec_reflect_max_iterations` (default 3) |
| `cross_check → design` | `analyze.next_step == "re_experiment"` | `engine.max_iterations` (default 2) |
| `cross_check → literature` | `analyze.next_step == "broaden_lit"` — re-enters literature with the design's hypothesis folded into the query | `engine.max_iterations` (default 2) |
| `review → design` | `review.verdict == "revise"` | `engine.max_iterations` (default 2) |

## Capabilities

Grouped for skimmability. If you want to know whether FI does X, this
is the index.

### Engine + execution

- **Async LangGraph engine** with 21 nodes and 4 feedback loops; see `core/engine.py:_build_graph` for the actual edges.
- **One Python for everything (default)** — agent-generated Python runs on the same interpreter that runs FI (`execution.shared_interpreter: true`). Nothing is built under the quest's own output path, so a package installed once (`pip install -e .`, or an earlier quest) is simply there for the next quest, and a long Windows output path can no longer stop pip installing `torch`. The cost is no isolation: what a quest installs stays in FI's environment. Installs are serialised across processes by a file lock, since concurrent quests share one site-packages. On success the packages the quest asked for are recorded, pinned to the versions it ran against, in `.fi/requirements.lock.txt`. `run.log` starts with `[env] python=<path>` naming that interpreter.
- **Per-quest venv (opt-in, `shared_interpreter: false`)** — agent-generated Python is installed and run in `<quest_root>/.venv/`, which sees FI's own packages (`system_site_packages`, on by default) and is built from the interpreter matching `execution.python_version`. On successful quest finish the venv is frozen to `.fi/requirements.lock.txt` (including the FI-provided packages the quest asked for) and then removed to reclaim disk (typically 150–250 MB per quest). The lock file makes the environment reproducible: `python -m venv .venv && .venv/bin/pip install -r .fi/requirements.lock.txt`. Failed or paused quests keep their `.venv/` so you can poke at it. A failed package install is retried once; a timed-out one is not.
- **Example files for the experiment** — `execution.inputs: [path, ...]` names files or folders the experiment should start from: a simulation setup, an input deck, a config, a script, a document — **any file type**. They are copied into `<quest>/inputs/examples/` (files dropped there by hand while the quest is paused count too, and a resume never overwrites a copy you edited unless the source itself changed). The design and the code-writing steps are shown their names and the text of the small ones (4,000 characters each, 16,000 in all; a binary file is listed, not shown) and told to combine them with the selected skills into a *new* simulation rather than re-run them; the experiment finds the folder in the `FI_INPUT_DIR` environment variable (an absolute path, read-only by convention). A path that does not exist, or more than 500 MB, stops the quest before its first LLM call. The older `inputs/data/` drop zone (tabular files, read only by the analysis) is unchanged. Web: an *Example files* control on the paused quest's banner (`POST /api/quests/<id>/upload` with `target=examples`); VSCode: the pause message (`NEXT_STEP.md`) names the folder, like the papers and data folders.
- **Background jobs (HPC, a cluster, anything longer than `timeout_s`)** — `execution.background_jobs: true` changes what `experiment.py` is: an idempotent driver that FI runs again and again rather than a script that waits. The first run submits the job and prints `RESULT_JSON: {"fi_job": {"status": "pending", "id": ..., "note": ..., "poll_s": ...}}`; every later run checks it (still running: the same line) and, once it is finished, collects the results and prints the real `RESULT_JSON`; a failed job exits non-zero and is repaired like any failed run. There is one fixed contract, not scheduler code in FI: the selected skill and the example files say how to submit, how to tell finished from failed, and how to read the results, and the prompts carry the contract. On a pending line the quest pauses and exits cleanly (rc 0), writes `.fi/pending.json` and a `NEXT_STEP.md`, and runs no pilot and no replicates (they would submit the job again). `fi --resume <id>` checks once. `fi --watch <id> --config <yaml>` checks on a timer (`--watch-every`, else the job's own `poll_s`, else 300 s; `--watch-max-hours`), prints and logs every check to run.log, and resumes the quest by itself when the script stops saying pending. Web: a *Watch automatically* button on the paused quest (`POST /api/quests/<id>/watch`). Starting the watcher does not mean it is still there a second later (`--watch` exits at once on a quest with no checkpoint), so the page then asks for its real status (`GET /api/quests/<id>/watch`: `state` running / exited / unknown / not_started, `returncode`, `last_line`, the last few lines of `log_tail`, and whether `.fi/pending.json` still exists), every 5 s while the tab is visible. It shows `Watching: <the watcher's last line>` while the process runs; `Watcher stopped (exit code N): <its last log line>` when it has exited, and the button comes back; and, when the web server was restarted after the watcher started and no longer holds its process, that it cannot tell whether it is still running. The exit code is kept in memory after the process is reaped, so another page polling the Jobs list does not erase it. VSCode: `@fi /watch [quest_id]`. Tested against a fake cluster; a real scheduler has not been run, the wait is only as good as the skill's status check, and `--watch` is a process that has to stay running (if it dies, `--resume` or a new `--watch` picks the same job up: nothing is submitted twice).
- **The simulation and its analysis as two scripts** — `execution.split_analysis: auto` (the default; `true` and `false` decide for every quest). `auto` turns it on for a stochastic design (its `protocol.runs_per_setting` is 2 or more, or its hypothesis, method, expected outcome or variables name a Monte Carlo / stochastic / Gillespie / MCMC / random-walk / agent-based / Langevin / Brownian process; `core/split_run.py::design_is_stochastic`) and leaves it off for a deterministic one, a background job, a study with no experiment and an analysis-only run; the decision is made from the design each time it is asked, so it is the same after a resume. A stochastic study keeps the raw outcome of every run on disk, which is what an interval computed from the runs themselves, rather than from a few batch summaries, needs. One script that simulates *and* analyses is repaired by writing it again and running it again, so a plotting mistake, a wrong interval or a mislabelled table costs the whole simulation a second time, which for a simulation that takes hours is a lost day. With the switch on, the code-writing step returns two scripts: `code/simulate.py` runs the simulation and saves everything the analysis needs as files in the folder named by `FI_RAW_DIR` (a path relative to the quest folder: `raw/seed<K>/`, one folder per replicate seed), and `code/experiment.py` — the name every other part of FI reads — is the analysis: it reads only that folder, computes the statistics, draws the figures and prints `RESULT_JSON`. Each replicate seed is its own pair, simulation then analysis, so FI's replicates, confidence intervals, per-seed figure records and mean figures work exactly as for one script. Which raw files are still good is decided by the files, not by anyone's judgement: each seed's folder holds a `manifest.json` with the SHA-256 of the `simulate.py` that wrote it, the seed, and every file with its size (and its SHA-256 up to 256 MB). The simulation runs again exactly when that record does not fit: its script was rewritten, the seed differs, a file is missing or a different size, or nothing was written yet; otherwise only the analysis runs. So a crash in the analysis is repaired by rewriting `experiment.py` alone (the repair is shown what is in the raw folder) and run against the same files; a crash in the simulation rewrites `simulate.py` alone (a failure names which of the two it is in); a simulation that exits 0 but saves nothing fails as the simulation; and when a review names something the run computed, the code-writing step is told to give `simulate.py` back exactly as it is unless the problem is in the simulation, and a script given back with other line endings or trailing spaces counts as unchanged, so its raw files stay in use. The seed checks read the simulation (where the seed belongs), the topic's settings and run counts are checked against both scripts, and the critique reads both. `execution.raw_dir` puts the raw files elsewhere (relative to the quest folder, or an absolute path on a big disk or an HPC scratch area; FI records the path and each file's size and hash, and copies nothing); with `sandbox: docker` it must be relative, because the container sees only the quest folder. Limits: there is no pilot pass for two scripts; a reply that does not hold both scripts is asked for once more and otherwise the quest runs as one script and says so in the log; the switch cannot be combined with `background_jobs` (refused when the config loads, since a background job's driver already submits, waits for and collects the run); a wrong result whose cause is in the simulation is fixed by the review's re-run rather than by the repair of the analysis; and each script gets the full `timeout_s`, so a simulation longer than that still needs `background_jobs`. FI removes a seed's raw folder only to write it again, when that seed's simulation runs again; otherwise a long simulation's files stay on disk.
- **Docker sandbox** — `execution.sandbox: docker` runs the experiment subprocess with network disabled, the quest mounted at `/work`, and the approved external skills the quest selected mounted read-only at `/fi-skills/<name>` (see *Skills from other agents* below).
- **Provider matrix** — direct HTTP, proxy, CLI exec, and VSCode-extension transports (see provider matrix below).
- **Per-node model routing** via `provider.node_models`. FI never chooses the model; the interview's "Per-node model overrides" field takes `node:model` pairs on every surface, and in VSCode it is a menu of the models that VSCode offers with one entry for the light nodes. Five nodes (`cross_check`, `select_skills`, `literature_screen`, `slides`, `poster`) were measured on a cheaper model (one simulation topic, three runs per arm: about 15% fewer tokens, no drop in paper, slide or poster scores seen, which three runs can show only above roughly ten points); every other node is untested (see `docs/PROVIDERS.md`).
- **Reasoning effort** via `provider.reasoning_effort` (`minimal` / `low` / `medium` / `high` / `xhigh` / `max`; unset sends nothing, so each provider keeps its own default). Sent as `reasoning_effort` in the chat-completions body to HTTP providers, `--effort` to `claude_cli` and `antigravity_cli`, and `-c model_reasoning_effort=...` to `codex_cli`. A level a provider cannot take — Ollama and `agy` beyond low/medium/high, `claude_cli` at `minimal`, or a provider with no such setting (`copilot_cli`, `gemini_cli`, `vscode_extension`, the proxies) — is left out with one warning in the quest log rather than failing the call; an unknown value fails at config load. Set from the interview's advanced screen on the CLI, web and VSCode. See `docs/PROVIDERS.md`, "Reasoning effort".
- **Pre-flight `clarify` node** — slot survey before `ideate`; off / auto / interactive modes. The slot set includes ``topic_shape`` (``experimental`` / ``survey`` / ``review`` / ``case_study`` / ``opinion``) so the engine recognises when a topic naturally wants a literature synthesis instead of a code experiment — ``survey`` (a "history of X" / "evolution of X" / overview topic) takes the no-experiment, no-dataset survey path. **Agent judgment beats the format heuristic.** Most `clarify_overrides` pinned by the interview are user *preferences* (study depth, venue, output kinds, baseline, metric, budget) and rightly win over the agent's self-answers — but ``simulatability`` and ``topic_shape`` are topic *judgments*. When the agent runs in `auto` mode and its judgment conflicts with the interview's pinned value (which is often just a paper-format heuristic), the **agent's value wins back** for those two slots, so a review-shaped topic the agent flags as no-simulation isn't force-run as a toy experiment by a stale `simulatability: "yes"` override. The hard `engine.no_simulation: true` YAML pin is separate and still absolute; there is intentionally no hard "force simulate" — the engine trusts the agent's "can a simulation actually answer this?" call. When the shape is non-experimental but simulatability still resolves to SIMULATE (the agent itself judged it simulatable), the engine logs a WARNING in run.log and the design stage falls back to a narrow illustrative experiment with weight shifted to literature synthesis (rather than a full comparative benchmark).
- **Execute-repair loop** — agent reads traceback, patches code, retries (`engine.exec_reflect_max_iterations`). Every patch is run, including the one written with the last attempt, so a paper is never written from an earlier run next to code that never ran. A result the last attempt could not bring inside its declared bounds is the one written up, so it still gets its replicate seeds and error bars. A run that worked but drew a legend over its data is also sent back, once (see *Branded figures*).
- **Stale-figure purge on re-execute** — every `execute` clears `figures/` before running the experiment. On a `re_experiment` / `broaden` / repair loop the `implement` node rewrites `experiment.py`, which may emit a *different* set of figure filenames; without the purge the previous version's plots linger (they're not overwritten), get counted in `figures=N`, and pollute the paper/slides/poster with a mix of current and stale figures. Only figure-suffixed files are removed — `results.csv` and other artifacts survive.
- **Every figure the run drew reaches the paper** — the write prompt tells the writer to include each figure it is given, and a draft that ignores it used to be caught only by the reviewer, which forces a rewrite that spends one of `engine.max_iterations` — and on the last iteration there is none left to spend, so the paper shipped discussing "Figure 1" through "Figure 3" with no figure in it while the images sat in `figures/`. Which figures are missing is a set difference (planned by the design ∩ drawn by the run ∩ not embedded in the draft), not a reading of prose, so the write node puts them back itself the moment the draft is written — before the review, for no LLM call and no iteration. Each figure is placed after the paragraph whose prose already names its number, which is where the writer would have put it, and before the source lists when the prose names no number; it keeps its place in the design's plan as its figure number, or the next free number when a figure the draft did embed already carries that one. The caption comes from the figure's own record, written from the panel titles and never from the series labels, so an engine-written caption cannot name a series its figure draws flat or not at all (which is itself a forced hit); a figure drawn as the mean of the seeds, or from seed 0 alone, says so in its caption. A figure a later experiment version superseded is never forced back: the stale-figure purge above means `figures/` holds only what this run drew. The reviewer's `figure_missing` check is unchanged and stays as the second line of defence.
- **Numeric oracle** — a deterministic, non-LLM comparison of the numbers in `paper.md` against the ones the run actually produced. Every other correctness gate ends in a language model reading text — `claim_check` asks one call whether a number "appears" in the evidence, with no arithmetic anywhere — so a mis-transcription (2.14 computed, 2.41 written) passes all of them. The oracle looks for the *signature of a copy that went wrong*, in two forms. A **digit transposition** — the same digits in another order — is almost never a coincidence. A **last-digit slip** (`near_miss`) is a number printed with at least two decimals that is one unit of its own last digit from the correct rounding of a result: 2.12 for a stored 2.1259, which rounds to 2.13, or 0.184 for 0.18346, which rounds to 0.183 — the truncation or the mistyped last digit that stored quests really contain. It used to be any number within a quarter of a result; a result dictionary holds hundreds of numbers, so that reported nearly every number a paper prints, and almost none of the findings was a copy error. Numbers far from every result are assumed to come from the design or the literature and are ignored, as are figure/table/section references, code blocks and low-precision quotes; results tables are deliberately checked. Three more kinds of number that sit near a result without being one are left out too. **A confidence level** — the `95` in `95% CI`, `95% Wilson interval` or `Wilson 95% intervals`, which lands within the comparison band of any result between 72 and 126 and was the most frequent false finding; only a `%` followed by interval wording counts, so `93% of runs` and `94% of the intervals covered the truth` are results and are still checked. **A setting the run was given** — the topic's grid and the numbers in the design's `variables` and `method` (`R0 = 1.5` printed beside an outcome of 1.33, a 13.5 nm wavelength, `gamma = 1.0`; a percentage there also counts as the fraction a paper prints for it). The design's `hypothesis` and `expected_outcome` are deliberately *not* settings: they hold what the author predicted a result would be, and a paper that prints the prediction where the measured value belongs is the mistake this check exists for. A digit transposition is still reported for a declared number, and the blind spot is accepted: a result that really equals a declared setting and is misquoted as it goes unreported. **A number cut off from a longer one** — `97.5th` is a percentile rank, not the `97` the extractor used to back off to. A minus typeset as `−` (U+2212) now keeps its sign, so `−0.114` is compared as a negative number rather than as 0.114 against an unrelated positive result. Replayed over the 153 stored quests that kept a paper and a checkpoint, the rules above took the `near_miss` findings from 311 to 207 (16 confidence levels, 82 declared settings, 5 dropped signs, 1 percentile rank) and added none, and what remained was mostly a paper number landing near an unrelated result in a dense result set — a table cell, an interval bound, a quoted theoretical value, a difference the paper computed. So `near_miss` is the last-digit slip above, and six more rules keep the rest out. A number inside a citation bracket (`[6, 15]`) is a reference number. A result named like an identifier or a count of files (`id`, `index`, `seed`, `year`, `n_files`) is not a measurement. A result the paper also prints correctly rounded, to two decimals or more, is stated right, so a number one digit off beside it is another quantity: a sibling, a bound, a sum worked by hand. A repeating-decimal constant printed with three decimals or more (0.333, 0.667, 0.143) is a theoretical value more often than a measurement. A result that is only a shorter rounding of the number printed (0.667 against a stored 0.67) is read against that result alone, so an unrelated stored 0.2 clears nothing. And a declared setting, as above. Replayed over the 136 stored quests with results, that takes the `near_miss` findings from 197 in 59 quests (37 in the worst) to 20 in 9 (6 in the worst), and the four last-digit slips found by reading the findings against their results (a MEEF printed 2.12 for a stored 2.1259 and 2.00 for 2.0053, a NILS of 0.184 for 0.18346 — one point of a nine-point sweep — and an AUC of 0.9120 for 0.91205) are all still reported. Read by hand, about a third of the 20 are last-digit slips of the quantity the paper means; the rest are another quantity sitting one digit from a result, which nothing about the number's own surroundings tells from a slip. A hit is reported under the name of the signal that fired — `transposed` when the paper's digits are the result's in another order, `near_miss` when the last digit is one off the correct rounding — naming the value and the `result_json` path, in the log, in `paper/numeric_audit.json`, and in the human-review panel of the web UI and the VSCode chat, under both the single reviewer and a `review_panel`. Each finding is labelled by its own kind rather than by one verdict stretched over all of them, because the three are not the same claim and a label that argues with the sentence under it makes the reader decide which half to believe. It does not force a rewrite: the check is a regex over prose, and a forced revise cycle on a false positive costs more than a flagged number, so the verdict stays with the reviewer. A third signal does not read the paper at all: a **reference value that is exactly 0 at every setting of a sweep** is reported as a `trivial_reference` finding naming the leaf and the settings it covers — and it says so under that name rather than being called an unverified number, because that value was computed and exported exactly as the code asked; what is unverified is the bracket the root finder was handed. A closed-form reference — the deterministic limit, the theoretical prediction, the analytic solution — is generated code, and it fails in one characteristic way: a root finder bracketed so the useless root sits on the bracket endpoint (`brentq(f, 0, 1)` where `f(1) == 0`, or a bracket of `[1e-10, 1.0]`) returns the trivial root, so the reference comes out as 0 at every point and the paper then draws that flat line of zeros in a figure captioned as convergence to the deterministic limit. Nothing else catches it: the range gate only checks quantities the design declared a bound for, a design that names `final_size` does not cover a leaf called `deterministic_final_size`, and 0 is inside `[0, 1]` in any case. Only an identically-*zero* reference is reported, deliberately — a correctly computed deterministic final size does not depend on the population size, so a legitimately flat reference line across a sweep over N is exactly what a convergence study plots, and flagging "identical" in general would fire on correct work. Values a run carries as settings rather than results (tolerances, horizons, seeds, step counts) are excluded by name, since a tolerance of 0.0 repeated at every point is configuration rather than a computation; that exclusion is a name list, so a setting named outside it is not recognised. The finding needs at least three settings and some other quantity that does vary — a result in which nothing varies at all belongs to the degenerate-run guard. Like the oracle's other signals it is advisory, so it reaches the audit file and the human-review panel rather than forcing a rewrite. `paper/numeric_audit.json` is written on every run, clean or not, so silence never has to be read as "the check was skipped".

- **Topic coverage (advisory)** — a topic that names its settings often gets an experiment that changed them: on the graded SIR runs one drew its grid at R0 = {0.8, 1.2, 2.0, 3.0} for a topic that asked for {0.9, 1.5, 3.0}, and another drew five figures for a topic that asked for three, and no later step compared the experiment with the topic. After each draft the review reads the topic for the numbers that are settings (the members of a set written in braces with at least two numbers, `R0 in {0.9, 1.5, 3.0}`, and a count of runs, `300 stochastic runs`; a number in running prose such as a wavelength, a threshold or a page limit is left alone, and so is an integer below 10, which every script holds) and for the number of figures it asks for (`three figures`, `at least three figures`, `no more than 2 figures`), and compares them with `code/experiment.py` (its numeric literals and the values its `linspace`, `arange`, `logspace`, `geomspace` and `range` calls with literal arguments generate), the keys of `result_json` (`R0_1.5_N_1000`) and the figures the run drew. A number given with a unit or a percent sign counts at any power of ten, since a script works in metres or in fractions (193 nm is 1.93e-7). What differs is one line each in the review's `goal_coverage_notes`, in `run.log` as `[goal_coverage]`, in `paper/goal_coverage.json` (written on every run with what the check looked at, clean or not), and in the human-review panel of all three interfaces (the CLI gate, the web quest page and the VSCode review message) under "Topic coverage (advisory, not blocking)". It is never a must-fix hit and never sends the experiment back: a topic is prose, and a wrong note would cost a whole cycle. Skipped for a survey or no-simulation study, a run on the user's own data (`--analyze`) and a run with no results (a failed run, which other checks report). Measured over the 122 stored quests that have a script and results, 10 (8%) get a note: three for numbers (the {0.8, 1.2, 2.0, 3.0} grid with N = 5000 dropped; the same grid in one graded run; a percolation run that swapped the lattice size 256 for 96) and seven for a figure count (three asked; two, four, four, four, four, five and six drawn); read against the scripts and the topics, each is a real difference between the topic and the run, and it finds both differences the grading recorded (the changed R0 grid and the five figures). What it does not do: a setting written in prose ("between 0.5 and 3") or in square brackets is not read, a value the script computes rather than writes is not seen, and whether a difference matters is left to the reader.
- **Statistics claim check** — the numeric oracle asks whether a number *matches* a result and `claim_check` asks a model whether a sentence is *supported*; neither asks what a number **is**. That gap ships papers whose numbers are all correct and whose sentences are not: a Bonferroni threshold printed as a p-value, "Cohen's *d* > 16 for all pairwise comparisons" when a third of the run's comparisons fall below it, three-seed t-intervals labelled "exact binomial 95% CI", a figure's y-axis limits printed as modal bin counts, and a major-outbreak probability described as the chance the disease dies out — which the numeric oracle passes, because the number really is one the run computed. This check reads what a number is *said to be* and recomputes the claim against the run's own replicates. Five things it can prove: an **effect-size claim carrying a universal quantifier** ("for *all* pairwise comparisons") is re-derived from every pairwise Cohen's *d* the replicates support — uncapped, unlike the analyze aggregate, whose limit of 24 hid 12 of one quest's 36; a number written as a **p-value** that equals this run's `0.05/n` when the run computed no p-value at all, matched to one unit in the paper's own last decimal because `0.05/36 = 0.0013888…` gets *truncated* to `0.001388` and a rounding comparison would miss it; an interval labelled with a **named estimator** (exact binomial, Clopper-Pearson, Wilson, bootstrap, …) whose endpoints reproduce FI's own t-interval over the seeds — proving the label wrong needs no second estimator, only that the printed interval *is* the seed-to-seed one; a number presented as a **count of runs** that equals a recorded figure's y-axis upper limit and appears nowhere in the results (matplotlib leaves 5% headroom above the tallest bar, so an axis limit reads exactly like a bin count); and a **probability of extinction** whose value matches a result named for the opposite event and none named for extinction, reported with its complement. **False positives are the failure mode that matters**, so each check fires only when it can name the contradiction, and the guards are as load-bearing as the checks: a bracket holding only digits is a citation and never a measurement, a count must sit within 40 characters of the noun it counts, a number the run computed anywhere is assumed to be that result, an effect size that survives rounding to the paper's own precision is not a contradiction, a threshold the paper *calls* a threshold is correct, and "the outbreak probability vanished as N increased" is a correct sentence about a probability going to zero rather than a disease that vanishes. Measured over the graded SIR papers, it flags all five known-defective runs — naming 17 of 36 effect sizes below the claimed bound, the `0.05/36` threshold, six mislabelled intervals as one finding, three axis limits, and the reversed probability with its complement — and **zero of the 35 others**. A hit is a forced `mislabelled_statistic` must-flag under both the single reviewer and a `review_panel`, listed in `_TEXT_ONLY_HITS`: the experiment computed the right numbers and the paper described them wrongly, so the route is `rewrite` (back to `write` alone, with the finding in front of the writer) and a mislabel never sends the experiment back to be run again. `paper/statistics_audit.json` is written on every run, clean or not.

- **Number provenance** — the numeric oracle asks whether a printed number is a slip of a result (its digits swapped, or its last digit one off) without matching it, and deliberately ignores one that is far from every result ("assumed to come from somewhere else"); the statistics claim check asks what a number **is**. Neither asks **where a number came from at all**, and a graded paper shipped straight through the gap: its Table 1 printed eight cells — `0.7093 (0.6934–0.7252)`, `0.2974 (0.2721–0.3227)` and their neighbours — matching no value the run computed, no per-seed replicate and none of the three-seed aggregates. The oracle, in its earlier and wider form, saw those numbers as 38 advisory near-misses that blocked nothing; the paper shipped, and the run failed its "numbers are correct" gate on exactly those cells. This check asks every number in the paper body to trace to something the run can account for, reports the ones that trace to nothing, and **blocks** — the difference that matters, since the finding routes to `rewrite` alone. **What makes it possible is that a paper does not print `RESULT_JSON`:** it prints the *mean over the replicate seeds* and that mean's interval, and no single seed holds either — checked against `RESULT_JSON` alone, all eleven of that same paper's *correct* headline numbers come out untraceable too, so the naive form of this check flags correct prose. With the across-seed aggregates included the two classes separate cleanly: 11 of 11 accepted numbers trace, and 11 of 13 of the ones the paper was failed over trace nowhere — the other two are values the run really did compute, printed against the wrong cell, which is a mislabel rather than a number from nowhere and is the statistics claim check's question, not this one's. A number may trace to the results or any replicate; to the aggregates over the seeds (mean, 95% bounds, SD, standard error, min/max); to the length of an array the results hold, so "300 runs" traces to the 300 entries behind it; to a stratum label read off a result path (`by_R0.1.5`); to a recorded figure's own numbers, **axis limits included**, so an axis limit printed as a bin count is left to the statistics check that can name the contradiction instead of being reported twice; to a number the run **configuration** or the **design** declared; or to arithmetic the paper writes out in full. Rounding *and* truncation to the paper's own precision both count, as do a scale change (`0.15` printed as `15%`) and a complement (`1 − p`). **The guards are the check.** The load-bearing one is precision: a number carrying fewer than three significant digits — or two without four decimals — is a round number, a convention or a stratum label ("we ran 3 seeds", "R0 = 1.5", "95% CI", "the 0.05 level"), and is never asked to trace anywhere, which removes that entire class without a single hand-written rule about rhetorical numbers. Years and dotted version numbers are not measurements; a random seed is chosen and never computed; reference lists and citation brackets are stripped before a number is read; and a range written `0.3126--0.3548` is rewritten before tokenizing, because a number reader takes the dash as a minus sign and invents `-0.3548` — that one artifact produced the majority of all flags across six runs whose numbers were perfectly fine. Five more readings of that kind are corrected the same way, before the paper is tokenized: a minus typeset as U+2212 is one number with its sign and is compared with its sign (`−38.61` is no longer checked as `38.61`, and a bare `38.61` is still not `−38.61`); a dash right after a percent sign ends a range (`68.1%-85.5%`) instead of signing its upper bound; a number after `±` stands for both signs; a comma run whose later group is not three digits (`n=107,104,94`) is a list rather than `107104`; and an integer of four or more digits after a capitalised acronym (`SPIE 11609`), or a year credited in the possessive (`Abbe's 1873`), is an identifier or a date rather than a result. An en or em dash is never read as a minus, and nothing in this paragraph is a derived-value allowance — a number the run never produced, beside a sign, inside a list or after an acronym, is still flagged. Over the 136 stored papers with recorded results, 13 of the 128 flags were these readings and are gone with none added, and every number of the fabricated table this check was built for is still flagged; the artifacts that remain (a value printed without the sign the run holds, and a well-formed `202,206,189` that is really a list) cannot be told from a real number by their text, and the check does not try. Where the paper shows no operator, as in a table column that is a difference, the operands must themselves be values the run computed, so three numbers standing near each other can never explain away a fourth. A run whose last `RESULT_JSON` holds no numbers at all goes **quiet** rather than flagging the whole paper. Measured over the 40 stored SIR runs and the 1,422 paper numbers in them, it flags **two runs, both of which failed the "numbers are correct" gate, and none of the other 38 — the eleven that passed that gate, the ten that failed it for other reasons, and the seventeen graded before it existed**. Two blind spots are accepted deliberately and are the price of that: a two-significant-digit textbook value quoted as the run's own result sits below the precision floor, and a number the design declared but the experiment never computed is treated as accounted for. A hit is a forced `unsourced_number` must-flag under both the single reviewer and a `review_panel`, listed in `_TEXT_ONLY_HITS`: the experiment ran and recorded its results, so the route is `rewrite` (back to `write` alone, with the finding in front of the writer) and an unsourced number never sends the experiment back to be run again. `paper/provenance_audit.json` is written on every run, clean or not.

- **Physics-plausibility gate** — the design declares what its outputs may legally be (`result_assertions`: a path, a min/max, a unit and the reason) and those bounds are enforced **in code** against `result_json`. This is the gap the degenerate-run guard cannot cover: that one fires only when every metric is ~0, so it catches a run that produced nothing and misses a run that produced the wrong thing convincingly — a unit error, a factor of two, a sign flip. A violation routes back through the execute-repair loop before any paper is written, and the repair is told which bound broke. A value sitting exactly on a non-zero bound is rejected too when the script itself caps values at that constant (`min(x, 10.0)`, `np.clip`, `if x > 1e6: x = 10.0`): a cap turns divergence into an in-range number the range check could not otherwise tell from a real one. Both halves are required, so a genuine perfect score is left alone. The same quantity exactly on one of its bounds in two or more settings goes back too, zero bounds included. A computation that returns a trivial answer (a root finder settling on the solution at the starting state, a sentinel) lands on the edge of the legal range, where a range check passes it: a real quest's deterministic model reported a final size of 0.0 at two reproduction numbers and 1.0 at a third, all inside [0, 1]. The repair is told to change the code only if that is the cause, and a single value on a bound is left alone. **A result equal to its bound is on that bound, not past it.** A bound is a number with a precision: a design that worked its maximum out as 2/3 declared 0.6666666666666666, the script that computed `1 - 1/R0` produced 0.6666666666666667, and an exact `>` called the run's correct answer a violation — the log read `branching_probability = 0.666667 violates [0, 0.666667]`, the same number on both sides of the word. The repair believed it, emitted `null` for every boundary value with a flag reading `exact_theoretical_boundary` — it knew the numbers were right — and the figure drawn to show that reference lost its line in two of three panels. The comparison the at-bound and clamped rules already used now decides the range test too, so a result can no longer be too large by an amount no measurement can resolve. **A bound the design derived is attainable.** "Exactly on a bound" is evidence about the computation only when the bound is a number a fault can return by accident: 0 and 1 — nothing and everything, which is what a saturating probability, a normalisation that divides a quantity by itself, an empty count and a guard branch all produce — or a constant the script itself writes down, which is where a bracket endpoint (`brentq(f, 0, 100)`), a sentinel and a cap come from. A bound the design derived for this experiment is neither: nothing returns 0.6666666666666667 by accident, so a result equal to it is the design's own prediction, arriving where the design said it would, and it is left alone — unless the quantity sits on that bound at *every* setting the assertion matched, which is a quantity that never varied with the sweep at all (a loop that captured one cell's value for all of them looks exactly like this) and is the trivial answer whatever the bound. **A correct zero is not sent back.** Below the epidemic threshold nothing takes off, so zero of 300 trajectories crossing a threshold at R0 = 0.9 is the answer rather than a fault, and a model told that a correct number is wrong will hide it rather than defend it — one run lost its replicates that way, one returned `null` and crashed its own plot, one spent a repair round and a skipped replication pass. Three things now separate a correct zero from a trivial one, all decided from the results themselves. **A setting is counted once**: a sweep reported under two groupings — once by R0 and once by N — lists the same cell twice, so a single zero looked like the two settings the rule needs; settings are identified by the coordinates in their path rather than by the path string, so the same cell reached by a different route is one setting, while two different cells whose paths happen to hold the same segments stay separate. **A zero below the critical point is expected**: where a path names the reproduction number, or an enclosing object carries it as a field, or a grouping key leads with it and packs its value alongside another coordinate, or a stratum label spells it with an `=` and packs the whole cell into one key (`strata.R0=0.9,N=100`, which leaves no numeric segment for the positional rule either), a zero at R0 < 1 is what the theory predicts. That excuses a zero only — a *one* below threshold is excused by nothing, and a run reporting a final size of 1.0 at R0 = 0.9 still goes back. **Zeros confined to one level of one coordinate are a regime**: where no name identifies the control parameter, the shape still does, so zeros that all sit at the same value of one sweep coordinate, in a minority of the sweep, with the quantity non-zero at the other levels, are read as a threshold effect — and a level explains them only when some setting outside it behaves differently. A quantity that is zero at *every* setting gets none of these excuses — that is the trivial answer the gate exists to catch. What still fails is reported together with the zeros that were recognised and the reason each was accepted, so a repair is told what has already been accounted for instead of being asked to change it. Values of exactly zero are checked against every bound, and the design is asked for the tightest range its guarantee allows (a small positive `min` for a quantity that cannot be 0). A value that really is out of range should be reported as `null` with a flag saying why, and the implement and repair prompts say so. Assertions state what physics or the definition of the quantity guarantees, never what the design expects to happen; bounding a result to the hypothesis would make the run unable to disagree with it. An absent assertion is not checked — silence means "nothing was claimed", never "everything is fine".
- **Simulation skills** — `engine.skills` lets a quest call tested code instead of re-deriving physics. A skill is a directory carrying instructions (`SKILL.md`), optionally an API surface and executable entry points, an executable `selftest.py`, and provenance including its own range assertions. The envelope follows the [Agent Skills open standard](https://agentskills.io/), so a skill written for another agent works here unchanged: bundled `scripts/`, `references/` and `assets/` directories are read alongside FI's own single-file `api_surface.md` and `skill.py`. Their *contents* never enter a prompt — the block names the files and their paths, and generated code opens what it needs, because a references directory can be larger than the quest itself. A skill shipping only `scripts/` is treated as a tool rather than a library, which is what puts "drive it" instead of "import it" in front of the model. Maturity is derived from which files exist (notes → guided → adapter), so a skill hardens without migrating. **FI ships no skills** — not one, including any its own authors wrote: a skill that arrives with the install is a curated library again, and curation does not compound. Discovery covers `FI_SKILLS_DIR` (default `~/.frontier-insight/skills`, deliberately outside the repo, because skills accumulate per machine rather than being things you commit) and the `fi.skills` entry-point group, so a library can ship its own skill without anyone editing FI. **Two gates stand before use, and both must pass:** the self-test the skill carries must run green, and a person must have approved *that exact content* — approval binds to a content hash, so a skill rewritten by distillation lapses its approval rather than inheriting it. An unattended `--fleet` run therefore cannot adopt capability nobody signed off on; a skill that is not trusted is absent from the prompt, and the quest falls back to generating the physics itself. **A self-test that already passed is not run again for every quest.** Loading skills for a quest records each pass in `skill_selftest_cache.json` beside the approval ledger (`~/.frontier-insight/` by default; `FI_SKILLS_SELFTEST_CACHE` moves it), keyed by the skill's name and content hash, the Python version and executable, and a fingerprint of every installed package's name and version. Editing any file in the skill, switching interpreters, or installing, upgrading or removing any package tests that skill again at the next quest. Only passes are recorded: a failing or timed-out self-test runs again on every load, and a self-test that fails anywhere — `--skills`, an approval, a quest — removes that skill's recorded passes, because the key cannot see an external binary or a service a test depends on. A recorded pass stands in for the test and nothing else: approval is checked against the ledger on every load, as before. The self-tests that do need to run, run in parallel (up to eight at a time) in a worker thread, so the web dashboard keeps answering while a quest loads its skills. On one machine's 108-skill library, whose self-tests take 340 s one after another, a load with an empty cache took 112 s and the next load 2 s. Commands that check a skill on demand — `--skills`, `--approve-skill`, `--approve-all-skills`, and their web and VSCode equivalents — always run the self-test fresh. The file is a cache, not a record anyone relies on: a corrupt or unreadable one is treated as empty, and deleting it is always safe — the next quest simply runs every self-test once more, and approvals are untouched. It is never written inside a skill directory, since that would change the content hash and lapse the approval the test was checking. A **selection step** between literature and design decides which skills a quest actually carries. It reads a catalogue — one line per skill: kind, description, its *when NOT to use* limit, and its track record — and picks what fits, at temperature 0 so the same topic selects the same skills. This is not cosmetic: injecting every trusted skill into the four design/implement prompts cost ~465 tokens per skill per node, so a 50-skill library added ~93,000 tokens to every quest pass — the accumulation mechanism becoming its own largest cost. The catalogue for the same library costs about 13k tokens once per quest — measured on a real published skill, whose 845-character description is carried in full because the phrases that make it findable sit in its later sentences. Still an order of magnitude better than injecting everything, and it is paid once rather than on every pass. Selection can only narrow: a name it invents, or one belonging to an unapproved skill, is discarded and logged, so no model can talk capability into a quest. Choosing nothing is a normal answer and the quest then generates its own code. Selection also says what each chosen skill is for. An **experiment** skill goes to the `implement` stages with its instructions, API surface and selection reason, and to `design`, which decides which skill a method rests on rather than writing the calls, as only its description, *when NOT to use* limit and selection reason; either may decline one it judges inapplicable, saying why in `method`. A **writing** skill — structure, style, diagrams in the text — goes only to `write`, as its instructions and selection reason, below FI's own rules on honesty, citations and format. The skills' range assertions join the plausibility gate above. `engine.skills` narrows the candidate set when set, and means "every trusted skill is a candidate" when empty; `engine.skills_exclude` keeps named skills out, which also makes the A/B comparison easy. `python launch.py --why-skills "<topic>"` previews the whole decision without running a quest, and a quest whose review is accepted writes itself into the provenance of the skills it used, under a file lock so parallel `--fleet` runs lose no records. Manage them from the CLI: `python launch.py --skills` lists every skill with the reason it is or is not usable (running each self-test, since a status that did not execute the check would be a guess), and `--approve-skill <name> --approve-as <you>` records approval (`--revoke-skill` undoes it). There is no anonymous approver — the gate exists so a person decides. **All three interfaces carry the whole gate**: the web dashboard's `/skills` page and the VSCode chat panel (`@fi /skills`, `/scan-skill`, `/approve-skill`, `/revoke-skill`, `/import-skill`, `/teach-skill`) list, review, approve and revoke exactly as the CLI does. They render `launch.py --skills --json` and the matching web API rather than reimplementing discovery, hashing, the ledger or the scanner, so the surfaces cannot drift. Each keeps the ceremony intact: the approver is named every time — prefilled in VSCode, typed in the browser, never derived from a session — and a high-severity finding takes a second explicit confirmation. The UI surfaces list without running self-tests, since each can take up to ~2 minutes (a generated selftest's own timeout scales with how many scripts a skill bundles — see `core.skills.registry.run_selftest`), and both say plainly that the statuses shown are as last recorded rather than verified.
- **Skills from other agents, and skills a quest must use** — skills another agent installed are **found by FI itself**, with no path given, in the places those tools keep them, on Linux, macOS and Windows alike: every tool folder in your home directory (`~/.claude`, `~/.codex`, `~/.agents`, `~/.cursor`, ... any dot-folder) and its `plugins` tree, `~/.config`, `~/.local/share`, `~/Library/Application Support`, `%APPDATA%`, `%LOCALAPPDATA%`, the folders the tools' own variables name (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`), and your project (the current folder and its parents, for `.<tool>/skills` and `./skills`). A folder counts when something inside it carries a `SKILL.md`; when a plugin cache holds several versions of a skill the newest wins. Add more with `engine.skills_dirs`; `engine.skills_scan_known_dirs: false` turns the search off, and `FI_EXTERNAL_SKILLS_DIRS` replaces all of it (empty means none). The two `engine` settings belong to the quest that names them: quests running in one process (`--fleet`) each look only where their own config says, so one quest never finds or uses a skill from a folder only another quest named. The skill commands take a quest's YAML: `python launch.py --config quest.yaml --skills` (likewise `--why-skills`, `--scan-skill`, `--approve-skill`, `--revoke-skill`) also looks in the folders that quest's `engine.skills_dirs` names, so a skill that lives only there can be listed, reviewed and approved. `--config` beside them starts no quest, and a config that cannot be read is a one-line error on stderr. Without `--config` they look in the usual places and `FI_EXTERNAL_SKILLS_DIRS` alone, and `FI_EXTERNAL_SKILLS_DIRS`, when set, outranks the config's folders too. The Web skills page and the VSCode chat panel take the same option: a *Quest config* field on the page (the full path of the YAML, kept in the browser, and a config that cannot be read is shown as the same one-line reason) and `--config <yaml>` after the command in chat (`@fi /skills --config C:\quests\a.yaml`, likewise `/scan-skill`, `/approve-skill` and `/revoke-skill`; a path with a space goes in quotes). It changes only where skills are looked for: what is shown, what is refused and what is recorded are the same, and bulk approval takes no config, as on the command line. They are read **in place** — nothing is copied or converted — and are searched and selected like FI's own. They carry no FI self-test, so the approval of their exact content is the only gate: `python launch.py --approve-skill <name> --approve-as <you>`, with `--config <quest.yaml>` for one that only that quest's folders hold (the Web skills page and `@fi /approve-skill` do the same, with the config path as above); edit the skill and the approval lapses. The listing marks them *external*. They are never approved in bulk (`--approve-all-skills` leaves them out), their approvals are namespaced so one cannot overwrite an FI skill's of the same name, an FI skill of the same name wins, and FI never writes into their folders. Their scripts run with your permissions when a quest uses them, called by absolute path. With `execution.sandbox: docker` the experiment cannot see host paths, so each external skill that is approved **and** selected for the quest's experiment has its own folder mounted **read-only** at `/fi-skills/<name>` (a name with unusual characters gets a stable, sanitised folder name; a skill selected only for writing the paper is never run, so it is not mounted), and the code-writing prompts that carry the skill's text and file list give that container path, in the bundled-file list and wherever the skill's own text names its host folder. Nothing else is added: not an approved skill the quest did not select, not an unapproved one, not a skills folder, the home directory or a tool's configuration folder. A skill folder that is a symbolic link (or a Windows junction), that resolves anywhere but a direct child of the folder it was found in, that has no regular `SKILL.md`, or whose path a bind mount cannot carry (a network path, a `:` other than the drive letter's) is refused; `run.log` says which and why, and the prompt then tells the model the skill's files are not reachable rather than naming a path the container lacks. The folder is checked again each time a container is created. A `--watch` re-mounts the same skills. A link inside a mounted folder is not followed by the mount (the container resolves it against its own filesystem), so one that points out of the folder finds nothing there. The other sandboxes see host paths as before. The mount was tested with a mocked docker client, not against a running daemon. `engine.skills_required: [folder-name, ...]` makes a quest use those skills whatever selection says; one that cannot be used (not found, not approved) stops the quest before its first LLM call and says why.

  Approval binds to the **whole** skill directory, not a list of named files: everything under it is hashed except `provenance.json` and Python bytecode. That distinction is load-bearing — a rule covering only the files someone remembered to name would let an approved skill's bundled `scripts/` be swapped with the approval intact, which is the human gate guarding the wrong thing.

  Because a skill's `SKILL.md` enters a prompt verbatim and its `selftest.py` is executed, `python launch.py --scan-skill <name>` statically reviews one before you approve it: instruction-injection phrasing and invisible characters in the prose, network access, `eval`, and environment reads in the code, fetch-and-decode chains in shell scripts. Nothing is imported or run — Python is parsed as a syntax tree, everything else by pattern. The scan runs every time a skill is evaluated, so hand-authored and entry-point skills are covered as well as imported ones — the one shortcut being a quest-time load that reuses a recorded self-test pass, which also reuses the scan recorded with it, taken of the same content by the same version of the scanner — and a high-severity finding **stops** `--approve-skill` unless `--despite-findings` is also passed, with the ledger recording that it was. The flag exists because approving past a flagged network call is often correct — what it buys is that reading the findings becomes an act rather than an assumption. **Findings never block a skill.** They are heuristics: a skill that legitimately drives a network tool will flag one, and quarantine stays reserved for a self-test that actually failed. For the same reason the report never says a skill is safe — it says how many findings came out of how many rules, because a payload no rule describes is unfound rather than absent.

  Because FI works in any field, the library is not filtered by domain — which would make every installed skill a candidate for every quest, the same accumulation problem one level up (~28,000 tokens for a hundred-odd skills, growing with the library). So the catalogue is **layered**: a skill with no domain tag is general and always a candidate, while tagged ones (`--import-skill --domains genomics,biomedical`) are admitted only when the quest's topic looks related. Relevance reuses the all-MiniLM cosine already used for passage ranking, blended with lexical overlap — no new dependency. Under `FI_OFFLINE` it loads the model from the local HF cache rather than skipping it (no network call either way); it degrades to lexical alone only when the model is genuinely absent — not installed, or not cached under `FI_OFFLINE`. If relevance cannot be computed at all, **every** domain skill is admitted and the selection report says why: selection can only narrow, so a catalogue that is too large costs tokens and is visible, while a silently too-small one changes results with nothing to show for it.

  Two commands teach FI a skill. `--teach-skill <name> --from <module>` drafts one from an installed library, reading its real signatures by introspection rather than generating them, and leaves the judgement calls — when it applies, when it does not, what its outputs may legally be — as TODOs for you. `--import-skill <path>` brings in a skill written for another agent, preserving the front-matter `description` that makes it findable and carrying its bundled directories; `--list-foreign-skills` shows what is available to import. An import **generates** a self-test rather than leaving the skill unusable: it probes that every bundled script is present and answers `--help`, which catches a broken, moved or incomplete install. That is deliberately less than a written test proves. A generated test cannot check that a tool still behaves the way `SKILL.md` describes — the thing a self-test exists for — so the generated file says so in its own text, `--skills` marks the skill, and approval repeats it. The marker lives in the file, so rewriting the test with real checks clears it; a flag in `provenance.json` would have gone stale at exactly that moment. For a prose-only skill with no scripts, the generated test states plainly that passing proves only that the files are on disk.

- **Degenerate-run guard** — `engine.degenerate_run_guard` (default on) treats a script that exits 0 but emits an all-zero RESULT_JSON as a soft failure: the execute-repair loop gets a chance to fix the underlying bug (wrong grid/sampling, a threshold/edge finder returning a zero sentinel, bad normalization) before a paper is written. If the result is still degenerate after repair, analyze flags it and frames an honest failure note instead of reporting silent zeros as findings.
- **Bounded result_json in the analyze prompt** — the full `RESULT_JSON` stays in state at full fidelity (it feeds `results.csv`), but the copy spliced into the analyze prompt is compacted to a ~200 KB budget. A pathological experiment can dump raw arrays/images into its `RESULT_JSON` — one low-k1 DUV quest emitted a 36 MB block that blew past `codex_cli`'s 1,048,576-char turn limit and hard-failed analyze. The compactor keeps the structure **valid and representative**: long lists keep head + tail elements with a count-of-elided marker, long strings are truncated, and dict keys + scalar summary stats (the values analyze actually reasons over) survive intact — so the model interprets summary statistics instead of choking on raw pixel dumps. A WARNING fires when compaction happens, pointing at the real fix (have the experiment emit summary statistics, not raw arrays). Complements the provider-layer input-cap guard, which remains the last-resort net for any oversized prompt.
- **Analyze-driven re-route** — `re_experiment` re-enters design; `broaden_lit` re-enters literature with the hypothesis folded in.
- **Cross-paper check** — per-finding literature search + supporting / conflicting / neutral classification. Optional CoVe-style **verification pass** (`engine.cross_check_verify: true`, default off): a second LLM call per finding re-examines each non-neutral assignment with pointed verification questions and revises the classification — typical revision is "this 'supporting' citation is actually too topically thin, downgrade to neutral". Adds 1 LLM call per finding with non-neutral hits (typically +1–5 calls per quest); skipped when the first pass produced no non-neutral assignments. Verified output replaces the first-pass classification in `state['cross_check']`; the first-pass snapshot is preserved alongside under `first_pass` for audit, and `verification_notes` carries the question/answer trail.
- **Pilot pass** — `engine.pilot_run: bool = False` (opt-in). Off by default because honouring `FI_PILOT` is a prompt instruction the engine cannot enforce: a script that ignores it runs at full scale under a fifth of the timeout, so it times out and warns on every quest. Turn it on once a setup has shown its scripts comply. Before the real run, the engine executes the same `experiment.py` with `FI_PILOT=1` set (the implement prompt instructs the script to shrink whatever dominates runtime while keeping the identical metrics and `RESULT_JSON` keys) under a short timeout (`engine.pilot_timeout_frac`, default 0.2 × `execution.timeout_s`, floored at 30s). `execute_reflect` already repairs a script that *crashes*; the pilot catches the other failure — a script that runs cleanly and answers the wrong question, which otherwise costs the full timeout to discover. Its numbers are **discarded**; only its signal is used, and it never fails a quest: a pilot that crashes logs a warning and the full run proceeds (where `execute_reflect` can repair it with the traceback it needs), and a pilot whose values break the design's own `result_assertions` warns that the **design** is the likely fault (range, units) rather than the code.
- **Design-revision provenance** — `needs/DESIGN_HISTORY.json`. `review` and `cross_check` can both route back to `design`, so a hypothesis can legitimately be rewritten after its results are known. A finished paper looks identical either way, which is what makes the record necessary: entry 0 is the pre-registration (stated before any result existed), and every later entry is flagged `post_hoc` with the trigger that sent the engine back (`analyze.next_step`, or the reviewer verdict) plus whether the hypothesis text actually changed. Nothing is blocked — the record exists so the revision is auditable rather than invisible.
- **Multi-seed replication** — `engine.execute_replicates: int = 3` (default 3). A single run is not a result: one number has no error bar, so reporting it as a finding overstates what the experiment showed. Replication re-runs the generated SCRIPT only -- `implement` is not re-invoked, so it costs only local compute, with one exception: at most **one extra LLM call** per implement pass, spent only when the script ignores the seed (below). Set 1 to opt out on a slow experiment. When >1, the execute node runs the generated `experiment.py` N times: each with its own `FI_REPLICATE_SEED` — **the first run included** — so the script can deterministically seed every RNG it uses (the implement prompt instructs it to read this env var). **The seeds are spaced so no two runs can share a draw.** Consecutive runs' seeds stride by `engine.replicate_seed_stride` (a million by default), because a script rarely uses the base seed directly: it derives one seed per trial, and `base + counter` is the obvious way to write that. Handed bases a few integers apart — 42 for the unseeded first run and 1 and 2 for the replicates — a graded quest drew 259 of every 300 trials in common between one pair of its three runs and 299 of 300 between another, then reported the spread across those near-identical runs as a 95% confidence interval: printed `0.581–0.581` and `0.941–0.941`, and read back in its own limitations section as evidence of stability. A stride keeps the streams disjoint for any experiment drawing fewer than a stride of seeds per run (that quest drew 2,700), so what varies between replicates is variation the experiment produced. All N `RESULT_JSON` payloads land in `state['result_json_replicates']`; the analyze node aggregates every numeric leaf — **nested results included**, flattened to dotted paths like `by_h.0.5.RK4.trajectory_error`, which is the normal shape for a parameter sweep — with mean ± sample-std **plus standard error and a 95% confidence interval**. An interval stops at the values its metric cannot pass: 0 and 1 for a metric named as a probability or proportion (`probability`, `fraction`, `share`, `accuracy`, …) whose seeds all lie in [0, 1], and the range the design's or a skill's `result_assertions` declares for it. Metrics that were identical across every seed are omitted from the analyze prompt and counted in a note, so a crossed design cannot crowd out the analysis it is meant to inform and surfaces them to the writer so the paper reports `metric (95% CI lo–hi, n)` instead of a single-seed point estimate. **Line figures are drawn as the mean.** The plot-style bootstrap keeps each seed's lines; after the seeds run, a figure whose panels hold only lines, with the same labels and x values at every seed, is drawn again over the same file as each line's mean shaded with its 95% confidence interval (bounded like the results), by `code/replot_figures.py` in the quest's Python under the house style, and the writer is told the figure is the mean of N seeds. Its legend is set outside the axes, to their right (the saved image grows to hold it), when it has four or more entries or when the drawn canvas shows it over a line or a band: the engine draws that figure, so nothing else moves its legend, and of the 20 redrawn figures in the stored quests whose layout was measured, 6 (in 4 of 9 quests) had it over their data, a legend of six to eight entries in the middle of the axes. Redrawn again with this rule from the stored plans, under each quest's own house style and recorder, the 6 of 8 figures rechecked that had it over their data no longer do. Error bars count as part of their line (`errorbar` with y errors and a drawn line): each series is drawn at its mean, and the 95% confidence interval over the seeds replaces one seed's bars. A bar chart, a histogram, a scatter, or a figure with anything else on it (text, an image, a colourbar) goes back to the primary run's file and its record of what it draws (seed 0), since every seed draws over the same files; the writer, the analysis and the review are told it shows replicate seed 0 only (seed 0 of N when the number of seeds is known): a seed repeats the whole experiment, so the figure holds every run that seed made, not the mean over the seeds, and the text quotes seed 0's values for it or says it shows a single replicate (seed 0). An empty shaded band that draws nothing (seaborn leaves one per line when each x holds a single observation) does not count as anything else. The number check and the claim check compare the paper with each result's mean and 95% CI over the seeds as well as with seed 0's values. **Stops early on a deterministic experiment.** Honouring `FI_REPLICATE_SEED` is not the same as consuming randomness: a script can seed every RNG and still compute the same answer every time (integrating an ODE, say). After seed 1 its `RESULT_JSON` is compared against seed 0; if they are identical the remaining seeds are skipped and analyze reports that the experiment is deterministic rather than printing an aggregate of zeroes. Costs at most one extra run to find out, and unlike asking the design to declare itself, it cannot be wrong about what the script did. **A script that never names its seed is sent back once, right after `implement`.** The implement prompts tell the model to read `FI_REPLICATE_SEED` and write no seed of its own, and four of six recent codex quests did anyway (`RNG_SEED = ...`, `SEED = 20260919`, `MASTER_SEED`), so every replicate was the same run. When replication is on (`execute_replicates > 1`), the quest is not a background job, and the script written by `implement` never contains the name `FI_REPLICATE_SEED`, the engine makes one repair call (`implement_seed` in `cost.jsonl`, so its cost is visible): the same request `execute_reflect` makes for a repair, with the whole script and one change asked for — read the integer from `FI_REPLICATE_SEED` (0 when unset) and derive every random generator's seed from it, keeping everything else as it is. The repair is written over `code/experiment.py` only if it parses as Python and now names the variable; a repair that did not, or a call that failed, is dropped with one `[implement]` warning and the script stays as written, so the fallback below still applies. It never runs for a single replicate, a background job or a script that already reads the seed, and it does not use up the `execute_reflect` repair budget. Measured over the 132 `experiment.py` files in the stored outputs, 56 do not name the variable (15 of 66 in the recent SIR quests, 41 of 66 in older ones written before the instruction existed), including the four quests that motivated this. Only a source scan and a fake model have exercised that shape: no real model has been asked to make that edit. **The same call goes out when the script reads the seed and builds a generator the seed cannot reach.** Naming the variable is not obeying it. One graded quest read `FI_REPLICATE_SEED`, handed it to `np.random.seed`, and drew all 300 of its Gillespie trajectories a cell from an `np.random.default_rng()` built ninety lines earlier with no seed at all -- separate streams, so the legacy global's seed reached none of them. That failure hides better than the first: the replicates DO differ, so an aggregate, a standard error and a confidence interval are all published, and only reproducibility is gone. The engine parses the script and reports every generator built without a seed (`default_rng`, `RandomState`, `Random`, `SeedSequence`, the bit generators, and a bare `np.random.seed()`), counting an explicit `None` as no seed and resolving names through the script's own imports so a quest's own `Random` class is not mistaken for the stdlib's. A generator built in a `if rng is None:` fallback is left alone -- that branch is how a script says its caller hands it a seeded one, and rewriting a reproducible script costs a call and risks the script; the blind spot that buys is a fallback some call site actually takes. The request names the offending lines and says that seeding the legacy global does not reach a Generator, and the repair is kept only if the script then reads the seed AND builds no generator without one. Measured over all 188 scripts the stored quests generated -- 135 `experiment.py` and the 53 plotting scripts written beside them -- it reports exactly one: the Gillespie quest above. Both fallback idioms are in that corpus and both stay silent. Exercised once end to end on that quest's own script with gemma4: the model threaded one seeded generator through the simulation, after which the same seed produced the same results twice and a different seed different ones, where the script as shipped produced different results from the same seed. **A script that never reads its seed is not deterministic — it is unreplicated.** Two runs agreeing has two causes that are not the same fact about the experiment, and treating both as determinism is what let a hardcoded seed reach a paper: three graded quests shipped a script carrying its own `RNG_SEED` constant and 300 stochastic trajectories per cell, whose replicates matched to the last leaf (242, 314 and 333 of them) but for the ordinal FI itself injects. So when two runs agree, the script's own source decides which case it is. If it names `FI_REPLICATE_SEED` the experiment is deterministic, exactly as before. If it never names the variable it cannot have responded to it, so the runs are **one run repeated**: no replicate list is published at all, which leaves every downstream path — the analyze aggregate, the figure captions, the writer's "seed 0 of N" language, the number check and the claim check — on its honest single-run behaviour without any of them needing to know why, and analyze is told in as many words to report one measurement and to print no mean over seeds, no standard error and no interval. The blind spot is a script that *names* the variable without obeying it (reads and discards it, or mentions it in a comment): that one still falls through to the runtime comparison, which can only call it deterministic. A script that never reads the seed and whose runs nonetheless differ is drawing from OS entropy — those are genuine independent samples, so the aggregate stands, with a warning that the run is not reproducible. **Runs after the plausibility gate, not before.** A result that violates the design's `result_assertions` is about to be regenerated by `execute_reflect`, so replicating it first would pay N× for an error bar on a discarded number. Failure isolation: a single replicate failure (NaN, OOM, transient) doesn't abort the rest — the aggregator skips the failed seed; if the *primary* run fails the engine skips replication entirely (fix the script first via the execute_reflect loop). Cost: N executions per design pass. Use 3–5 for variance reporting; 10+ for the rare case where a tight CI matters.
- **Statistical rigor — CIs, effect sizes, multiple-comparison guard** — beyond the per-metric 95% confidence intervals above, when results carry `by_<factor>` strata the analyze payload also gets, computed in pure stdlib (no numpy/scipy): a **95% CI per stratum**, the **pairwise effect size** (Cohen's d + a negligible/small/medium/large label) between strata for each shared metric (strata nest: in a crossed design such as `by_h` → step size → method → metric, every level below the `by_*` key whose children share one shape is compared too, so method A vs method B is reported at each step size under a dotted label like `by_h.0.5`), and a **multiple-comparison guard** — the number of comparisons made and the Bonferroni-corrected α (`0.05 / N`), with a `many` flag when there are more than five. The analyze + write prompts are instructed to report the CI alongside each headline number, quote the effect size when claiming one group beats another, and not over-claim a single stratum difference that wouldn't survive correction; a single-seed run honestly reports "no replication → no CI." A small embedded t-table covers small-n replication exactly.
- **Stratification-by-factor across the implement/analyze/write contract** — when the experiment naturally has categorical strata (clip classes, methods, datasets, seeds, difficulty levels), the engine threads them through end-to-end. The `implement` prompt instructs the generated `experiment.py` to emit ``by_<factor>`` per-stratum breakdowns in `RESULT_JSON` alongside aggregates; the `analyze` prompt surfaces per-stratum findings as tagged bullets (``[by_clip_class:isolated_lines] ...``); the `write` prompt's honesty rules forbid collapsing those findings into an aggregate-only Results section unless the analysis explicitly notes the effect is uniform. Single-condition experiments are unaffected — aggregate-only stays aggregate-only.
- **Ideate self-reflection** — extra LLM call may swap the chosen idea (or `engine.ideate_tournament: true` for pairwise N-way comparison).
- **Design self-critique** — after the design is drafted (by the `plan` step, on the first pass), a second LLM pass audits it and emits an amended design BEFORE `implement → execute → analyze → write` spend compute on a bad plan. The checklist is the five patterns the methodologist reviewer hard-flags (circular evaluation, single-point eval, weak-baseline retention, dimensionless/grid-only metrics, natural-stratum collapse) and seven more: a precision that was chosen by cost rather than by the interval the claim needs (with the arithmetic: about 0.98/sqrt(n) for a probability near 0.5), the estimand and how its uncertainty is estimated (a spread across a few seeds is not a sample size), an arbitrary threshold the conclusion depends on, whether settings and runs share a random stream, numerical convergence and the invariant every run must satisfy, a declared oracle, and what becomes of failed runs. An amended design keeps every key the draft had (the `protocol` included). Failure-isolated: a transient provider error or a reply that cannot be used keeps the original draft, never blocks the quest. Every pass is kept in `needs/DESIGN_CRITIQUE.json`: the objections in full, the design before and after, the keys that changed, and a `status` that says `failed` (with the reason) for an audit that did not run, so it no longer looks the same as one that found nothing; `plan.md`'s *Checks already made* says which keys the audit changed, or that it did not complete. The reviewer panel (`review` after the paper) is a separate, later check and is still empty by default: the interview recommends it (a 3-persona panel by default, and a 4-persona one that adds the reproducibility reviewer, worth it for a stochastic simulation study) and the engine leaves the choice, and the cost, to you.
- **Two-stage implement** — the `implement` step is split into `implement_outline` (writes a Python scaffold with function signatures, constant sources, and the `RESULT_JSON` template — typically 30–80 lines with `raise NotImplementedError` bodies) and `implement` (fills in each function body, consuming the outline as input). Splitting the work lets each LLM call be smaller; on complex topics that previously triggered ~9 min extended-thinking spans on Sonnet 4.6, the outline+body pair lands in 2–5 min total with progress visible between calls. Failure-isolated: an unparseable outline OR a transient outline-call error makes the body fall back to the legacy single-shot prompt (also used on pre-Phase-2 checkpoint resume). The body stage commits to the outline's function signatures, so an outline mistake surfaces at body-write time rather than after execute. Default `provider.node_cli_timeout_s`: outline → 600 s, body/legacy-fallback → 1800 s (the body call typically finishes in 90–180 s once the outline lands, but the same `implement` bucket also covers the legacy single-shot fallback that needs the full extended-thinking budget). An explicit `provider.cli_timeout_s` acts as a **floor**: raise it and leave the per-node map alone, and every built-in entry below it — the outline's 600 s included — is raised to match, so a quest that asks for 900 s everywhere actually gets it.
- **Prompts carry only what their step needs** — two prompts used to carry text their step does not use. `implement_outline` fixes a script's structure (its functions, constants and result template) and received every selected skill's full text, about 21,000 tokens that the body stage receives again when it writes the calls. It now gets the summary the design step gets (what each skill is for, where it does not apply, why it was selected) and the body stage still gets the full text. A run that submits a background job (`execution.background_jobs`) or carries example files (`execution.inputs`) keeps the full text in the outline, since there the skills say how a job is submitted and how the examples are combined. `analyze` interprets an experiment's results and received the whole reviewed-literature block, 7,000 to 13,000 tokens that the write step and the cross-check read on their own; when an experiment produced results it now gets the titles of the sources retrieved (under 1,000 tokens), and the whole block stays for a survey or no-simulation study, a run on the user's own data (`--analyze`), a run with no results and a degenerate one. Replayed from three stored quests of one topic with the real model: 18 of 18 outlines parsed, outlines from the summary named the same functions and result template as ones from the full text (the two agreed with each other as much as two outlines of one kind did) at 2,066 prompt tokens per call instead of 22,894; 6 analyses with only the titles matched 6 with the whole block (5.0 against 5.3 key findings, 2.0 against 2.5 supported claims, every `next_step` still `publish`) at 25,098 prompt tokens instead of 34,702. Together about 30,000 tokens a quest, 13% of the 232,000 a quest used on average. Not measured: a topic other than the one replayed, a background job, and whether a graded paper differs; the analysis's `broaden_lit` route is now judged from the titles and the results, and it appears in 3 lines of the stored run logs.
- **Reviewer panel** — N personas in parallel + moderator synthesis (`rigor_score` + `depth_score` axes). The built-in **methodologist** persona hard-flags four common-but-fatal patterns: circular evaluation (optimization objective shares model/simulator/distribution with the evaluation metric — "train-on-test"), single-point evaluation where a sweep is the field norm, admitted-weak baselines kept in the comparison instead of re-run, and metrics in dimensionless / grid-only units without a physical-grounding bridge. Each persona's response includes a ``must_flag_hits`` list (canonical names: ``circular_evaluation``, ``single_point_eval``, ``weak_baseline_no_rerun``, ``pseudo_units``); the aggregator unions hits across the panel. A non-empty ``must_flag_hits`` forces another revise pass **even when** ``engine.review_loop: false`` is set — the operator cannot accidentally short-circuit the design loop the must-flag block exists to gate. The persona must explicitly state non-applicability of each check rather than reach acceptance by silence. **New quests (via the interview, CLI `--new`, or VSCode `@fi /new`) default to a 3-persona panel** (methodologist + statistician + devil_advocate) instead of the cost-conscious single reviewer; the methodologist must fire for the non-bypassable must-flag enforcement to take effect. Single-reviewer mode is still selectable in the interview when cost is the priority.
- **Unified human-in-the-loop (`pauses:`)** — every place the quest stops for a human is one of two interactions — **ANSWER** (it asks; you reply) or **SUPPLY** (it needs files; you drop them) — configured under one coherent `pauses:` section: `pauses.clarify` (off/auto/ask), `pauses.papers` (bool), `pauses.supply` (never/after_literature/before_build/before_review/both/all), `pauses.plan` (off/ask), `pauses.review` (off/ask), plus `pauses.auto_accept_on_pass` and `pauses.timeout_s`. The legacy flags (`engine.clarify_mode`, `engine.human_feedback_gate`, `engine.pause_for_user_input`, `knowledge.pause_for_user_papers`, `engine.auto_accept_on_pass`, `engine.human_feedback_timeout_s`) still parse and are mapped in automatically. Whichever pause fires, the engine writes one **`<quest_root>/NEXT_STEP.md`** — why it stopped, exactly what to do, and the resume command — and deletes it on completion; the Web GUI and VSCode each show a single **Action needed** affordance sourced from it. Resume is always `fi --resume <id>` (or the Resume button).
- **Human-review gate** — `pauses.review: ask` (the default) pauses the quest after the review node and waits for a human to accept / reject / refine the result before finalising. The snapshot includes verdict + score + must-flag hits + suggestions + the accumulated `feedback_history` of every prior refine round (so a later iteration honours every prior ask, not just the most recent). Three interfaces consume it:
    - **Web dashboard** — banner on `/quest/<id>` with Accept / Reject / Refine buttons + a textarea for refine feedback; in-process spawn paths resolve via a Python future, subprocess paths write `<quest_root>/.fi/human_review_answer.json` and auto-trigger a resume.
    - **CLI** — `python launch.py --config <yaml> --interactive` prompts on stdin (`accept` / `reject` / `refine` + one line of feedback). For a headless run that paused, decide in **one command** with the resume flags — `--resume <id> --accept`, `--resume <id> --reject`, or `--resume <id> --refine "your feedback"` (these write `human_review_answer.json` for you, no hand-editing). The pause message prints these exact commands. A terminal **`--accept` / `--reject` is guarded**: it's refused (exit 2) unless the quest is genuinely paused awaiting review (`pause.json` with `kind=review`), and it will not overwrite a *different* decision already staged (e.g. a `refine` just submitted from the web UI). This stops a stray CLI accept from silently bulldozing an in-flight refine and auto-finalizing past it. A **`--refine` is never blocked** — it's the user adding work.
    - **VSCode** — the chat panel renders the verdict + must-flag hits + suggestions; QuickPick collects the action; refine opens a second input box for the feedback text.
  An explicit **refine is always honoured** — `_route_after_human_feedback` routes it to a real revision pass even when `iteration >= max_iterations` (that cap bounds the *unattended* review loop, not the user's deliberate click); the refine runs one design→…→review pass and returns to the gate, so the user can refine again or accept. A finished quest can also be **re-opened for another pass** — the quest page's **Re-run** button (or `fi --rerun <id>`, or `POST /api/quests/{id}/resume?rerun=true`) re-enters the pipeline even when the LangGraph checkpoint is at its terminal state (`next=()`): the engine `aupdate_state`s back in at the human-review gate's edge so the graph re-routes through `design → … → review → human_feedback`, applying any saved `feedback_history` (so a refine that landed past the cap finally runs) and re-running whatever stages an Update invalidated. Without this a finished quest's checkpoint has no pending task, so a plain resume was a no-op.
- **Human-review timeout** — `engine.human_feedback_timeout_s` (default 1800 s; `0` disables) bounds how long a wired callback (web POST, VSCode QuickPick) is awaited. If it elapses, the engine stops waiting and falls back to the headless path (on-disk `human_review_answer.json`, else clean pause-exit with the snapshot saved + a `--resume` hint), so an orphaned UI prompt can never park a quest forever.
- **`--auto-accept-on-pass`** — auto-accept the human-review gate for *clean* papers only (verdict=accept AND no must-flag hits). Flagged or revise-verdict papers still pause for review. Intended for `--fleet` so the production runner doesn't block on every clean quest. Also exposed as `pauses.auto_accept_on_pass: true` in YAML and the engine fixture path used by tests.
- **Multi-model ensemble** — fan out a node's LLM call across multiple models in parallel and merge. Per-node `provider.node_ensemble` with `models` / `merge` (`tournament` | `synthesize` | `vote`) / `moderator`. Interview surfaces four preset profiles (`off` / `cross_check_only` / `ideate_and_check` / `full`, cost multipliers 1.0× → 2.5×); a profile chooses which nodes fan out, never which models — you name at least two, and FI adds none. `analyze.merge: synthesize` is rejected at config load.
- **No-simulation decision** — three-tier (`engine.no_simulation` → clarify `simulatability` → legacy `empirical_vs_theoretical`); routes through `auto_collect_data → wait_for_data → data_load → web_plots → analyze`. In this mode the design stage produces an **analytical / observational study** (a derivation, comparison, or synthesis — no executable experiment), and the paper is written as such: it never frames a "planned experiment that wasn't run" or narrates the engine that produced it.
- **Web-derived plots** — `engine.web_derived_plots` (default on) gives the no-simulation path figures even though it runs no experiment: an LLM charts the concrete quantitative data found in the collected web/data sources and writes a self-contained matplotlib script (data inline), run in the same sandbox the simulation path uses; each figure is stamped with its source. It charts **only numbers a source actually reports** — never the model's own categorization turned into a count (no fabricated "4 of 6 → 66.7%" pies) — and emits `NO_PLOT` honestly for qualitative topics with no real numbers, rather than forcing a chart. The script is prefixed with the **Frontier Insight house figure style** (Palatino-style serif, teal-anchored palette, warm off-white ground, hairline grid, no top/right spines) so the charts match the paper / poster / slides identity instead of the default matplotlib look.
- **One downloaded-sources folder** — retrieved sources are written once to `data/literature/` (the citation record, every quest). On the no-simulation path the analysis reuses that folder directly instead of duplicating it; `data/auto_collected/` holds only the *additional* agent-collected evidence (Axon hits, dataset-adapter tables) that isn't part of the cited literature, so the two folders never hold the same files twice.
- **License-clean figure enrichment** — `knowledge.fetch_web_figures` (off by default) embeds up to `knowledge.web_figures_max` (default 2) *illustrative* figures so a study carries a visual point of view beyond its own charts: a real figure from a **cited CC-licensed arXiv paper** (the default arXiv license forbids reuse, so those papers are skipped) plus **Wikimedia Commons** diagrams under CC / public-domain. Only ever embeds free-licensed images (CC BY / CC BY-SA / CC0 / public domain — NC/ND rejected); an LLM relevance gate drops keyword-match misfires; each figure is attribution-stamped (Source + license) and recorded with its caption + license so the writer credits it and the references log its provenance.
- **Quest plan (`plan.md`)** — after the literature and skills and before the design, the `plan` step writes `<quest_root>/plan.md`: what the literature says (each source named), the gap, success criteria, risks, what the quest will not do, the methodology audit's objections, and the design as a fenced YAML block under *The design (used as written)*. The design step adopts that block exactly (validated by `core/plan.py`: a hypothesis is required, `result_assertions` need a `path` and numeric `min` ≤ `max`), so a person's edit is what runs; without a plan file, or on a later revise pass, the design is drafted as before. The plan call is the design call with a plan directive appended, so the first pass makes the same number of model calls as before (the methodology audit still runs on it). `pauses.plan: ask` (interview question **Stop to read and edit the plan**; default `off`) stops the quest once the file is written; a `plan.md` whose design block cannot be read stops it again on every resume, with the reason. To change the plan without editing it: `launch.py --config <yaml> --resume <id> --revise-plan "<request>"` (web: the quest page's **Plan** panel; VSCode: `@fi /plan <id> <request>`), which rewrites the file through the `plan_revise` prompt, keeps the old one, and refuses a rewrite whose design block cannot be read. Versions live in `.fi/plan_versions/` and `needs/PLAN_HISTORY.json` (who: model / request / user); `needs/DESIGN_HISTORY.json`'s first entry names the plan hash. Web routes: `GET/PUT /api/quests/{id}/plan`, `POST/GET /api/quests/{id}/plan/revise`.
- **Experiment protocol (`protocol` in `plan.md`)** — the plan's design block may carry a `protocol`: `grid` (each parameter and every value it takes), `runs_per_setting`, `thresholds`, and the prose `seed_policy`, `ci_method` and `acceptance` (`core/plan.py::normalize_protocol` checks the numbers' shape; other keys are kept). The plan directive asks for it and says the topic's own numbers must appear in it; `core/protocol_check.py::plan_notes` lists under *Checks already made* any number the topic sets (braces, run counts) that the protocol does not hold. When `implement` has written the script (and after the seed repair), `_enforce_protocol` compares it with the protocol using only the AST, and reports a difference only on evidence: a **grid** axis is a list, tuple, numeric range or `for` loop over literals that the script names after the axis (`R0_LIST` for `R0`) or, unnamed, shares at least half its values with it, and differs when none of those lists holds exactly the protocol's values; **runs per setting** differs when the script names counts of runs (`NUM_RUNS`, `n_samples`, `TRIALS`, ...) and none is the protocol's; a **threshold** differs when its value (or that value as a percentage) appears nowhere. Assignments under `if os.environ.get("FI_PILOT")` (the engine's smoke test, which discards its numbers) are not read, in either polarity. A difference sends the script back for up to `engine.protocol_repair_attempts` (default 2) repairs, one script at a time, made with the `execute_reflect` template under the node name `implement_protocol` (so each is visible in `cost.jsonl`); a rewrite is kept only if it parses and has fewer differences than the script it replaces. If it still differs: `engine.protocol_check: block` (default) stops the quest (an interrupt with `protocol_stage`, pause kind `protocol`, its own `NEXT_STEP.md` naming each difference; `warn` logs and records it and goes on; `off` never looks). On resume a script that now agrees with the plan (edited by hand, or after a plan edit) is adopted as written and not generated again; one that still differs is written again. Every attempt is recorded in `needs/PROTOCOL_CHECK.json`, and the review's advisory notes (`goal_coverage_notes`) repeat any difference the final scripts have, which catches a constant changed by a later repair after a failed run. Nothing is checked without a `protocol` in the design, for a no-simulation or survey study, or in `--analyze` mode. What it does not do: it reads literals only (a grid built from a computed expression is no evidence either way), it cannot prove a script that agrees, and a repair by `execute_reflect` after the script is written is reported to the reviewer but does not stop the run. Fixture: the three stored SIR runs (`tests/fixtures/protocol_runs/`); the checker flags the one that swept `R0` over `{0.8, 1.2, 2.0, 3.0}` and `N` over `{100, 500, 1000, 5000}` for a topic that asked for `{0.9, 1.5, 3.0}` and `{100, 1000, 5000}`, and passes the other two.
- **Precision from a target, streams that are not shared by accident, and a grid dense enough for its claim** — the protocol's `precision` (`target_half_width`, optionally a `metric` and a `reason`; `core/plan.py::normalize_protocol` checks the shape) says the 95% half-width the headline probability needs. `core/stats.py::trials_for_half_width` gives the trials a probability near 0.5 needs (`z²·p·(1−p)/h²`: 1068 for ±0.03, 385 for ±0.05) and `wilson_half_width` the width trials give. The plan's *Checks already made* (`core/protocol_check.py::precision_notes`) compares them with the trials the protocol plans (runs per setting times the seeds the engine runs, `engine.execute_replicates`) and says how many runs per seed the target needs; a protocol with runs and no target is told what those runs give. After the run, `_annotate_precision` puts each pooled proportion's `ci_half_width`, the target and `precision_reached` in the analysis prompt, and a `precision_note` (which the analyze prompt turns into a limitation) when a target was missed. `grid_notes` says when a parameter the design's hypothesis, method or expected outcome makes a claim about (convergence, scaling, a threshold, a transition, a limit) has fewer than five values. The protocol check gained a fourth kind of difference, **`rng`**: `rng_reuse` finds a function with arguments that builds a random generator (`default_rng`, `RandomState`, `Random`, `np.random.seed`, `SeedSequence`, ...) from something that does not depend on them, and is called from a loop or more than once, so every call restarts the same stream and the settings share their random numbers (one stored run did exactly this, its `run_stochastic_experiment` called for every cell); it goes through the same repair and stop as a grid difference, and does not apply when the protocol's `seed_policy` says common random numbers, paired, a shared stream or coupled runs. On the three stored SIR runs only the one that rebuilt its stream is flagged. Not done: sequential stopping (adding runs until the target is reached), and a generator that varies with a value the script computes without using its arguments is not detected.
- **OpenAI-compatible models that fix their sampling** — `provider.fixed_temperature` (0 to 2) is sent on every HTTP call in place of the per-node temperature (0 for the deciding nodes, 0.2 for the others), and `provider.extra_body` is merged into every HTTP request body before a per-call `extra`; both ride on the resolved endpoint, so every client built from it (the engine's, the slides / poster / speech generators') applies them, and the fallback chain resets them (they belong to the primary's model). Moonshot's Kimi K2.6 and K3 need this: they answer any temperature but one with HTTP 400 (1 with thinking on, 0.6 with it off) and `extra_body: {thinking: {type: disabled}}` turns the reasoning off (one measured reply: 32 output tokens with thinking on, 4 with it off). `examples/kimi_moonshot/config.yaml` is a working example; the key comes from the environment variable named by `api_key_env`.
- **Numeric warnings fail closed** — `core/numeric_warnings.py::scan` reads a run's stderr and its printed results for the warnings that mean the numbers may not be what the script claims, and only these: `RuntimeWarning` overflow / invalid value / divide by zero, `IntegrationWarning` / `OptimizeWarning` / `ConvergenceWarning` / `LinAlgWarning` and their text ("maximum number of subdivisions", "not making good progress"), an argument that "has no effect for a chosen solver" or is unexpected, unrecognised or ignored (SciPy's `solve_ivp` given `abs_tol` instead of `atol` runs with its default and warns), `ComplexWarning`, and a NaN or infinity in a result. `DeprecationWarning`, `FutureWarning`, font, legend, layout and matplotlib warnings and "Mean of empty slice" do not count; each warning is named once and at most 8 are kept. `_node_execute` scans the primary run (`exec_result["numeric_warnings"]`), logs each as `[numeric]` and appends it to `needs/NUMERIC_WARNINGS.json`. With `engine.numeric_warnings: block` (default) `execute_reflect` treats the warnings like a crash or an implausible value: the script is sent back with the warnings and a request that names the SciPy tolerance arguments, forbids silencing the warning (`warnings.filterwarnings`, `np.seterr(all='ignore')`) and allows an `np.errstate` guard only around one intended operation, with a stated reason, all inside the same `exec_reflect_max_iterations` budget. If the warnings remain when the budget is spent, the quest stops instead of proceeding to analyze (an interrupt with `numeric_stage`, pause kind `numeric`, its own `NEXT_STEP.md`), with the hash of the scripts recorded in `.fi/numeric_stop.json`: on resume a script that changed is run again (and may stop again), and one that did not is accepted as it is (`numeric_warnings_accepted` in the state, cleared by the next run of the experiment), the warnings staying on record. `warn` only logs and records; `off` does not look. It reads the primary run only (replicates' stderr is not scanned), and it reads no warning it has no pattern for.
- **Oracles the script must pass before its main run** — the plan's protocol declares `oracles` (each a `name`, a `check` saying what is compared with what on which small case, and optionally a `kind` and a `tolerance`; `core/plan.py::normalize_protocol` checks their shape; the plan directive asks for at least one and lists a closed form, a limiting case, an invariant, an exact small case and an independent implementation as the kinds). The implement prompts give the contract (`core/oracle_check.py`): when `FI_ORACLE` is `1` the script does not run its sweep, it runs each declared check on a small fast case, prints one `ORACLE_JSON: {"checks": [{"name", "passed", "value", "expected", "tolerance"}]}` line and exits 0 if every check passed. `_oracle_gate` runs that at the start of `execute`, before the pilot and the main run (on `simulate.py` for a two-script quest), and reads the answer: a problem is any of (a) the protocol declares no oracle, (b) no `ORACLE_JSON` line, (c) a declared oracle not among the checks, (d) a check whose `passed` is not true, (e) a non-zero exit, (f) a timeout (the pilot's). A protocol with no oracle first asks for the plan to be rewritten with one (the same rewrite as `--revise-plan`, so the version is kept and `plan.md` is what is read afterwards); a missing or failing check asks for a repair of the script, one at a time, with the `execute_reflect` template under the node name `implement_oracle` (kept only if it parses and honours `FI_ORACLE`; the request forbids loosening a tolerance, skipping a check or hard-coding its answer, and asks which of the simulator and the check is wrong). Up to `engine.oracle_repair_attempts` (default 2) attempts in all; then `engine.oracle_check: block` (default) stops the quest before the main sweep (an interrupt with `oracle_stage`, pause kind `oracle`, its own `NEXT_STEP.md` naming each problem), `warn` logs and records it and goes on, `off` never looks. On resume the checks run again before anything else, against the script on disk and the protocol in `plan.md`. Every attempt is recorded in `needs/ORACLE_CHECK.json`. Nothing is checked without a `protocol` in the design, for a background job, for a no-simulation or survey study, or in `--analyze` mode. The protocol (for the oracle gate and the implement-time protocol check) is now read from `plan.md` on the first pass, so an edit made to it while a quest was stopped for the protocol takes effect on resume. What it does not do: it cannot tell a strong oracle from a weak one (a check the script can always pass is asked not to be written, not detected), and a repair by `execute_reflect` later does not rerun it.
- **Evidence status** — `core/evidence.py::assess` reads a quest's records (the paper-vs-results audits, `PROTOCOL`/`ORACLE_CHECK`/`NUMERIC_WARNINGS` records, the precision each pooled proportion reached, the review verdict) and names the highest of four levels it reaches: `executed`, `internally_consistent`, `validated_against_oracle`, `publication_ready`, with the `gaps` that stand between it and the next. It is written to `needs/EVIDENCE.json` when the quest ends, needs no model, and never touches the quest; it is shown in the run summary (`evidence`), the web quest page (`/api/quests/<id>` carries it) and as a `[FI] evidence:` line in VSCode.
- **Intervals that say what they are an interval of** — a probability that a script estimates from repeated trials is reported with its counts beside it in `RESULT_JSON` (`<name>`, `<name>_count`, `<name>_total`; asked for in the outline and both code-writing prompts). The engine runs the script once per seed, and `_aggregate_result_json_replicates` pools the seeds' counts: `ci_method: wilson_pooled_counts` gives a 95% Wilson interval for the pooled proportion (with `n_trials`, `n_successes`, `se`, and the seeds' own `batch_mean` / `batch_std`), where the t interval over three batch proportions used to be the headline uncertainty (for three batches of 300 runs at R0=1.5, N=5000 that interval was 0.3218-0.3382 for a run whose 900 trials give a Wilson interval of 0.3001-0.3614, and 0.2280-0.4453 for another whose 900 trials give 0.3065-0.3682). A mean over selected trials that the script reports with `<name>_values` beside it gets `bootstrap_pooled_values` (a deterministic percentile bootstrap over the pooled values, thinned to 20000; the long lists are left out of the analysis prompt and counted in `n_values`). Every other metric keeps the t interval and is labelled `t_between_seeds`, and the analyze and write prompts say that interval is a spread across seeds, not the number of trials. Counts that do not add up (not whole, more successes than trials, missing from a seed) are not pooled. The statistics check's `interval_method_mismatch` (a paper interval labelled with a named method whose endpoints ARE FI's seed-level t interval) is asked only about the intervals whose `ci_method` is `t_between_seeds`: a pooled Wilson or bootstrap interval printed under its own name is that estimator, and was condemned as a mislabel by a real quest until the interval handed to the check said which kind it was. Not done: a single-replicate run does not use counts, and the intervals of the between-strata comparisons (`comparison_stats`) still come from the seeds.
- **Pause-drop-anytime** — opt-in user-input gate at up to three natural pause points: `pauses.supply: never | after_literature | before_build | before_review | both | all` (default `never`; `both` is before_build + before_review, `all` is all three). `after_literature` splits a quest in two: it stops once the literature is saved, and `--resume` starts the second half — skills, design, experiment — with that literature already in state, without searching again; papers dropped in `inputs/papers/` meanwhile join it. When set, the engine pauses after the named stage (LangGraph `interrupt()` → clean rc=0 exit with the unified `<quest_root>/NEXT_STEP.md` explaining what to drop where), the user drops reference papers into `inputs/papers/` (PDFs/MDs, ingested by the literature node on resume) and/or datasets into `inputs/data/` (CSVs/JSON/Parquet/etc., walked into `state['user_supplied_datasets']` and surfaced in the analyze prompt under the `_user_supplied_datasets` key inside its `result_json` block — no new `$placeholder` in `analyze.md`, so the prompt stays backward-compatible), then runs `fi --resume <quest_id>`. A disk marker at `<quest_root>/.fi/paused_at_<stage>.flag` is the authoritative "already paused here" signal so a re-entry doesn't loop the user through the same drop screen (state-only tracking can't survive a LangGraph `interrupt()` raise — the partial state-list update never lands in the checkpoint). Datasets are picked up by both the design node (on after-design resume) and the analyze node (catches drops staged at after-paper), so the analyze prompt always sees fresh data regardless of which pause stage was used.
- **Auto-collect before pause** — `auto_collect_data` queries Axon with `topic + hypothesis` and drops up to `engine.auto_collect_top_k` (default 5) hits into `data/auto_collected/` before pausing for the user.
- **Dataset adapters** — `engine.dataset_adapters` opts into structured external lookups (`worldbank`, `wikipedia`). Writes evidence into `auto_collected/<adapter>/`.

### Knowledge layer

- **Axon-backed retrieval + write-back** — literature retrieval and cross-quest memory.
- **Web research toggle** — `knowledge.web_search` (interview question **Web research**, default on, independent of the Axon layer) runs a general web search (Brave when `BRAVE_API_KEY` is set, else keyless DuckDuckGo) in parallel with academic retrieval, and `knowledge.web_fetch_pages` (default on) fetches each hit's full page text so the writer can quote it and the plotter can mine numbers.
- **Literature downloaded for every quest** — the literature node writes each retrieved source to `data/literature/lit_NNN_<slug>.md` (provenance front matter + content) for **every** quest, simulation and observational alike — so the collected corpus is always auditable on disk even on the simulation path (which never reaches `auto_collect_data`).
- **Bot-wall handling + open-access full-text cascade** — many academic sources (PMC, MDPI, …) serve a reCAPTCHA / "checking your browser" wall on a `200`, and paywalled publishers (ScienceDirect, Wiley, IEEE, Springer) serve an abstract-only stub; both are detected and discarded (paywall stubs via a schema.org `isAccessibleForFree` / known-paywall-vendor / call-to-action check) rather than stored as content. For an academic source the fetcher prefers the clean open-access full text directly: it resolves the article's `PMCID` / `DOI` / arXiv-id (cross-resolving via Europe PMC when a web result carries only one), then tries, in descending order of text quality, **the PMC BioC API** (clean section-labelled passages, no HTML cruft), **Europe PMC** `fullTextXML`, the **preprint** server (arXiv / bioRxiv / medRxiv), **Unpaywall** (every OA location, published-version + direct-PDF + repository copies first), and finally **Semantic Scholar** / **CORE** (when an API key is set). Whatever is recovered lands as real full text instead of a snippet. **Formulae survive.** BioC hands back its passages with the mathematics removed, so a sentence that stated a formula arrives truncated to its punctuation — a stored record read `the probability of no outbreak is either 1 or .` where the paper says `(1/R₀)ⁱ` — and a claim the source genuinely supports then cannot be verified against it. So when a recovered PMC body has no mathematics left in it *and* that article's XML does carry formula markup, the Europe PMC XML is kept instead; an article that never had formulae keeps its BioC text and pays one extra keyless request. Flattened XML also keeps its paragraph breaks (and drops journal front matter and the reference list), so the excerpt chunker splits on paragraphs instead of mid-word.
- **Clean main-content extraction** — HTML pages are run through `trafilatura` (when installed) to isolate the article body and drop nav / menus / related-article / reference cruft, falling back to a built-in tag-strip extractor otherwise. Figure captions + image alt-text are appended so the writer is aware of a source's visuals.
- **Relevance-selected excerpts** — full text is fetched and stored uncapped on disk, but each node's prompt receives only the passages most relevant to the quest question (`knowledge.literature_excerpt_chars`, default 4000). Ranking is `knowledge.passage_ranking`: **`auto`** (default) blends sentence-transformer cosine with lexical term overlap so a result stated in *paraphrase* ("death rate" for a "mortality" query) is still surfaced — `FI_OFFLINE` loads the model from the local cache rather than skipping it, falling back to pure lexical only if no model loads at all. `hybrid` and `embed` request the semantic path explicitly (still falling back to lexical if the model is unavailable); `lexical` forces the dependency-free term-overlap path. So a result or number buried mid-document reaches the writer / plotter — not just the abstract that happens to sit in the first 2000 characters.
- **Independent Axon vs external caps** — `knowledge.top_k` (default 8, RAG precision) is independent of `knowledge.external_top_k` (default 20, web breadth). The literature node passes both; ideate/cross_check seeds respect the smaller per-call cap.
- **Audience-aware citations** — `output.audience: "external" | "internal"`. External papers drop FI-internal cross-quest entries from References; internal papers keep everything.
- **Further reading** — web pages are listed apart from the scholarly sources a claim is cited to. The writer's prior-work block numbers papers `[1]`, `[2]`… and labels web pages `[W1]`, `[W2]`…; the engine writes the paper's `## References`, listing the papers the text cites, and a `## Further reading` section listing every web page; a list the writer wrote itself is replaced. Every output labels from one de-duplicated list: claim grounding accepts a `[W<k>]` source, the poster's reference band lists the web pages its text cites as `[W<k>]` with their site name, the slide deck leaves the web pages to the paper, and the pages are exported to `paper/further_reading.bib` / `.csl.json`. The review's depth floor (at least 3 sources discussed by content for a journal-length paper) counts References and Further reading together. Applies to every quest.
- **Axon sidecar auto-launch** — every CLI / `--serve` boots `python -m axon.api` if one isn't already listening. Skip with `--no-axon-sidecar` or `FI_NO_AXON_SIDECAR=1`.
- **Axon endpoint discovery** — the sidecar's port isn't fixed (Axon resolves it as `--port` > `AXON_PORT` > its `config.yaml` `api.port` > `8420`), so FI searches instead of assuming: the running server's own lock file (`<projects_root>/.axon-api.lock`), then Axon's `config.yaml`, then the built-in defaults, probing each until one answers. All three surfaces use the same search, so a sidecar you started by hand is found without configuring anything. `AXON_API_BASE` (or the VSCode `frontierInsight.axonUrl` setting) pins FI to one specific instance — useful for a remote or containerised Axon, and deliberately *not* a fallback, since two Axon instances hold different corpora. When nothing answers, the error names every endpoint tried and where each came from. In VSCode the search also runs patiently at startup — the extension keeps watching for `frontierInsight.axonStartupWaitSec` (10 minutes by default) and stays silent throughout, so starting Axon minutes after opening the editor produces no notice at all; only a sidecar that never appears does.
- **Offline / air-gapped models** — `knowledge.offline` + `knowledge.models_dir` (or `FI_OFFLINE` / `FI_MODELS_DIR` env) load the embedding + reranker weights from a local HF cache with no network call. Produce a shippable cache on a connected machine with `launch.py --export-models <dir>`. Both the in-process layer and the sidecar honour it. See `docs/INSTALL.md`.
- **arXiv request queue** — every connection FI makes to arXiv (full-text HTML and PDFs, abstract pages, figures, arXiv copies found through Unpaywall or Semantic Scholar, and the headless-browser fallback) goes through one queue: one connection at a time, at least 3 seconds apart, as arXiv asks of automated clients. The queue's state is a lock file under the cache directory, so it holds across processes too — the web UI and VSCode run each quest in its own process. A rate limit (HTTP 429) pauses the whole queue for 1, then 2, then 4 minutes; if arXiv is still refusing, that quest stops contacting arXiv and the other sources carry on, and the source failure report says so. Work with a time budget (full-text enrichment has 90 s) gives up on a slot it cannot get in time rather than sleeping through a backoff. Successful responses are cached on disk for 24 hours (`FI_CACHE_DIR`, default `~/.frontier-insight/cache`; `FI_ARXIV_CACHE=0` disables), so a resumed or repeated quest does not download the same papers again.
- **Multi-source literature router** — arXiv / OpenAlex / Crossref / Semantic Scholar / PubMed / CORE / OpenAIRE / DOAJ / Google Scholar in parallel, deduplicated by id and normalized title. CORE, OpenAIRE and DOAJ need no key; they carry the open-access humanities and social-science books, theses and journals the STEM-leaning indices cover thinly, and the router is told to use them for those topics. CORE also accepts an optional `CORE_API_KEY` for a higher rate limit. OpenAIRE and DOAJ require every query word to match, so when a longer query finds nothing FI retries once with its first three words. arXiv is searched through OpenAlex's arXiv source rather than arXiv's own query API, which has been capacity-throttled for everyone since arXiv's move to the cloud; full text still comes from arxiv.org. `knowledge.openalex_api_key` / `OPENALEX_API_KEY` unlocks OpenAlex's full daily budget (keyless is about 100 searches a day, and arXiv searches count against it); it is sent in a request header, so it never shows up in a logged request URL. And `knowledge.semantic_scholar_api_key` / `SEMANTIC_SCHOLAR_API_KEY` gets Semantic Scholar off its mostly rate-limited shared pool.
- **General web search** — `knowledge.web_search` (default on) adds a general-web layer (Brave when `BRAVE_API_KEY` / `knowledge.brave_api_key` is set, else keyless DuckDuckGo) that runs **in parallel** with Axon + the academic adapters for every quest and is merged + deduped by URL/DOI/title. This is what lets non-academic topics (company financials, markets, current events, culture, how-to) retrieve real sources instead of irrelevant nearest-neighbour papers. Web hits carry their `url` / `site` as citation metadata. With `knowledge.web_fetch_pages` (default on) the result pages' readable text is fetched (not just the snippet) so the writer can quote real content and the plot step can mine numbers from it.
- **Blocked pages render one at a time** — `knowledge.headless_fetch` (default on) retries a page that answered 403 or came back empty by rendering it in a headless browser, which clears the Cloudflare / JS-only walls a plain request cannot. Those renders **take turns**: one browser, and one browser driver, at a time for the whole process. Each render starts its own driver process and drives it over a pipe, and several of them running at once can break that pipe — a failure Node reports as an unhandled `'error'` event, which ends the process outright rather than raising it, so nothing downstream ever gets the chance to record it: the quest is simply gone, without even a source failure report to say what happened. Taking turns is slower for a quest with several blocked pages, since the renders now add up instead of overlapping, and that is the deliberate trade — a slower literature step instead of a lost quest. **Only the render takes turns.** Everything else in the same batch still runs in parallel: the ordinary page fetches, the open-access cascade (Europe PMC, PMC BioC, OpenAlex, arXiv, Unpaywall) and the publisher PDF downloads. A render that cannot get its turn before the full-text budget expires gives up, keeps the search snippet, and is listed in the source failure report like any other source that could not be fetched.
- **Relevance guard** — `knowledge.relevance_guard` (default on) scores the auto-collected sources against the topic and drops confident-but-off-topic hits; if nothing is on-topic it pauses for user-supplied sources rather than writing an honest-but-useless "pipeline failure" paper on garbage. Fail-open on any judge error.
- **Literature relevance floor** — `knowledge.relevance_min_score` (default 0.20) is a cheap, deterministic complement to the LLM relevance guard, applied in the **literature node for every quest** (the guard runs only on the auto_collect path, which survey/simulation quests skip). Each retrieved doc is scored by embedding cosine (the shared all-MiniLM model) against the **topic**, and the off-topic tail is dropped before it reaches analyze/write — so a "sculpture in pop culture" quest no longer carries change-point-math papers. Never-starve: `knowledge.relevance_min_keep` (default 3) always retains the top-scoring docs; fail-open when embeddings are unavailable (FI_OFFLINE); `0.0` disables.
- **Literature screen** — `knowledge.literature_screen` (default on). The embedding floor scores word overlap, so a journal's table of contents, or a paper on another system that shares the search terms, still passes it. After the floor, one batched call (node `literature_screen`, run at temperature 0 like the other gates) grades every retrieved source 0–3 on one question: could the paper cite this for a claim? Scholarly records need a 2 to stay. Web pages are dropped only at 0, because they are kept for the text the writer quotes. The rubric tells the model that for a quest without an experiment, books and chapters count as fully as articles. At least `knowledge.relevance_min_keep` sources survive, best grades first. A failed or unreadable call keeps everything, and a source left ungraded is kept. Sources the user supplied (`knowledge.local_papers`, `inputs/papers/`) are never screened. Kept sources carry `screen_grade`.
- **Foundational works** — `knowledge.foundational_works` (default on). A search engine matches every word of a query, so the original papers and standard textbooks a topic rests on rarely come back: for a quest comparing integrators on a damped oscillator, none of the three facet queries returned Verlet (1967), Hairer, Lubich & Wanner, or Butcher in OpenAlex's first 200 hits, and sorting by citations only pulled in famous off-topic work. After the relevance floor, one call (node `literature_foundational`) asks the model for up to eight foundational works (any beyond the eighth are ignored); each is looked up by title in OpenAlex (sorted by citations, books and chapters allowed) and kept only when a record's title matches and its year is within two or its authors include the suggested first author. **A suggestion whose title matches nothing is looked up once more, by author and year.** The model names works whose author and year it knows and invents the title: for one topic it named Whittle (1955) under four different titles, none of them real, and it paraphrased Gillespie (1977) and Kermack (1927) so that their titles matched nothing, while OpenAlex holds all three. So the second request asks OpenAlex for the works by that surname (a whole word of an author's name, so "Ball" is not "Ballesteros") published within a year of the suggested one, most cited first, 25 of them, books and chapters allowed, and takes the first that shares a word of subject matter with the suggested title (a word of three letters or fewer and a short stop list do not count, and only a word's first six letters are compared, so "epidemic" and "epidemics" are one word). The suggested title is used only to tell that author's papers apart, never to match. The record found is labelled `suggested as a foundational work; found by author and year, the suggested title did not match`, the title the writer sees and cites is the record's own, and the run log's outcome line reads `<suggested> -> <the record's title>, by author and year`. One record at most per suggestion, and no second request after a lookup OpenAlex refused with HTTP 429, since a spent budget refuses it as well. What it takes is a candidate, not a finding: the literature screen grades it like any foundational candidate, and that grading is what keeps off-topic work out. Tried without the word check on the 19 suggestions the model's titles failed to find across 76 logged runs of one topic, and on five other topics (lithography, quantum noise, optical imaging, mammal evolution, numerical integration), 92 candidates went to the screen (the shipped lookup applies its word check first and would have thinned them, so this measures the screen's judgement of an author's works, not the check's): every work from another field (surgery, genetics, marketing, atmospheric reanalysis) was graded 0 or 1 and dropped, and 14 were kept, of which 6 were the canonical works (Gillespie 1976 and 1977, Kermack 1927, Whittle 1955, Abbe 1873, Simpson's *The Major Features of Evolution*), 7 were real neighbouring papers by the same authors (sequels of Kermack's, a Diekmann textbook) and 1 was a wrong paper of the right field (*Sauropoda*, for a topic on mammals). Replayed through the changed lookup and the real screen on the suggestions three quests had lost, it found and kept Whittle (1955, graded 3) and Gillespie (1977), the works that cost those quests canonical-works points. It does not always find the work meant: a common surname puts a more cited paper of another subject ahead of it (Bernstein 1993 returned *Quantum cellular automata*, which the screen dropped, not the Bernstein-Vazirani paper), and a wrong year returns a neighbouring paper of the author's instead. It has not been run through a whole quest: whether the writer then cites what it finds, so whether a canonical-works score moves, is not measured. The works that at least two retrieved papers cite (two OpenAlex requests over their reference lists) are added too. Works already retrieved are dropped. That is up to eighteen OpenAlex requests per literature pass (eight title lookups, up to eight author-and-year lookups for the ones that matched nothing, and the two over the reference lists), sent one at a time with a second between them; without an `OPENALEX_API_KEY` the keyless daily budget covers fewer quests. A lookup OpenAlex refuses with HTTP 429 looks exactly like a work it does not hold, so the lookup logs a warning with the number of refusals and the `OPENALEX_API_KEY` hint: on one real day four concurrent quests each met 13–15 refusals once the keyless daily budget was spent, and found no foundational work. The rest join the candidates labelled foundational, and the literature screen grades them with one extra rubric line: a method's original paper or textbook is a 2 when the paper would cite it for something it uses, however old, and a famous work the question does not use is still a 0 or 1. Their `data/literature/` files record how each was found (`foundational:`). A failed call or lookup adds nothing. The run log lists every work the model suggested as `title (year, authors)`, untruncated, and then which were found in OpenAlex and added, which were already among the search results, and which were dropped because OpenAlex had no matching record, so a work the model never named can be told from one OpenAlex does not hold. **The writer is asked to cite them.** Being retrieved, screened in and labelled foundational does not make a paper cite a work, so the writer's prior-work block ends with a short note that lists the foundational works in the citable set (authors, year, title, whether it is a book or how many retrieved papers cite it) under the labels the writer cites them by, with one instruction: cite each one that bears on the paper's claims where it belongs (the original paper for a method or relation the paper uses, the standard textbook for the field), and none that does not bear on the paper just to cite it. The note is left out when the citable set holds no foundational work. The review prompt carries the counterpart as advice, never as a forced hit: an advisory list of the foundational works in the citable set that the paper does not cite, which the reviewer may ask for under its suggestions and is told not to flag or to send the paper back for on that alone. The run log records, after each draft, how many foundational works were in the prior-work block, how many the draft cites and which it left out.
- **Thin sources are marked for the writer** — a retrieved work whose stored text is only its title, or a book with a short blurb and no full text, cannot show a finding, a number or a mechanism, yet a graded quest cited a 57-character title-only record for "stochastic extinction" and a book blurb for "the effective R0 drops more rapidly". The writer's prior-work block (in the write prompt and in the edit prompt of a revise) puts `[title only]` or `[short blurb only]` after the title of such an entry, and so does the foundational-works list; the write instructions say once that such an entry may be cited only to say the work exists or for what its own title states, never for a specific finding, number or mechanism. The work stays in the list and every other prompt that reads the literature is unchanged. The test is on the stored text: a record with full text is never marked; one whose text after the title is under 100 characters is `title only`; a book without full text is `short blurb only`. Over the 2,321 sources of the 131 stored quests that kept their literature, 513 are title-only (508 with nothing after the title, five with 22–85 characters, none with 86–99) and 62 are book blurbs of 760–1,376 characters: 575 in all (25%), and none of them has an abstract or full text. A length cut alone could not separate a blurb from an abstract (137 articles have an abstract of 700–1,499 characters), which is why a book is decided by its type. On the write prompt of a stored quest with 19 marked entries the marks and the sentence add about 120 tokens to 21,800. A record with only its title is also checked in code after the claim check: a sentence that cites only title-only records and says at least four content words that those records' titles, authors and stored text do not contain ("Kermack and McKendrick [1] introduced the SIR model" adds one or two to a title that names its subject; a specific result adds many more) is marked `unsupported` in the claim ledger, however the check judged it. A claim the check grounded in such a record is changed to unsupported (the quote it gave can only have been the title), a sentence it did not list as a claim is added as one, and a claim it already marked unsupported, or grounded in the run's own results, is left as it is; a book's blurb is text the check can read and is not covered. On the 72 stored SIR papers this finds 9 sentences: the check had marked 6 of them unsupported and had not listed the other 3 as claims at all, and read by hand each of those 3 attributes a specific statement to a record that holds only a title (one was the graded citation loss of a final draft). The review's advisory about foundational works the paper does not cite carries the same `[title only]` / `[short blurb only]` marks and says to ask for such a work only to say it exists or for what its title states: in one stored quest a reviewer's advice to cite a title-only book for a claim led a rewrite to cite it twice, and the claim check then marked both sentences unsupported. All three interfaces share the engine.
- **Topic-aware LLM source routing** — agent picks venues (web + academic) from the source catalog.
- **Citable record types only** — scholarly indices also hold datasets, figure components, peer-review reports, dictionary entries and journal issues, none of which a claim can cite. Crossref, OpenAlex and OpenAIRE searches keep journal articles, conference papers, preprints and reviews. A quest without an experiment (a survey, a history, a humanities or policy question — `no_simulation` resolved on) also keeps books, book chapters and dissertations, because much of that scholarship is published there. The rule follows the resolved run mode rather than a separate subject classifier. Each retrieved record carries its `work_type`.
- **Keyword search queries, three facets** — the literature node does not hand the topic statement to the search engines, because a paragraph-long topic tends to match nothing in keyword-based academic search. One small call (node `literature_query`, routable through `provider.node_models` like any other) turns the topic, the chosen idea and, on a re-entry, the design's hypothesis into three short keyword queries, one per facet: the core subject, a specific angle and the wider frame. A single query reaches only the work written in its own words. The wording follows the kind of quest: methods, systems and measured quantities when there is an experiment; the names scholars write under (works, people, periods, places, movements) when there is not. The facets share one source-routing decision and only the first also runs web search. Their results are interleaved and deduplicated, and legal full text is fetched once, for the sources that survive the relevance screen. DOAJ requests are paced to its two-per-second limit. Any failure falls back to the previous title + topic string. The queries sent are kept on the quest state as `literature_queries`, and the first also as `literature_query`.
- **Local paper feed** — `knowledge.local_papers` pins paywalled PDFs / MDs to the retrieval head. An entry may be a **file or a directory** — a directory is scanned recursively for `.pdf` / `.md` / `.txt`, so a quest can be pointed at a folder that already holds enough research material.
- **Pause-for-user-papers gate** — `pauses.papers` (interview question **Supply paywalled papers**; default **on**, `false` for an unattended run) pauses when a real, resolvable paper (DOI / arXiv-id / PMID or an academic adapter) came back as abstract-only — the cases the open-access cascade genuinely couldn't fetch (SPIE / IEEE / Elsevier …). It writes a single ranked **`needs/WANTED_PAPERS.md`** — most relevant first (scored against the topic + hypothesis), each with a download link, what it's about, and its status — plus per-paper `needs/<slug>.json`. The user downloads the few that matter, drops the PDFs into `inputs/papers/`, and runs `fi --resume`; the literature node ingests them as `source=user_supplied` full text. In the **Web GUI** the quest page shows the wanted list with an upload box + Resume; the **VSCode** extension surfaces the same list with drop-and-resume instructions.
- **Full-text fetch** — `knowledge.try_fetch_full_text` (default on) fetches legal full text for the scholarly sources that survive the literature screen: open-access copies (arXiv, PMC, Unpaywall, …) and publisher PDFs your own network can already reach, with login walls rejected by a content-type and `%PDF` check. The whole batch shares `knowledge.full_text_fetch_total_s`; set `false` for abstracts only.

- **Paper PDF** via pandoc + LaTeX — real venue-flavored templates for `generic` / `neurips` / `iclr` / `ieee_access` two-column / `nature_mi`. Preprocessor lifts `# H1` into YAML `title:`, lifts `## Abstract` into YAML `abstract:` and the `**Keywords:**` line under it into `keywords:` (printed under the abstract and set as the PDF's keywords), shifts heading levels by −1, dedupes `"Title. Title."` patterns, puts a float barrier just above the reference list so a figure LaTeX is holding back for a later page is placed before that list instead of printing among the references (with no figure waiting the barrier does nothing, so a paper whose figures already sit beside their text keeps its layout unchanged), gives a figure line a blank line before and after it in the render copy when it lacks one (pandoc gives an image a numbered caption only when the image is a paragraph of its own, and three figures written one under the other printed with no caption at all in a stored quest: 5 pages with the captions, 4 without; the page-limit check renders the same copy, so it counts them), sets PDF metadata via `\hypersetup`. A figure is capped at 33% of the text height in every paper, so two figures and their captions fit on a page with text above LaTeX's `\topfraction`: the deferred-float queue drains beside the text that discusses it instead of backing up until the reference list, which is what put a figure after the references in the first place. Math is read in both spellings — `$x$` and `\(x\)` inline, `$$x$$` and `\[x\]` display — because writers use both; pandoc's markdown understands only the dollar forms on its own, so a paper written the backslash way used to reach LaTeX as text and stop at the first command (`Missing $ inserted`).   - Font choice: Noto Sans CJK / Source Han Sans first, then Microsoft JhengHei, Microsoft YaHei, Yu Gothic or Malgun Gothic, found through fontconfig or the Windows fonts folder.
  - With no XeLaTeX or no CJK font, the paper goes straight to the HTML fallback.

- **Selectable paper style** — `output.paper_style: latex | briefing` (default `latex`). `latex` keeps the venue LaTeX template (Computer Modern article). `briefing` renders `paper.pdf` in the Frontier Insight **"Research Briefing"** look — warm paper, deep-teal accents, serif display, the brand mark — via the HTML/Chromium backend, so it matches the slides + poster identity. It needs pandoc + a Chromium-family browser (no LaTeX) and falls back to the LaTeX path with a warning when those aren't present; it's single-column regardless of `paper_format`. Selectable in YAML and in the `--new` / `@fi /new` / web interview (the `paper_style` slot — under "Edit an advanced field" in VSCode). Works in all three interfaces because it's an engine-level config.
- **LaTeX-free PDF fallback** — `output.html_pdf_fallback` (default on) gives a 4th tier: when no LaTeX engine is reachable at all, pandoc renders `paper.md` into a Computer-Modern-styled HTML page (the `templates/paper/_html/latexlike.css` theme, with **Latin Modern Roman vendored + embedded** so the output matches the MiKTeX/tectonic `article` look — flush-left title, "Frontier Insight" byline, centered Abstract, numbered sections, justified body), then a headless system **browser** (Edge/Chrome/Chromium) prints it to `paper.pdf`. No LaTeX, no admin install — just pandoc (already needed) + a browser, which a locked-down machine almost always has; figures and fonts are inlined so the PDF is self-contained. It can't reproduce a venue's two-column class, so it always renders the single-column house style; set `output.html_pdf_fallback: false` to force the strict LaTeX-only path (skip-with-diagnostic when no engine). The pre-flight treats a present browser as satisfying the `paper_pdf` prerequisite, so `require_pdf: true` won't abort a quest that can render via the fallback. **The fallback also fires when a LaTeX engine is present but *errors*** — not just when none is found. A half-present MiKTeX that chokes on something the LLM emitted (a bare `\command` in text mode, an unsupported glyph) used to hard-skip the PDF; now the browser path — which never touches LaTeX — rescues it, so the same `paper.md` still produces a `paper.pdf` while the LaTeX error stays in run.log. The browser path reads the **same markdown dialect** as the LaTeX path and sets math as MathML, the `\(x\)` / `\[x\]` spellings included. What it cannot express it **keeps**: LaTeX written outside math prints as written and is named in a run.log warning, rather than being dropped. An HTML writer discards raw TeX silently, which is the worse failure — it turned "zero when `\(R_0\leq1\)`" into "zero when (R_0)" and a table header into `(R_0) (N) () () ()`, so the page read as a finished sentence that no longer said what the paper said.
- **Non-scientific paper formats** — `essay` / `report` / `policy_brief` / `whitepaper`, each with a full LaTeX template + per-format writer persona.
- **Author line** — `output.author`, `output.affiliation`, `output.contact_email` and `output.url` (all optional, asked as the last tier-1 interview questions on the CLI, web and VSCode) print under the paper title in every LaTeX template and the HTML render, set the PDF's Author field, go on the slides' title slide (HTML/PDF deck and pptx), and head the poster, whose QR code appears only when `url` is set. Pandoc receives them as metadata, which it escapes for LaTeX, so an `&` in an affiliation or a `_` in an email cannot break the compile. With no author set the byline stays "Frontier Insight". The values go only into the quest's own files. `output.poster_size` (`a1_portrait` default, `a0_portrait`, `landscape_48x36`) picks the poster sheet.
- **Research poster** — `poster.pdf` follows published poster guidance instead of squeezing the paper onto a page.
  - **Header:** the main finding as the headline, the paper's title under it, the author line, and a QR code when `output.url` is set.
  - **Type:** body 26 pt on A1 (36 pt on the larger sheets), headings about 1.5× the body, numbered figure captions, about 60 characters a line.
  - **Content:** the model writes headings, short texts, bullet lists and captioned figures to a word budget for the sheet; the generator writes all the LaTeX.
  - **References:** only the sources the poster cites, at most 8, without raw URLs.
  - **Layout:** whole sections go to columns, and figures fill each column, narrowing to 70% of its width to fit. When one column is planned to end more than 6 cm above the other, the longer column's figures narrow further, down to half the column, until the columns end together.
  - **Checked:** every compile is measured (fonts, overflow, column balance), and the result lands in `.fi/poster_fit.json`. The first plan never cuts content, since the header and band heights are only known once compiled; a compile that measures more room than planned is planned again. The model's reply is kept in `.fi/poster_reply.txt`.
  - **CJK:** Chinese, Japanese or Korean text compiles with XeLaTeX and a CJK font, as for the paper.

No external binary, so it renders on locked-down hosts; it replaced a `pandoc -o slides.pptx` shell-out that needed pandoc on PATH and produced an unthemed plain-white deck. Output is native, fully editable PowerPoint. **Each figure gets a slide of its own** (the prompt, `agents/slides.md`): the finding as the title, one bold lead sentence, the figure alone, and its discussion on the next slide; figure slides do not count toward the deck's 8-12. A figure is drawn at its slide box's width, and its tick labels shrink with it: beside bullets, a figure gets about 40% of the slide's width. Alone, the Marp theme lets it take all the room under the lead line (the 48vh cap stays for a figure that shares its slide with a list, table, code or quote), and the pptx draws it out to 0.75 in from each side edge and 0.6 in from the bottom instead of the text's margins. Measured on one stored quest's 13.1 in wide figures, a three-panel row went from 0.43 of the width it was drawn at (in the side pane) to 0.90 in the PDF and 0.87-0.90 in the pptx exported by LibreOffice. A 3x3 grid is height-bound and gains almost nothing by moving: 0.45 alone in the PDF (0.36 under the old cap) and 0.41 in the pptx, against 0.43 in the side pane. Grids are why a figure is capped at three panels (see Branded figures). A model that ignores the prompt is caught by the tick-label floor of the visual check below; whether models follow the prompt is not measured. This applies to the CLI, the web UI and the VSCode chat alike, since it is the engine's deck. Paragraphs and bullets keep the slide's order, and `**bold**`, `*italic*` and `_italic_` carry over (an underscore inside a word, as in `forward_euler`, stays as written). A Markdown **table** (`| a | b |` over a `|---|---|` delimiter row) becomes a **native PowerPoint table**, not lines of pipes: a tinted header row in the darker teal over a teal rule, hairlines between the rows, and each column as wide as its longest cell (compact when the table fits, wrapped inside the slide's body when it does not). `:---:` and `---:` set a column's alignment, and a cell reads like a bullet, so `**bold**`, `_italic_`, `` `code` `` and `$...$` math work in it; a cell that is only a formula keeps its column's alignment, which PowerPoint would otherwise set in the middle. The table counts in the slide's text height: its type is 14.5 pt and shrinks with the text down to a 10 pt floor, below which it is not shrunk further, so a table too tall even at 10 pt still runs past the bottom of the slide. `$...$` math (pandoc's rule, so "$5 and $7" stays text) becomes **native PowerPoint equations** (`generation/_pptx_math.py`: LaTeX → MathML with `latex2mathml` → OMML for rows, superscripts, subscripts, fractions and roots). Each equation carries a readable text form with real superscripts and subscripts for viewers without equation support. LibreOffice, and so the pptx visual check, shows that form. Math outside the supported set is written as that text only. A slide's text layer showing `$...$` or a LaTeX command is also measured as `raw_markup`. `poster.tex` always when `poster` is in `output.kinds`; `poster.pdf` compiles via the same 3-tier LaTeX-engine fallback the paper generator uses (pdflatex → system tectonic → repo-local `tools/tectonic[.exe]`), with a `poster_pdf_skipped.md` diagnostic on skip. Both the paper and poster run LLM-authored content through a shared Unicode sanitizer before pdflatex sees it — Greek/math glyphs become LaTeX commands, emoji are stripped, and **invisible/zero-width format characters** (zero-width spaces, joiners, BOM, soft hyphens, exotic spaces) are stripped or normalized, since a single stray U+200B otherwise hard-errors the compile. It finds math as pandoc does (`$...$` by pandoc's rule, so "$5 and $10" is text; `$$...$$`, `\(...\)`, `\[...\]`; never code), and inside a math span an en or em dash is set with `\text{}`, so a range written `$0.322–0.338$` prints a dash where LaTeX's `--` would print two minus signs, and a run of super- or subscript glyphs in math (`$10⁻³$`) is set as one script instead of stopping the compile. `speech` via single LLM call.
- **Consistent Frontier Insight design + branding** — the slide deck, poster, and paper share one editorial "Research Briefing" identity: a serif display face for titles, a system-sans body, a single deep-teal accent, and structure carried by hairline + teal rules rather than boxes. Each surface carries a subtle palette-native teal brand mark — a bottom-left corner lockup on the slides, a masthead lockup plus a reference-band mark on the poster, and a footer mark on the paper — driven from a single glyph asset so the look is uniform across all three.
- **Branded figures (matplotlib house style)** — experiment figures are no longer raw matplotlib defaults. Before the experiment runs, the engine drops a guarded `sitecustomize.py` bootstrap onto the script subprocess's `PYTHONPATH`, so Python applies the FrontierInsight house style at interpreter startup — *before* the generated code imports matplotlib, with zero edits to that code. The look: the brand teal-anchored qualitative color cycle (teal → terracotta → slate → olive → …), despined axes with a hairline y-grid, clean left-aligned editorial titles, frameless legends, and a branded teal sequential colormap (`fi_teal`) for heatmaps. The figure backdrop tracks `output.paper_style` — warm cream for `briefing`, white for `latex` — so figures blend into the paper they land in. Model-independent (it can't be forgotten or done wrong by the LLM) and failure-isolated (any error falls back to the plain environment). The same bootstrap records what each saved figure draws (`.fi/figure_records/<figure>.json`): every panel's title, axis labels, y scale and limits, and each line's or scatter's range, named by its label or by its entry in a legend given only names (`ax.legend(["euler", "rk4"])`), marked **flat** when it spans under 1% of its axis or **not shown** when it lies outside it. A series drawn by several calls with its label on the first (a scatter per point, say) is recorded as one series, and a single point is never flat. A series drawn with `ax.hlines`, `ax.vlines` or `fill_between` is recorded at the values it draws (the ends of its segments, the corners of its band), so a horizontal line at 0.94 is a series at 0.94 that shows **flat**, not one at 0; a collection that cannot be read that way (a mesh, or one drawn in axes coordinates) is left out of the record rather than recorded at 0. The writer and the analysis see that record next to each figure's file name, and before review a script checks every caption against it: a caption naming a series its figure does not show, or one it draws flat without saying so in the same clause ("stay flat at this scale", "near zero", "indistinguishable" say so) (the validation quest captioned a plot "energy drift rates for RK4 and Velocity-Verlet" while both lines lay flat at 0 under Forward Euler's spike) is listed in the review prompt with an instruction to must-flag `figure_caption`, logged, and shown in the human-review panel of the web UI and the VSCode chat. The reverse is checked as well: a caption clause that names a series by its exact label and calls it flat, constant, unchanged or horizontal, when the figure draws that series varying over more than 5% of an axis's span in at least one panel, is listed the same way with the panels and ranges named (a stored caption said "deterministic final-size values drawn as flat reference lines within each R0 panel" of a series that runs from 0.002 to 0.073 in the R0=0.9 panel), and the writer is told to say that it varies there or to describe only the panels where it is flat. A clause that hedges ("nearly flat", "approximately constant"), denies ("not flat"), confines the claim to part of the run ("starts flat") or names a panel where the series is flat is not flagged. Its limits: it reads exact labels only, so a caption that says "flat deterministic predictions" of a series labelled "Deterministic ODE" is missed, and it was measured on SIR figures only, where 15 of 166 recorded figures had a caption using one of those words (11 correct, 3 describing a sloping series as flat, 1 that could be read either way) and it flags 1 of the 3 and none of the other 12; how it behaves on other kinds of study is not measured. The record also says what the finished canvas draws over what, because only the drawn positions can: on each save the bootstrap draws the figure once more and measures whether a figure title covers at least a fifth of a panel title (a suptitle with no room made for it sat over the middle panel's "N = 1000"), and whether a data line or a scatter's points run under a legend's box, measured three pixels in from its frame and only where the axes do not clip the data (a legend sat on the very lines it named). A record with no `layout` was not measured; one with an empty list was measured and is clean. A run whose figures have such a finding is sent back to the execute-repair step **once per quest**, before any paper is written: the repair prompt names the figure and what overlaps, says what to change (the legend outside the axes or in a corner the data does not reach, room for the title) and forbids touching any computation, data, seed use, printed value or `RESULT_JSON`, and the redraw's result is measured again. It costs one model call and one more run of the experiment, replicate seeds included, and only for a run that has such a finding. It is asked for only when nothing else is wrong with the run (a crash, an all-zero result or a broken bound is repaired first, and regenerates the figures anyway), only while one more attempt would be left to repair the redraw if it breaks the script, and never for a figure the engine drew itself as the mean over the seeds. A redraw that is refused, is not Python, or whose call fails leaves the script and its figures as they were, and a figure that still overlaps afterwards is logged, not asked about again. Only a legend over data lines and scatter points is measured: one over error-bar stems, bars, shaded bands or a reference line drawn with `axhline` or `axvline` is not. Replayed over the stored experiment scripts of 40 quests, which drew 102 figures, it flagged 10, each a real overlap (three of them mild). A figure planned by the design and drawn by the run that the paper leaves out is must-flagged `figure_missing` by the engine itself, whatever the reviewer says: the write prompt already asks for every figure, yet 3 of 12 real papers left one out, and one kept 1 of its 3. A planned figure the run did not draw, or a drawn one nobody planned, is not counted. With `execution.sandbox: docker` the record's path is a host path the container cannot write, so no record is made. The implement prompts also steer the model toward figures that *read well* — units on axes, direct labels over boxed legends, small-multiples for per-stratum comparisons — and away from dumping raw arrays into `RESULT_JSON`. **Text size:** the house style's text is 1.5 times the size it was first set at (`core/plot_style.py`, `FONT_SCALE`): ticks 15 pt, axis labels and body 17.25 pt, titles 20.25 pt; the canvas and the dpi did not change. A figure is shown at a fraction of the width it was drawn at, and the experiments draw 8-13 in wide (the house canvas is 7 in), so on the slides of six stored quests, ticks first set at 10 pt came out at 2.9-6.9 pt (median 4.6). Re-drawn under the larger text, those quests' papers kept their page counts (4, 4, 5, 5, 5 and 4 pages) and the recorder's layout check found nothing to flag on any of their figures; clipping starts at about 1.8x (a y label). A font size a script sets itself (a legend's `fontsize=8`) is not scaled. The recorder also writes each figure's smallest tick label size (`tick_pt`, null when it draws none), which the slide check reads. The web-only `web_plots` step keeps its own, older style (its own preamble in `core/engine.py`), which is not enlarged. **Panels:** the design, outline and implement prompts cap a figure at 3 panels side by side in one row (`plt.subplots(1, n)`, n at most 3), and a comparison that needs more (a grid over two factors) becomes several figures. This is the prompt only: no repair round enforces it, and its effect on a model is not measured.
- **Length-aware page fitting** — outputs that pack content onto a fixed page are auto-fitted so an over-long LLM result can't overflow. A slide figure takes only the room left under its slide's text (at most about half the slide, aspect kept), and a caption written on the line under a figure is split into its own paragraph, so neither the figure nor its caption runs off the bottom of the slide. In `slides.pptx` a figure goes 0.2 in under its slide's text by the text's estimated height, and the text shrinks before the figure gets less than 2.2 in. The estimate counts each line at its line spacing times 1.2 times the type size, measured against LibreOffice and PowerPoint on seven slides (within 3.3 pt of LibreOffice, up to 6 pt over PowerPoint); the old 1.0 left a figure 0.1 pt under the last bullet. The **poster** plans its columns from estimated block heights, compiles, and measures the PDF (`generation/_pdf_measure.py`). Sections stay whole where they fit, and the text or list right after a figure stays with that figure; a column that still has to open inside a section repeats the section's heading as "Heading (continued)". A first plan made for the guessed room that came out over its own limit is planned again for the measured room even when the sheet measures clean, since it may have split a section to get close. Content that runs past the sheet or into the reference band first narrows figures, then trims lists and sentences, then drops blocks from the middle; uneven columns are re-split. It stops after at most six compiles and never shrinks the type. The **paper** breaks reference URLs at any character (`xurl` + pandoc's `autolink_bare_uris` + `\urlstyle{same}`) so a long wiki-style link wraps inside the text column instead of running into the right margin.
- **Page limit** — `output.page_limit` (unset by default; the interview asks it as the advanced, tier-3 answer "Page limit" on the CLI `--new` review screen and `--update`, on the web review screen's Advanced block and the `/update/<id>` form, and under "Edit an advanced field" in `@fi /new`; blank means no set limit, and a changed limit re-runs write and review), or a limit the topic states: `≤ 4 pages`, `<= 4 pages`, `at most four pages`, `no more than 4 pages`, `up to 4 pages`, `4 pages max`, `a 4-page paper`. The config value wins over the topic, a bound in words wins over the `N-page` form (which can name a part, as in "a 2-page appendix"), and a range such as `4–8 pages` is a length, not a limit. Without a limit the layout, the write prompt and the review are unchanged. With one:
  - **Layout:** the LaTeX templates switch on the `fi-tight` variable. The templates with 1 in margins (`generic`, `neurips`, `iclr`, `report`, `whitepaper`) use 2 cm; the others keep their own (`ieee_access`'s 0.75 in is already tighter). Figure height is not part of this switch: every paper caps a figure at 33% of the text height, limit or no limit. The References and Further reading lists are set in `\small`, by raw LaTeX added to `paper_pdf_source.md` only, so `paper.md` stays as written. The final `paper.pdf` and the visual check's recompile go through the same render, so they get the same layout. On three real 5- and 6-page papers from quests whose topic asked for at most 4 pages, the layout alone took one from 5 to 4 pages and one from 6 to 5; the third stayed at 5, its last page 91% empty.
  - **Word budget:** the write prompt tells the writer the limit, which overrides the `Study depth` length, and a budget of about limit × 450 words less a third of a page (0.37 × 450 words) for each figure the run drew (or the design planned), and that the source lists added after the last section take room on the pages too.
  - **Measured after each draft:** the review renders the draft with the same template and flags as the final `paper.pdf`, into `.fi/page_check/` with the quest's figures copied beside it, and counts its pages. A draft over the limit gets the forced, text-only must-flag `over_page_limit`, which gives the writer the page count, the limit and about how many words to cut (450 for each full page past the first one over, plus the filled share of the last page, at least 100), and asks it to keep every figure and number and shorten background and discussion first. Only the paper is written again (write → claim check → review). Only the measured count forces this hit: an `over_page_limit` the reviewer or a panelist writes itself is dropped, with a warning, since it could send the paper back without end.
  - **Further reading goes first, without a rewrite:** FI writes `## Further reading` itself and sets it after the body, so on a paper cut to the limit it is what spills onto one page more. When the measured draft is over the limit, the review first renders it with as many Further reading entries removed as may go (an entry the text cites, as `[W2]`, is never one of them, since the citation would name nothing). If that still is not within the limit, the body is what is too long and nothing changes. Otherwise it renders the draft with the last entry dropped, then the last two, and so on (one render per entry at most, about 3 seconds each on a 4-page paper), and the first draft that fits is written to `paper/paper.md`: the entries dropped are the last ones, `paper.md`, `paper.pdf` and `paper/further_reading.bib` then list the same pages, one log line says how many were dropped and which, and the review's `page_limit` record names them in `further_reading_dropped`. No model is called, the body is not rewritten, and `page_limit_rewrites` is not counted; a later whole-paper rewrite writes the full list again and the same trim runs on that draft. Only a list FI wrote is touched. Measured on a stored 5-page paper whose limit is 4 (page 5 held two of its three entries): entries 2 and 3 dropped, 4 pages, three extra renders, 8 seconds; on 4-page papers nothing changes. All three interfaces share the engine.
  - **A few sentences out, without a rewrite:** when the body is what is over the limit and about 400 words or fewer must go, the review asks the model which sentences to take out instead of sending the paper back. The model reads the draft with a marker before each sentence it may choose (`<<12: 23 words>>`: its number and its length) and answers `{"delete": [12, 7, 30]}`, the numbers of sentences that together are between the words to cut and 40 more (`agents/write_trim.md`; the call is logged as node `write.trim`, runs at temperature 0 and uses the model set for `write` unless `provider.node_models` names `write.trim`). What it may choose is decided in code, not by the model. Only sentences in a section called Introduction, Background, Related work, Discussion, Limitations, Conclusion (or prior work, literature, future work, implications, context, overview) are offered, and of those never: the sentence that opens a paragraph, a list item, a table row, a heading, a figure or a caption; a sentence that refers to a figure or a table; one that defines a term, a symbol or an abbreviation (`let`, `denote`, `defined as`, `where $x$`, `(SIR)`); one that says what the paper does or finds (`we`, `our`, `this study`, `here`); in an Introduction, the sentence that says why the work is needed (`However, …`, `While …, … fails to …`); a sentence the next one points back at (`However`, `This`, `It`, …); one that states a number the rest of the paper does not state; or one shorter than 6 words. The Abstract, the Methods and the Results are therefore as written whatever the model answers. The engine takes the listed sentences out in the model's order until the words are gone, skipping any that holds the last remaining citation of a source or the last remaining statement of a number (so no source becomes uncited, no citation number changes and no number is lost), renders the draft, and, when the list fell short or the draft is still over, asks again on the paper as it now stands: at most 3 calls. The draft is written to `paper/paper.md` only when it fits. The review's `page_limit` record then carries `trimmed: {words, sentences}`, `run.log` names the sentences, and the claims the check listed for a sentence taken out leave `paper/claims.json`, `paper/CLAIMS.md` and the review's claim list, unless another sentence of the paper still says them. No claim check or review is repeated for the trim. It is tried after the Further reading and before the shortening rewrite, also when the two rewrites are used up, and does not use `page_limit_rewrites`. A reply that is not a list of offered numbers, a failed call, too few sentences that may go, or a draft still over after 3 calls leaves the paper as it was, one warning says why, and the review forces `over_page_limit` as before. Measured: the stored run logs hold 77 forced shortenings, 39 that asked for 100 or 150 words and 57 for 350 or fewer (20 asked for 600 or more), and the small ones are the cases a trim is for. Under these rules the sections that may lose a sentence offer a median of 173 words on the 73 stored SIR papers, and the most that could be taken without breaking a rule is a median of 162 (for 33 of the 73 that is under 150 words, for 14 under 100), so a paper with few sentences that may go, such as a stored one whose background and discussion offer 106 words, is not trimmed and falls back to the rewrite. With the real model and the real render, on stored papers made one page too long by added background paragraphs, 2 of 2 came back to 4 pages: 114 words taken out in one call of 3,067 tokens, 224 words in three calls of 8,983 tokens, against about 43,000 tokens for a rewrite round (write, claim check, review); no number, citation, figure line, heading, Abstract, Method, Result or reference changed. A model asked to order the sentences returned the list in document order, and asked for the least valuable ones chose the statement of the paper's aim and the Introduction's first sentences, which is why the code, not the model, decides what may go. Not measured: whether the sentences chosen read better or worse than a rewrite's shortening, and how often a real first draft is within reach of a trim.
  - **Own counter:** these shortening rewrites are counted in `page_limit_rewrites`, at most 2, and do not use `engine.max_iterations`. When `over_page_limit` is the only must-flag, the paper is rewritten even with the iterations spent and the review does not bump the iteration. With other must-flags the usual route and budget apply, and the shortening still counts. A draft still over after two shortening rewrites is not forced again; the review records `page_limit: {pages, limit, rewrites, exceeded_after_rewrites: true}`. Every measured draft records its `pages` and `limit` there.
  - **Not measured:** a paper that renders through HTML (`paper_style: briefing` with a browser present, or no LaTeX engine), or a draft that does not render; the run logs one warning and forces nothing.
- **Visual check of every rendered PDF** — `output.visual_check` (default on) runs after the outputs render, on each PDF the pass produced (paper, slides, poster). A resume checks only the outputs it made. Each PDF is measured and screenshotted; the AI step, which sends the screenshots to the provider, runs only with `output.visual_check_ai: true` (default off, about 12,000 tokens a quest).
  - **slides.pptx:** with LibreOffice installed (`generation/_office_pdf.py`, found on PATH or in its default install folder), the pptx is exported to PDF with a fresh LibreOffice profile, so a LibreOffice window the user has open is never involved, and checked as `slides_pptx` with the slides' checklist and measurements. It is checked once, after any slides redo, since it comes from the same `slides.md`. Without LibreOffice the report says the pptx was not checked. `--doctor` lists LibreOffice.
  - **What it sends (with `output.visual_check_ai: true`):** screenshots at 90 dpi (longest edge at most 2000 px) and the `_pdf_measure` measurements go to the configured provider, with a fixed checklist of what only eyes can see: cut-off text, overlaps, unreadable figures, raw markup, broken math, garbled text and empty areas, plus a check or two per output. Sizes, overflow, a figure drawn over a slide's text, a figure whose tick labels come out under 8 pt on its slide (below), and a figure starting less than 6 pt under a line of text (`figure_gap`, low severity, never a redo), and a paper page before the last with 35% or more of its text area empty (`half_empty_page`, never a redo) come from the measurements, not the model.
  - **Tick labels on a slide (`figure_ticks_small`):** a figure's tick labels must be at least 8 pt on the slide (`SLIDE_FIGURE_TICK_MIN_PT` in `generation/_pdf_measure.py`, one constant). Each image on a slide is matched to a file in `figures/` by its pixel size (by its proportions when LibreOffice has resampled it, as in the pptx), and its tick size on the slide is the figure's tick size times the width it is placed at over the width it was drawn at (the file's pixels over its dpi). The tick size is the figure's record, `tick_pt` in `.fi/figure_records/<figure>.json`, which counts a script's own `tick_params(labelsize=...)`; a record from before the recorder wrote it takes the house style's tick size, since a figure of the house style is drawn at that size unless its script says otherwise (so a quest drawn before the house text was enlarged, and checked again on a resume, is read 1.5 times larger than it was drawn, and a figure whose ticks really come out between 5.3 and 8 pt on its slide passes). Only figures the recorder saw are measured: a fetched web figure or a `web_plots` figure has no record and its tick size is unknown, and under `execution.sandbox: docker` no figure has one, so the check is silent there. The finding names the slide, the figure, how wide it is drawn and the tick size it comes out at, and tells the slides model to give the figure a slide of its own, with no bullets, and put its discussion on the next slide. That finding is medium and is redone when the figure shares its slide with text; a figure that already has its slide alone and is still under 8 pt (a grid too tall for one slide) is low: it is reported and not redone, since no new deck changes it. The redo is the existing one (`output.visual_check_max_redos`, at most 2), and the version that checks best is kept, so a model that ignores the finding uses at most two redo rounds; the pptx is only reported. On the stored quest measured, its old deck was flagged on all three figure slides (4.1-4.3 pt), and a deck with each figure alone and at most three panels is silent (13.0-13.5 pt).
  - **Grounded findings:** every finding must quote text visible where the problem is. A quote that is not on that page (or the page before or after), a check not on the list, or a finding with no region is dropped, and the report keeps it with the reason.
  - **Redo:** the slides and poster are generated again with the findings a new version can fix, at most `output.visual_check_max_redos` times (0–2, default 2). The slides' model writes the whole deck, so its layout findings count. On the poster only text the model wrote counts, since the layout is the planner's. The version that checks best is kept and a worse one is put back file for file. The paper is never rewritten: when its last page holds only a line or two (measured as `last_page_nearly_empty`), it is recompiled once with a text area one line taller (its footer stays where it was), and the better version is kept.
  - **Providers without image input** check from the measurements alone, and the report says so. [docs/PROVIDERS.md](PROVIDERS.md) lists which providers can see images.
  - **Report:** `.fi/visual_check.json`, one entry per output with its attempts, plus the screenshots under `.fi/visual_check/<output>/`. The CLI and the VSCode chat print one line per output, the web quest page shows the same lines (read from the report, so a running quest shows them too), and `frontier_insight_summary.json` carries each output's result in brief. A check never stops the quest.
- **Citations in every output** — the sources a quest actually consulted (web pages carry their URL) are rendered as References across all three surfaces, not just the paper: the engine builds the paper's numbered References section from the papers its text cites, numbered in the order the text first cites them, rewrites the citations to those numbers and drops any citation of a number the prior-work block does not have (the literature is reordered to match, so the claim check, poster, slides, bib and the next write pass use the same numbers); the poster's reference band lists the sources its text cites (at most 8, built from the retrieved literature, so it survives even when the LLM only saw a truncated `paper.md`, and showing a web page's site name rather than its URL); the slide deck ends on one appended **References** slide, in both the HTML/PDF deck and the pptx: the sources the paper cites most (at most 6, as many as fit at 18 pt, in two columns: `_SOURCE_SLIDE_*` in `core/engine.py` are counted at that size, so change the theme's 0.96em and the budget together), in reference order, and a line saying how many more are in the paper. Web URLs and paper DOIs are both first-class; FI-internal cross-quest entries are filtered out of external-facing outputs.
- **Claim grounding** — `engine.claim_grounding` (default on) inserts a `claim_check` node between `write` and `review` that extracts the paper's substantive claims and grounds each as **experiment** (it restates a number/result this quest produced), **citation** (it rests on a specific cited `[N]` paper in References, or a `[W<k>]` web page in Further reading), or **unsupported**. For each source the paper cites, the check is shown the passages of its text most related to the citing sentences (up to 6,000 characters), and a citation must quote that text: FI looks the quote up in the source (ignoring case, quote marks and line-break hyphens, at least 25 characters), and a claim with no quote, or a quote the source does not contain, is unsupported. A quote that is not there as written is looked for once more with the mathematics folded, because a PDF and the paper quoting it render the same formula differently and neither is then a substring of the other: one source wrote its reproduction number `ℛ(0)` in its abstract and `R`, a line break, `0` in its full text, against a paper that wrote `R0`; the same exponent appears as `( i )`, as `^i`, and as a bare `i`; `$\mathcal{R}$` is `R`; and the spacing around an operator is typesetting. Only layout is folded — the numbers, the operators and the order of the tokens all still have to match, so a quotation that changes one of them is still rejected, and a quote found as written is accepted without folding anything. Without this the check called a formula quoted **verbatim** unsupported, and a run could spend its whole review loop rewriting a paper around a citation that was right. The same second chance allows for what a source's text extraction does to its layout, each only for a quote that is not there as written: a space the source has inside a word (`equati on`, `p robability`) or before the hyphen that broke a word at the end of a line (`inap -` line break `propriate`); a stacked fraction the source has as a numerator and a denominator on separate lines with no bar, against a quote that writes `1/R0`. The allowance is one-directional: the source may have a space the quote does not, but a quote may not add one (`the rapist` is not found in `therapist`), and a word changed, left out or added, two sentences that are not neighbours run together, and a quote of another source are all still rejected. A formula the source has lost altogether is not a layout difference and is not allowed for: a web page's text with its mathematics taken out reads `Given  and , the epidemic ends at time t, when .`, nothing in it says what the formulas were, and matching the words either side of the hole would accept any formula a quote put there, so a quote that spans one is not found and the writer has to quote words the source has whole. The quest's own evidence has a budget of its own (14,000 characters): every key finding and every claim the analysis says the run supports is shown whole — a finding is never cut off part-way, and none is dropped for being last — and the run's results fill what is left, all of them when they fit, otherwise the top-level branches most related to those findings, each one whole, with a long numeric array shown as its length and its range instead of printed. Ranking whole branches is what reaches a result a large sweep buries: the leading characters of a big result set are all sweep, so a validation the paper's claims rest on would never appear at any budget. A transparency ledger is written next to the paper — **`paper/claims.json`** (structured) + **`paper/CLAIMS.md`** (grounded-fraction + the unsupported list) — and any unsupported claims are surfaced to the reviewer with an instruction to must-flag them. The check and the review both read the whole paper; above 120,000 characters they read the start and are told the paper continues. When the check cannot run on a draft (its model call still fails after the provider's retries), the failure is recorded and the review forces `citations_unchecked`: nothing checked that draft's citations, so it is written and checked again, and it cannot be accepted until the check runs. When a reviewer does raise a must-flag, the revise pass is then **non-bypassable and deterministic** (forced even with `review_loop` off, capped by `max_iterations`) — but note the trigger runs *through* the reviewer reading the unsupported list, not a direct `claim_check → revise` edge, so enforcement is only as reliable as the panel (the methodologist persona owns it; a single-reviewer/empty panel weakens it). When the review's own must-fix prose — its blocking sentence, its weaknesses and its suggestions — names something this run computed (a key of `result_json`, a figure's underlying data, or `experiment.py`), no rewrite of the paper can fix it, so the experiment is written and run again instead (`review` → `implement` → `execute` → … → `write`), with what the review named and its must-fix prose added to the implement prompt — which otherwise carries only the design and would regenerate the same code. This replaces the text rewrite and nothing else: a must-flag that already sends the quest back to `design` (`circular_evaluation` and the rest) re-runs the experiment on its way through `implement` anyway, and a flawed design is not fixed by writing the same experiment again; a draft merely over the page limit keeps its own route and counter. A must-flag hit is a short identifier by the review's own schema, so what it is about can only be in that prose — and the hits themselves are deliberately not read, because the ones the engine forces quote the figure they checked (`figure_caption: the caption of figures/x.png names …`, `figure_missing: figures/x.png`), which would read as a problem with that figure's data when it is a problem with the paper's words. The prose is matched against names this quest actually produced rather than a list of words, and a results key must be a compound name (`deterministic_final_size`), so a leaf called `mean` cannot match prose by accident. The advisory numeric-oracle findings are not read here, so a flagged number still never forces a re-run. A re-run costs an iteration, so it happens at most once per quest and a flag that survives it takes the text route. Otherwise, when every must-flag is a problem with the text (`unsupported_claim`, `figure_caption`, `figure_missing`), the experiment stands and only the paper is written again (`review` → `write` → `claim_check` → `review`, with the review, the unsupported claims and the user's feedback in the write prompt; when each of those hits names a passage, the write node edits those passages instead, next bullet); any other must-flag sends the quest back to `design`. Set `engine.claim_grounding: false` to make the node a no-op passthrough (no LLM call, no ledger). The ledger records each citation's quote.
- **A revise edits the passages the review flagged** — a whole rewrite of a reviewed draft does more harm than the flags it answers: on the stored quests each one added background sentences whose citations their sources do not back (28 of 38 graded papers ended at the iteration cap still flagged `unsupported_claim`), one swapped two citation numbers in a paper whose first draft had them right, and one dropped all three figures. So when every must-fix hit names one passage of the paper — an `unsupported_claim` (the claims the check listed), a `figure_caption` (the figure its finding names), an `unsourced_number` or a `mislabelled_statistic` (the sentence it quotes) — and nothing the paper was written from has been run again since the draft (design, results, analysis, figures, cross-check and the user's feedback are fingerprinted in `paper_basis`), the write node does not write the paper again. It gives the writer the earlier draft and only those passages (`agents/write_patch.md`; the call is logged as node `write.patch` and uses the model set for `write` unless `provider.node_models` names `write.patch`) and asks for edits, `[{"find": "<text copied from the draft>", "replace": "<new text, or empty to take it out>"}]`. The engine applies an edit only where its `find` occurs exactly once in the draft's text before the source lists, applies all of them together, and leaves every other character as it was: the figures, the headings and the figure numbers included. The References and Further reading are then rebuilt from the citations in the edited text by the same step a whole paper goes through, so an edit that leaves a source uncited renumbers the sources after it, in the text and in the list together, and a citation of a number the prior-work block does not have is taken out. The checks paraphrase rather than quote, so the engine finds the passage a flag means: the flagged text as it stands, else the one sentence (or two adjacent ones) whose content words cover at least 80% of it, and never one of two that fit equally. That sentence is handed to the writer as the draft's own words; a flag the engine cannot place is handed over as text and the writer finds it. On the 314 unsupported claims in the final drafts of the stored quests, 13% were an exact substring of the paper and 81% could be matched to a sentence this way; a caption is found by the figure file its finding names. A round writes the whole paper instead when a hit is about the whole paper (`over_page_limit`, `figure_missing`, `citations_unchecked`), when a hit names no passage, when the study has been run again since the draft, or when the draft is over 120,000 characters, and the same fallback follows a reply that is not JSON, is a whole paper or holds no edit, an edit whose `find` is missing or occurs more than once, edits that overlap or replace more than 40% of the draft, and an edit that changes a figure link or a heading. Each of those is one line in `run.log`: `[write] writing the whole paper again: …` or `[write] the edits could not be used (…); writing the whole paper again`. A first draft, and a revise that runs the design or the experiment again, are written as before.
- **Evidence gate** — `engine.evidence_gate` (default on) inserts an `evidence_gate` node between `cross_check` and `write` that weighs the assembled evidence — source count, the cross-check supporting/conflicting balance, whether the run produced real measurements — against the research question **before** any paper is written, and returns a verdict: **sufficient** (write), **broaden** (re-enter the literature loop once more, bounded by `engine.evidence_gate_max_broaden`, default 1), or **insufficient** (write anyway, but the assessment is handed to the writer so the paper frames its thin evidence honestly rather than over-claiming). Two cases are decided from the counts without a model call, because across 68 recorded gate calls the model answered them the same way every time: a simulation quest with no source with text is **broaden**, and one with at least 15 sources and a finding a source supports is **sufficient**. Everything else — and every quest that is not a simulation, runs with `--analyze`, or has retrieval off (`knowledge.enabled: false`, where a broaden could not find a source) — is judged by the model, and the assessment records which decided (`decided_by`). It **fails open** — any parse error, or the flag off, routes straight to write — and is deliberately calibrated to pass most well-run quests; it exists to stop a confident-looking paper from being authored on evidence that doesn't support the question, not to refuse answerable topics. Set `engine.evidence_gate: false` for a no-op passthrough.
- **Research protocol** — a typed `core.protocol.ResearchProtocol` (research question, `topic_type`, `source_policy`, expected evidence, baseline, success metric, replication, stopping criteria, requires-user-input) consolidates the otherwise-scattered clarify slots into ONE validated contract, derived deterministically from the resolved clarify answers + engine config (no extra LLM call). It is handed to the `evidence_gate` so the sufficiency judgement is **contract-aware** — e.g. a topic whose `source_policy` is `web_current` (markets/current events) is judged insufficient if it has only academic sources, because that policy requires recent web sources; a `survey` (history/overview) topic's `mixed` policy accepts credible web / encyclopedic / museum sources so a humanities corpus isn't judged insufficient merely for lacking peer-reviewed papers. Recorded in `state['research_protocol']`. A declarative `core.protocol.ROUTE_MATRIX` is the single source of truth mapping each `topic_type` to the graph path it expects (`simulation` vs `no_simulation`) and the `source_policy` it implies; it is consulted at the design fork so `topic_type` is a first-class routing input. The resolved `no_simulation` flag stays authoritative (config/clarify wins the actual edge), but when the topic type's expected path disagrees with the resolved route the engine logs a `[route]` WARNING in run.log — bidirectional (it also catches a future build/engineering topic that resolved to no-simulation), complementing the earlier clarify-time `topic_shape`-vs-SIMULATE warning.
- **One entry per work** — retrieved sources are de-duplicated on every identity they carry, not just the strongest id: DOI / arXiv id / PMID / URL, and also a normalized title (case, dashes, punctuation, HTML entities and full-width forms folded). The same textbook appendix printed in three books under three DOIs, or an arXiv preprint returned once with its DOI and once without, is one source in the literature, the merged search results and the References. Titles shorter than three words or generic ones ("Introduction", "Preface", "Book review", …) never count as an identity, so different books' chapters stay apart.
- **Machine-readable citations** — the numbered References (scholarly sources) are also exported next to the paper as **`paper/references.bib`** (BibTeX) and **`paper/references.csl.json`** (CSL-JSON), and the Further reading web pages the paper lists as **`paper/further_reading.bib`** and **`paper/further_reading.csl.json`** (a page dropped to keep the paper within its page limit is not in them), so a finished quest drops straight into Zotero / Mendeley / a LaTeX or Pandoc workflow instead of leaving citations trapped in the markdown body. Entry types are chosen from the available fields (`@article` when it has a venue/journal, an `eprint`/`archivePrefix=arXiv` entry for a bare preprint, a `howpublished` web entry for a page), cite keys are stable + unique (`firstauthor+year+word`), and BibTeX special characters are escaped. Both files are listed in the quest's file tree in the Web GUI for direct download.
- **On-demand artifact generation** — produce ONE more output format (PDF / slides / poster / talk) for an **already-finished** quest **without re-running the research**. `Engine.emit_artifacts_only()` loads the quest's LangGraph checkpoint read-only and bundles its on-disk `paper.md` + figures (no node re-runs), then only the requested generator fires. Three surfaces: CLI `python launch.py --config <yaml> --resume <id> --emit paper_pdf`; the Web quest page's **Outputs** panel (a ✓/Generate row per format, showing which the quest is configured for and which exist); and VSCode `@fi /generate [<quest_id>] [<format>]`, which runs in an integrated terminal handed the address of the extension's session-long bridge, so the formats that call the model (slides / poster / talk) reach `vscode.lm.*` there too — which means the VSCode window has to stay open for those. So a markdown-only quest can get a PDF (or slides/poster/talk) later, on demand, for the cost of one render.
- **Source failure report** — every literature and full-text source (OpenAlex, Crossref, arXiv, PMC, Unpaywall, publisher pages, web pages, figure sources, …) records its failures against the quest that made the request: a rate limit, another 4xx/5xx answer, a timeout, a network error, an unparseable body, a headless browser render that crashed or failed, or full-text fetches abandoned at the time budget. A render whose browser driver dies is one failed source and nothing more — it is caught, reported and left behind, never allowed to end the quest. A 404 is an answer ("not in this index"), not a failure. Each failure is a `[source-failure]` line in `.fi/run.log` as it happens, with credentials redacted, and every run ends with one `[source-failures]` summary line (`none` when clean) plus `.fi/source_failures.json`, written on success, pause and failure alike. The CLI prints `[FI] source failures: …`, the web quest page shows a banner, and the VSCode chat shows the same line. Before this, a quest could lose every arXiv and OpenAlex result and its log said nothing.
- **Skip diagnostics** — every output kind that fails to produce its primary artifact drops a `<kind>_skipped.md` breadcrumb next to where the artifact would have landed (`paper_pdf_skipped.md`, `poster_pdf_skipped.md`, `slides_skipped.md`, `speech_skipped.md`), explaining what was requested, why it couldn't be produced (missing CLI, refused LLM response, render-tool error, …), and how to fix it. The user discovers the failure by opening the quest folder instead of grepping `run.log`. Diagnostics are idempotent: a subsequent successful run of the same kind removes the stale breadcrumb.
- **Quest failure diagnostic** — when a `_node_*` method raises or a pre-graph stage (preflight, endpoint resolution, executor setup) fails, the engine writes `<quest_root>/quest_failed.md` with the exception text, failing-node name (from the LangGraph snapshot when available), provider context, log tail, and a `--resume` command. Any re-run clears the stale file **as soon as it starts** — not only at terminal state — so an in-flight resume that's already running past the node that broke isn't shown as "failed"; if the re-run also fails, the exception handler writes a fresh diagnostic in its place. Same discoverability contract as the skip diagnostics: the failure is visible from the quest directory itself, not just `<quest_root>/.fi/launch.log`. A failure that does not arrive as an ordinary Python error gets the same breadcrumb. Not every failure comes back as one: a driver process dying under a tool the quest is driving can surface outside Python's usual error hierarchy, and a failure of that shape used to skip the diagnostic entirely and leave an empty quest folder whose only trace was a buried traceback. The literature fetch already contains that shape for the sources it wraps (above); this covers the same shape reaching the engine from anywhere else. Stopping a quest yourself is not a failure and writes no diagnostic: Ctrl-C, a shutdown signal and a cancelled run stop it immediately and silently.
- **Cite-by-content references** — prior-work block carries author / year / title / venue / DOI, and the engine's References entries carry the same fields. The writer cites only the prior-work block's labels and writes no source list; the prompt forbids fabricating a source or embedding fenced code in the body.

### Cost + observability

- **Engine cost instrumentation** — `core/provider.py:MODEL_PRICING` + `estimate_cost_usd(...)`. Every model call appends `{ts, node, model, usage, cost_usd}` to `<quest_root>/.fi/cost.jsonl` through `core/provider.py:append_cost_row`: the engine's nodes and the output generators (`slides`, `poster`, `speech`, `visual_check`). `cost_usd` is an estimate from the table's rates, and it is `null` for a model the table does not list: a newer model that merely contains a listed name (`gpt-5.6-luna` contains `gpt-5`) is a different model with its own price, so it does not borrow that row, and its token counts are still logged. Char-based token estimate (~4 chars/token) when the transport returns no `usage`; row carries `usage.estimated: true`. Quest finalization writes `<quest_root>/.fi/cost.summary.json` with totals + per-node + per-model breakdowns, and the output pass writes it again so the generators' calls are in it. `total_cost_usd` (and each bucket's `cost_usd`) adds up the calls that carry a price and is `null` only when none do, so a quest that mixes priced and unpriced models has a total that is a lower bound: the summary then carries `total_cost_usd_partial: true`, and `unpriced_requests` (in the totals and in every `by_node` / `by_model` bucket) counts the calls whose `cost_usd` is `null`; the token counts are always complete. The web quest page and compare page read the same roll-up from `/api/quests/<id>/cost` and append "(partial: N calls unpriced)" to the dollar figure when the total is partial; a total that is `null` shows as before. The CLI and the VS Code extension print no cost figure, so nothing there changes.

### Interviews + frontends

- **Unified interactive interview** — CLI `--new`, VSCode `@fi /new`, web `/interview` all drive `core/interview.py` (snapshot in `core/interview_schema.json`). Tier 1 asks topic, paper format, outputs, study depth, ensemble profile and — when one is picked — the models to fan out over, provider + model (CLI and web only; VSCode uses its chat model) and the optional author line (author, affiliation, contact email, project link); tier 2 is auto-derived and shown for review, and holds the mid-quest pause for your own papers / datasets; tier 3 holds the advanced slots, including paper style, poster size, the design-revise iteration budget and reasoning effort (`provider.reasoning_effort`). Pinned values land in `engine.clarify_overrides`. Every question declares which surfaces ask it, and the schema-parity test derives its expectations from that declaration, so a question cannot ship unasked on one interface while CI stays green.
- **Mid-quest interview re-entry** — `--update <id>` / `@fi /update <id>` / `POST /api/interview/update/{id}` re-open the interview with editable fields. The form pre-fills from the quest's existing YAML (not interview defaults), so unchanged fields round-trip cleanly; `STAGE_INVALIDATION` decides which downstream nodes re-run when an editable field changes. Hand-crafted `provider.node_ensemble` blocks the interview can't classify back to a preset are preserved across update saves. `no_simulation` is hard-locked mid-quest. In VSCode the update runs in an integrated terminal that is handed the address of the extension's session-long bridge, so the resumed quest's model calls still route through `vscode.lm.*`, together with the quest output root the picker listed from — so a non-default output directory resolves to the quest that was actually offered instead of reporting it missing.
- **Status GUI** — FastAPI server at `web/static/index.html`: fleet list, SSE log stream, clarify panel, paper preview, panel-review cards. Tools dropdown with ARIA semantics (`aria-haspopup` / `aria-expanded`) + Escape-to-close + first-menuitem auto-focus on open.
- **Web UI quest launching** — `--serve` spawns `python launch.py --config <yaml>` via `web/quest_launcher.py` (capped at `--max-concurrent`). Detail page auto-refreshes every 3 s. Non-loopback bind logs a WARNING.
- **In-process quests over the API** — `POST /api/quests/start` with `{"yaml": "<config>"}` runs the quest inside the server process instead of a subprocess, answering its clarify and human-review pauses through `/api/quests/{id}/clarify` and `/api/quests/{id}/human-review`. When the engine finishes, the server runs the same output pass as the CLI: `paper.pdf`, slides, poster and talk per `output.kinds`, the visual check, and `frontier_insight_summary.json`, so the same config produces the same files either way. The paper's pandoc and LaTeX compile runs in a worker thread, so the server keeps answering other requests meanwhile. A generator that raises is written to the quest's `.fi/run.log` and listed under `errors` in `GET /api/quests/{id}` (`stage` is `paper`, `slides`, `poster` or `speech`, `outputs` when the pass stopped, as it does under `output.require_pdf`, or `quest` when the engine run itself failed); the server keeps running.
- **Web UI "everything" pass** — `/tools/{proposal,critique,digest,portfolio,summarize,analyze,fleet,ingest}`, file browser, zip download, resume button, clarify-resume panel, labels, cost chart, paper iterations, exec edit (gated by `FI_WEB_ALLOW_EXEC_EDIT=1`), trash bin at `/trash`, `/compare?a=&b=`, `/settings`, `/about`. Self-hosted Markdown renderer (`md_lite.js`).
- **Bridge-aware vscode_extension across all serve forms** — `/interview`, `/update/<id>`, and every `/tools/*` form surface `vscode_extension` at the top of the provider picker when a VSCode bridge is reachable. The model dropdown lists **every** chat model VSCode exposes to the extension, tagged with the vendor it came from — Copilot's catalogue, and anything registered by another extension's language-model provider (an Ollama server, a BYOK OpenAI-compatible endpoint). Picking one routes the quest through it. The schema endpoints **TCP-probe the bridge port and IPC-probe the bridge socket** before reporting availability, so a stale or wrong configuration can't lie to the UI. Without a reachable bridge the entry stays hidden — same source of truth as the submit-time 400 guard. Model dropdowns offer "Other (type your own)" with a text-input fallback on every page. The picker's selection is threaded through to the spawned subprocess via a `--<tool>-model` flag for every LLM tool (proposal / critique / digest / portfolio / summarize / analyze), so the picked id reaches `ProviderConfig.model` and the bridge actually routes to the chosen model instead of falling through to the Copilot Chat-picker default.
- **id-first model selection on the VSCode bridge** — `selectChatModels` is queried with `{id: hint}` first, then `{family: hint}`, in both `PersistentBridge` (`--serve` / tools path) and the per-chat-command `Bridge` (`@fi /start` path). The picker stores model **ids** (e.g. `gemini-3-flash-preview`), and Copilot's family is sometimes coarser (`gemini-3-flash`), so filtering by family alone misses every versioned/preview model. Family fallback keeps the legacy `gpt-5` / `claude-opus-4-7` style hints working. When nothing matches, the error dumps the full `id|family` catalog so the next mismatch is self-diagnosing.
- **Per-user IPC PersistentBridge for --serve / --tools** — the FI VSCode extension starts a session-long bridge at activation, listening on a per-user OS-managed address (`$XDG_RUNTIME_DIR/fi-bridge.sock` on POSIX with `/tmp/fi-bridge-{uid}.sock` fallback, `\\.\pipe\fi-bridge-{USERNAME}` on Windows). `--serve` auto-resolves the same path via `core.bridge_path.persistent_bridge_path()` and routes LLM calls through `vscode.lm.*` with no port to wire and no env var to set. Shared-Linux hosts isolate cleanly (each UID gets its own socket); per-chat-command bridges (`@fi /start`, `@fi /digest`, etc.) keep using their existing per-spawn TCP transport. Opt-out via `--no-vscode-bridge`.
- **Bridge stall-timeout recovery** — when Copilot's HTTP/2 stream stalls mid-response, both the TS-side bridge (per-chunk inactivity timer) AND the Python-side `VSCodeBridgeClient.chat` (outer `asyncio.wait_for` against `provider.cli_timeout_s`, default 300 s) surface a `bridge stalled` error. The phrasing is load-bearing: `_TRANSIENT_BRIDGE_MARKERS` in `core/provider.py` matches it so tenacity retries the call. Older `.vsix` builds (no TS-side timer) or a TCP/IPC blip that drops the `lm_error` itself can no longer wedge the engine.
- **CLI streaming + inactivity watchdog** — `claude_cli` is invoked with `--output-format stream-json --include-partial-messages` so Sonnet 4.6's `thinking_delta` events arrive as a steady pulse during extended-thinking spans that otherwise look identical to a hung process (the old `--output-format text` mode buffered the entire response, including 9+ minutes of pre-answer thinking on complex prompts, into one silent stdout flush). The reader resets a soft `cli_inactivity_timeout_s` watchdog (default 180 s) on every stream event, while the hard `cli_timeout_s` ceiling still applies as a last-resort kill; per-node overrides in `provider.node_cli_timeout_s` raise that ceiling for reasoning-heavy nodes (`implement` → 1800 s, `execute_reflect` → 900 s) without bumping the cheap nodes. Setting `provider.cli_timeout_s` yourself makes it a floor rather than a fallback: the built-in per-node defaults are raised to it and the change is logged, so a config asking for 900 s no longer silently gets 600 s on the outline node — while a `node_cli_timeout_s` map you write yourself is honoured exactly as written, including a deliberately tighter budget that catches a hang on one node faster. `Engine._chat` wires a heartbeat callback that logs progress every ~30 s: `[implement] still waiting on LLM — thinking (2400 thinking-token events), elapsed=4m22s, idle=0s`. The **non-streaming CLIs also heartbeat** — `codex_cli` (`last_message_file`, stdout DEVNULL'd) and `copilot_cli` / `gemini_cli` (plain stdout) have no token-level signal, so the `communicate()` path fires the same callback on a ~10 s timer; the line reads `still waiting on LLM — no events yet, elapsed=Ns`, so a long silent codex/copilot call no longer reads as "pending" on the dashboard.
- **CLI output gate registry** — vendors sometimes deliver upstream-state text (rate-limit messages, give-up placeholders, policy refusals) as plain `text_delta` events instead of structured error envelopes. Without protection, the engine aggregates that text and writes it to disk *as* the artifact — observed in production where `paper.md` became literally `"You've hit your session limit · resets 2:30am (Europe/Brussels)"`. `_collect_via_streaming` and `_run_cli` both run the assembled response through `_check_output_gates`, a registry of named gates: `rate_limit_message`, `placeholder_response`, and `refusal`. Each gate has its own marker list and a 500-char length cap so a real paper-length output that mentions any marker in body text doesn't false-positive. The first gate that fires names itself in the raised `_CliTransientError` so retry logs say *which* gate triggered. Tenacity retries (and may escalate the model via the per-node fallback table — see model-escalation bullet).
- **Jittered retry backoff** — every tenacity retry policy in `core/provider.py` (HTTP direct, VSCode bridge, CLI exec) uses `wait_random_exponential` instead of a deterministic `wait_exponential`. A deterministic schedule synchronises N concurrent fleet quests on a shared upstream blip — they all retry at the same wall-clock instant and re-clog the upstream. Random-exponential picks uniformly from `[0, multiplier · 2^attempt]` capped at `max`, spreading retries over a window so the upstream sees a gentler ramp. Eliminates a thundering-herd failure mode that's invisible until you run a busy fleet.
- **Tenacity model escalation on retry (opt-in)** — `provider.node_model_fallbacks` maps node name → fallback model and is **empty by default**: FI never picks a model on your behalf. When you set it, on retry attempt 2+ `_chat_cli` switches that node's CLI invocation to the fallback model (attempt 1 always uses your primary model). Empirical motivation: Sonnet 4.6 + extended-thinking on long code-gen prompts (implement-body, write) reproducibly paralysis-thinks (verified 3× across prompt size and output shape variants, all hit 15-min wall with zero text); in that test, a retry on Opus 4.7 landed the same prompt in ~5 min. To opt in, name a stronger model for the nodes you want, e.g. `implement: <your stronger model>` and `write: <your stronger model>`; the string is passed straight to whichever CLI is active, so it has to be a model that provider accepts (see `docs/PROVIDERS.md`). Standalone CLI matrix (verified on this very prompt): `claude_cli`+`claude-opus-4-7` works, `codex_cli` works, `copilot_cli`+`gpt-5-mini` works, `gemini_cli` aborts via its own loop-detector, `copilot_cli` default model times out.
- **Wedge fail-fast** — an extended-thinking CLI hang (the model streams thinking for minutes, then closes stdout with **no answer** and won't exit even to SIGKILL) is raised as a distinct `_CliWedgeError` and **bailed after the 2nd occurrence** instead of burning the full 4-attempt budget on the same dead end (~2 wasted multi-minute calls). Observed 4-for-4 on a heavy `claude_cli` code-gen prompt. The reraised error carries actionable guidance — *"the fix is a different provider for this node (e.g. resume with `--config <codex_or_openai>.yaml`)"* — so the `quest_failed.md` tells the user how to recover instead of showing a cryptic "stdout closed" line. (Model escalation happens on retry 2, so the wedge still gets one shot at the fallback model before bailing.)
- **Tenacity retry visibility** — the `_chat_cli` retry loop wires a `before_sleep` callback that logs the caught `_CliTransientError` text + the next attempt's model to `run.log` as a WARNING. Without this, transient retries were silent (caught exception text dropped) and write-attempt-1 deaths showed up only as a sudden `elapsed=1s` heartbeat with no diagnostic.
- **CLI input-cap guard** — a CLI provider with a hard per-turn input limit (`codex_cli` rejects turns over 1,048,576 chars with `input_too_large`) carries a `max_input_chars` on its `_CliSpec` (codex_cli: 900K, sitting under the limit to leave room for codex's own system prompt + tools schema). When a node's prompt exceeds it — e.g. `analyze`/`write` after an evidence-gate **broaden** pulled in many literature sources — `_run_cli` trims the **middle** of the prompt (keeping the task head + the output-format tail, where FI always puts the load-bearing instructions) and logs a WARNING, so the call goes through instead of hard-failing the quest. Trimming is lossy (some literature/result detail is dropped); the warning points at the leaner-footprint knobs (`knowledge.top_k`, `knowledge.literature_excerpt_chars`, `engine.evidence_gate_max_broaden: 0`). **`copilot_cli` carries the same cap for a different reason** — it passes the prompt as a command-line **arg**, so on Windows the whole command line hits the `cmd.exe` ~8191-char limit (`copilot.BAT` fails a long design/write prompt with `rc=1: The command line is too long`); its `max_input_chars` is 7000, well under that. 7 KB is small for a rich node prompt, so copilot trims heavily on long-context nodes — the real fix is a stdin/temp-file transport, so prefer `codex_cli` / `openai` for long prompts on Windows. The stdin-based CLIs (`claude_cli` / `gemini_cli`) have no arg-length limit.
- **Provider fallback chain + circuit breaker** — `provider.fallback: [codex_cli, gemini_cli]` (default empty) lists providers to try, in order, when the primary terminally fails a chat call (after its own retries). Each provider carries a circuit breaker: after repeated failures — or one auth/quota/credit error — its circuit opens and it's skipped, so subsequent calls jump straight to a live provider instead of re-burning the dead one's retry budget every call. The breaker is **half-open**: after a cooldown (`breaker_cooldown_s`, default 90 s, above the retry budget) one probe is let through, and a provider that has recovered rejoins the chain — so a transient blip doesn't permanently drop it for the rest of a multi-hour quest. Fallbacks are built lazily (nothing is resolved and no proxy is spawned until the primary actually fails); `last_model`/`last_usage` track the serving provider so cost accounting stays correct; a `CancelledError` never triggers a fallback. A single provider outage (rate limit, auth failure, proxy crash) no longer forfeits the whole quest.
- **Global LLM-call backpressure** — `FI_MAX_CONCURRENT_LLM_CALLS` (default `0` = unlimited) caps the number of in-flight provider calls across every quest in one process. A `--fleet` of N quests each fanning out a review panel / ensemble can otherwise burst into dozens of simultaneous requests and trip provider rate limits; set e.g. `8` for a large fleet. The slot wraps only one dispatch, so retries/fallbacks re-queue rather than deadlock; single quests see no change at the default. **Scope caveat:** the cap is per-OS-process. `--fleet` runs its quests in one process, so the value is a true aggregate ceiling. `--serve` launches each quest as a separate subprocess, so each gets its own cap and the effective ceiling is `FI_MAX_CONCURRENT_LLM_CALLS × --max-concurrent` — size the value with that multiplication in mind under `--serve`.
- **Retry classification** — the provider retry loops distinguish *transient* failures (5xx / 429 / network blips, and CLI `OSError` / transient markers) from *deterministic* ones. A 4xx (bad key, content policy, oversized body) and an hours-long CLI session/usage/credit-limit or auth failure abort immediately with the original message instead of burning the 4-attempt jittered-backoff budget on an error that can't clear in the retry window. A CLI reporting that its model's server has no capacity (HTTP 503, `UNAVAILABLE`, `RESOURCE_EXHAUSTED`: the server's state, not the account's quota) is transient, and waits 30–90 seconds between attempts instead of at most 20, since capacity takes longer than a dropped connection to come back. A call **killed for running out of wall-clock** is retried with a *longer* budget (1.5× per attempt, capped at 2.25×), because retrying the same work under the same ceiling reproduces the timeout — one node burned three attempts and about 40 minutes that way. Capacity errors and wedges keep the configured budget: neither is a "needed more time" failure.
- **Gates fail open, panels degrade** — a provider blip in the `review` / evidence-gate path can't forfeit a finished paper: a single-reviewer failure degrades to a neutral accept, one panelist raising doesn't abort the panel (the rest still vote, and an all-panelists-fail case falls back to a neutral verdict). `CancelledError` still propagates cleanly so a real cancel isn't swallowed.
- **Deterministic gate routing** — judgment nodes (`evidence_gate`, `review`, `review_panel.*`, `claim_check`, `cross_check`, `relevance_guard`) run at temperature 0 so their routing decision (sufficient vs broaden, accept vs revise, supported vs not) is reproducible run-to-run instead of flipping and triggering wasted broaden loops or spurious revise cycles. Applies wherever the transport honours temperature (HTTP + vscode_bridge); generative nodes keep the 0.2 default. CLI transports that don't expose temperature are unaffected.
- **Per-node HTTP timeout + prompt-size guard** — the OpenAI-compatible transport takes a per-node read-timeout (`provider.node_http_timeout_s`, base `provider.http_timeout_s` = 120 s), mirroring the CLI's `node_cli_timeout_s`: reasoning-heavy nodes (`implement` → 900 s, `write` → 600 s, …) get headroom while cheap nodes keep the tight base that catches a hung server fast. A transport-agnostic `provider.max_prompt_chars` (default `0` = off) generalizes the CLI middle-trim to every transport — when set, a prompt over the cap is trimmed in the middle of its largest message (head + tail kept) with a loud warning, so a runaway prompt can't blow the context window into a hard 400 / stall.
- **Bridge reconnect-on-drop** — a mid-quest VSCode-bridge socket drop nulls the stale transport so the next chat reconnects, instead of leaving a dead writer that wedges the rest of a long `--serve` / `--tools` session. In-flight calls fail with a transient `BridgeError` (retried), and pending awaiters are unblocked rather than hanging.
- **Fleet isolation + memory-cap safety** — in `--fleet`, a quest whose Engine construction fails is isolated (siblings still complete; the runner exits non-zero) instead of aborting the whole batch, and a `--memory-cap-mb` set below the baseline RSS — which would deadlock the fleet (nothing can run to free memory) — is disabled with a warning rather than hung on. `--profile` is rejected with `--fleet` (viztracer can't meaningfully trace N concurrent quests in one process).
- **Resume completes missing outputs** — a `--resume` regenerates only the outputs actually missing on disk: a kind whose final deliverable already exists (`paper.pdf` / `slides.pdf` / `poster.pdf` / `talk.md`) is carried through untouched, so resume no longer re-invokes the LLM for slides/poster/speech that already rendered or clobbers good decks. **Existence isn't trusted blindly** — a PDF must be non-empty *and* start with the `%PDF` magic, and a text deliverable must be non-empty, so a truncated file left by a kill mid-compile is regenerated rather than shipped. Any configured output still missing after the pass is reported. `--emit` stays an explicit force-regenerate path.
- **Resume self-heals a half-built venv** — `VenvExecutor.setup()` reuses a per-quest `.venv/` only when the interpreter actually exists *and* a cheap `import pip` probe passes (CPython writes `pyvenv.cfg` before copying the interpreter and running ensurepip, so a run killed mid-build leaves a `pyvenv.cfg` with no interpreter). A broken venv is rebuilt from clean on the next `--resume` instead of spawning a missing-python `FileNotFoundError` on every retry.
- **Unknown config keys fail fast** — `Config.from_yaml` audits the top level and the six known sub-sections against their real fields and **raises** on an unrecognized key, listing the offending dotted paths. Pydantic's default is to silently drop unknown keys, so a typo like `provider.node_http_timeoutt_s` would otherwise validate cleanly and quietly revert a reliability knob to its default. Legacy pause flags and free-form dict fields (`node_models`, `node_*_timeout_s`, `clarify_overrides`, …) are still accepted.
- **Windows MAX_PATH venv diagnostics** — a deep `output_dir` on Windows can push the per-quest venv's native-extension paths (PIL/matplotlib `.pyd`) past the 260-char limit, silently killing figure generation. `setup()` warns when the venv path already exceeds ~200 chars, and `execute()` sniffs a DLL-load failure in stderr and logs one actionable hint (enable `LongPathsEnabled` or shorten `output.output_dir`) — so even the otherwise-silent web-figures path surfaces the cause.
- **Stuck-quest dashboard surfaces** — `/api/quests/{id}` returns `node_started_at`, `node_elapsed_s`, `node_idle_s`, and `quest_failed: {present, failing_node, what_broke}` derived from `run.log` timestamps and `<quest_root>/quest_failed.md`. The detail page (`web/static/quest.html`) renders a colored chip next to the current-node label (green = active, yellow = idle ≥5 min, red = idle ≥10 min) and an error banner with the failing-node + one-line exception when a `quest_failed.md` is present. The banner clears the moment a resume **starts** — the engine deletes the stale file at the start of every run (not only at terminal state), so an actively-running resume isn't mislabeled "failed"; a re-run that fails again writes a fresh diagnostic. Because that idle chip is driven by `run.log` recency, the **execute node emits a heartbeat** (`[execute] running experiment.py — still running, Ns elapsed`, every 30 s) while the experiment subprocess runs — otherwise a multi-minute parameter sweep, which the executor just blocks on silently, would show as idle/red the whole time even though it's hard at work.
- **"Needs you" is distinct from "complete"** — a paused quest still writes `frontier_insight_summary.json` on its clean rc=0 pause-exit, so a single `_quest_pending()` helper (shared by the dashboard scan and `/api/quests/{id}`) decides whether the quest is actually *waiting on the user* — via the unified `NEXT_STEP.md` / `.fi/pause.json` markers, or a human-review / clarify snapshot with no answer yet. The dashboard shows a **"Needs you"** badge (filterable) instead of "complete", the quest page keeps **Resume** and the right input control live (for older quests too, from the on-disk snapshots), and the engine clears those snapshots **both at the start of every run and on true completion** — so neither a finished quest *nor an actively-running resume* shows a stale pending state. (A refine/resume that continues past a pause used to leave the old `NEXT_STEP.md` / `pause.json` / human-review / clarify snapshot on disk for its whole run, mislabeling a busy quest as "Needs you"; the run-start clear drops those display markers while deliberately keeping the `*_answer.json` files, which are the input that resume is consuming.) **Add papers / data to any quest from the quest page** — a persistent upload writes into `inputs/papers` + `inputs/data` (the generalised `/api/quests/{id}/upload`), picked up on the next resume / refine — so you can feed a quest files from the frontend whenever, not only when a supply-pause fired. Quests with no `config.yaml` (CLI-started before configs were saved) disable Update/Resume with a clear note, since both need the original YAML.
- **Ensemble profile is a tier-1 quest decision** — `Multi-model ensemble` (`off` / `cross_check_only` / `ideate_and_check` / `full`) sits next to provider/model on `/interview` and the CLI's `--new` flow rather than under "Show advanced". The models are the user's to name: `Models for the ensemble` takes at least two ids (comma, semicolon or newline separated, duplicates dropped, order kept; the first is the moderator), and a profile with fewer than two named models configures no ensemble and says so in the YAML — the web form and `/api/interview/submit` refuse it with a 400 instead. VSCode offers the models `vscode.lm` reports as a multi-select. Every LLM `/tools/*` form (proposal / critique / digest / portfolio / summarize / analyze) carries the same picker and model field; the form passes the named models as a CSV via each tool's `--<tool>-ensemble` CLI flag. Default merge differs per tool: `tournament` for the canonical-synthesis tools (proposal / portfolio / summarize / analyze) and `synthesize` for the disagreement-preserving ones (critique / digest). Single-shot tools (digest / portfolio / summarize / critique / proposal) wrap one LLM call via `core.ensemble.run_singleshot_with_ensemble()`; `--analyze` runs a full engine quest and the ensemble lands on `cfg.provider.node_ensemble` for the `analyze` and `cross_check` nodes.
- **VSCode extension** — sanctioned `vscode.lm.*` integration with `@fi /new`, `/start`, `/fleet`, `/resume`, `/summarize`, `/proposal`, `/critique`, `/digest`, `/portfolio`, `/analyze`, `/update`, and `/probe [all]`, which asks the model selected in the Chat picker (or every model VS Code lists, after a confirmation that states the request count) whether text FI did not send appears to be in its context. It is behavioural evidence only: `vscode.lm` reports no usage figures, so the overhead itself is not measured, and the token counts it prints cover only what FI sent.
- **Accessibility** — `prefers-reduced-motion` honoured on `marketing/index.html` (terminal fade-in + pulse-dot disabled when the OS preference is set).

### CLI tools

- **`--serve`** — local web UI; honours `FI_VSCODE_BRIDGE_PORT` env var for routing LLM calls through Copilot when launched from a VSCode terminal. Refuses `provider=vscode_extension` quests when no bridge is wired (400 at submit).
- **`--resume <quest_id>`** — re-enter the LangGraph from the last checkpointed node when a prior run died mid-pipeline.
- **`--fleet <yaml> ...`** — bounded concurrency, ref-counted proxies (per-provider locks so one provider's proxy warmup doesn't block others), `--memory-cap-mb` (a below-baseline cap is disabled with a warning, never deadlocked on), per-quest construction-failure isolation, and an optional process-wide LLM-call cap via `FI_MAX_CONCURRENT_LLM_CALLS`. `viztracer --profile` is single-quest only (rejected with `--fleet`).
- **`--summarize <folder>`** — walks mixed content, classifies each file, calls LLM once, writes `outputs/<summary_id>/summary.md`. Ingested into Axon.
- **`--digest --days N`** — weekly PM digest with WeekDiff (✅ promoted / 🆕 new / ⚠️ still-in-progress / 🛑 stalled / ❓ dropped) vs prior digest. Ingests as `fi_digest`.
- **`--portfolio`** — all-time cross-quest synthesis: topic clusters, near-duplicate detection, meta-paper candidates, coverage gaps. Ingests as `fi_portfolio`.
- **`--critique <id>`** — adversarial second-pass review (`--critique-provider <name>` to use a different model family). Writes `outputs/<id>/critique.md`. Ingests as `fi_critique`.
- **`--proposal "<topic>"`** — pre-quest planning doc + companion YAML under `outputs/_drafts/`. Companion YAML auto-pins the proposal into `knowledge.local_papers`. Ingests as `fi_proposal`.
- **`--analyze <data-path> --analyze-topic "..."`** — no-simulation quest on pre-staged data. Routes through `auto_collect_data → wait_for_data → data_load → analyze → write → review`. ~6 premium requests.
- **`--ingest <paths>`** — one-shot Axon ingest, no quest. Zero LLM calls.
- **`--install-tectonic`** — drops a self-bootstrapping LaTeX binary (~70 MB) into `tools/`. SHA-256 verified.
- **`--install-tectonic-from <path>`** — airgapped variant: install from a locally-staged archive or extracted binary. No network call. ELF / Mach-O / PE header sanity check.
- **Resumable quests** — SQLite-checkpointed state at `<quest_root>/.fi/state.sqlite`.

at engine init. Set `FI_SUPPRESS_PROXY_WARN=1` to silence (use at your
own risk).

**CLI calls are answer-only.** `codex_cli` and `claude_cli` run with web search, shell and code execution, MCP servers, skills, plugins, subagents and memory turned off, and do not save a session. Every CLI call, for every CLI provider, starts in a new, empty temporary directory that is removed when the call ends (also after an error or timeout), so a CLI never sees FI's working directory. `codex_cli` does not read `~/.codex/config.toml`: custom model providers, profiles and MCP servers defined there are not used, the model comes from `provider.model` (blank = codex's own default, not config.toml's) and the effort from `provider.reasoning_effort`. Not restricted yet: `antigravity_cli` (no option turns its tools off, and it works in its own fixed workspace), `copilot_cli` (keeps `--allow-all-tools`; not checkable while the Copilot quota was used up) and `gemini_cli` (keeps `--yolo`; the Gemini CLI no longer signs in individual Google accounts). Flags and measurements: [PROVIDERS.md](PROVIDERS.md#answer-only-cli-calls).

## Knowledge layer — three-layer retrieval

```
asearch(query)
  ├─ 1. Pinned local_papers (always first)
  ├─ 2. Axon (your long-term store; falls through on empty)
  └─ 3. External router: agent picks 1–5 sources from the catalog
        ├─ openalex / arxiv / crossref / semantic_scholar / pubmed / core / google_scholar
        └─ (optional) full-text fetch via host network
```

After an **accepted** quest, the write-back lays down a structured
bundle so Axon stays title-searchable and topic-linkable:

| kind | Purpose |
|---|---|
| `fi_paper_spine` | One tight chunk per paper — title / authors / DOI / keywords / abstract / key claims. Title queries hit this directly, and the keywords the writer picked (shown under a scientific paper's abstract, kept out of sight in a report, brief, essay or whitepaper) give later searches the paper's subject terms. |
| `fi_quest_paper` | Full paper body with a 1-line `[Title · Year · Venue · DOI]` citation header on every chunk. |
| `fi_quest_summary` | Structured-findings JSON (hypothesis, key_findings, result_json, verdict, score, model). |
| `fi_topic_event` | One pointer per accepted quest keyed by topic slug — enables "what do we know about X" rollups. |
| `fi_external_ref_spine` × N | Curated card-catalog entries for cited papers. Only refs from *accepted* quests persist. |

## Configuration

See [USAGE.md](USAGE.md) for the full annotated YAML schema. Quick
landmarks:

- `provider.*` — provider name, model, reasoning effort, per-node model routing, ensemble.
- `engine.*` — max_iterations, review_panel, ensemble, no_simulation, survey_mode (literature/history synthesis: no experiment and no dataset), and the rest of the research-loop knobs.
- `pauses.*` — the unified human-in-the-loop section: clarify, papers, supply, plan, review, auto_accept_on_pass, timeout_s (legacy `engine.*` / `knowledge.*` pause flags still map in).
- `execution.*` — venv vs docker, timeout, python version.
- `knowledge.*` — Axon config, top_k (RAG) + external_top_k (web), relevance_min_score (literature relevance floor) + relevance_min_keep, local_papers, full-text fetch.
- `output.*` — kinds, paper_format, audience, output_dir, require_pdf.
