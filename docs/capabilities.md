# Frontier Insight — capability reference

What this doc is: a feature index for people evaluating FI or looking
for a specific knob to twist. README is the elevator pitch; USAGE.md
is the YAML schema; this file is the breadth catalogue.

## The 20-node DAG

> Simplified happy path below — see ``core/engine.py:_build_graph``
> for the authoritative edge set. Conditional branches that aren't
> drawn: the design→implement vs design→auto_collect_data fork (no-
> simulation mode), and the ``broaden_lit`` arc from cross_check back
> to literature when analyze asks for a wider sweep.

```
START → clarify → ideate → literature ←─────┐ (broaden_lit)
                                │             │
                                ↓             │
                              design ─────────┘
                                │
            ┌───────────────────┴───────────────────┐
            ↓ (computational)                       ↓ (no_simulation)
     implement_outline                       auto_collect_data   ‡ survey: design ──→ web_figures (skips
            ↓                                        ↓              auto_collect_data … web_plots) ──→ analyze
            ↓                                        ↓
        implement ──→ execute ──┐               wait_for_data
                                │                    ↓
                          execute_reflect ←─(retry)  data_load
                                │                    ↓
                                │                 web_plots
                                │                    ↓
                                ↓ (proceed)       web_figures
                              analyze ←───────────────┘
                                ↓
                          cross_check ──┐ (re_experiment → design)
                                │       │ (broaden_lit → literature)
                                ↓
                          evidence_gate ─┐ (broaden → literature)
                                │ (write)
                                ↓
                              write
                                ↓
                          claim_check
                                ↓
                              review ──→ human_feedback ──→ END (accept)
                                │
                                ↓ (revise → design)
```

Feedback loops in this diagram: `execute_reflect → execute` (retry),
`cross_check → design` or `cross_check → literature` (analyze re-
route), `evidence_gate → literature` (broaden), `review → design`
(revise). `evidence_gate` (between cross_check and write) weighs
assembled evidence before any paper is written; `claim_check` (between
write and review) grounds the paper's claims. The `human_feedback`
gate, when enabled, sits between review and END.

The design fork has a **third branch, `survey`** (‡ in the diagram), for a
descriptive history / overview synthesised purely from the literature — no
experiment and no dataset. It is a stronger form of no-simulation: after
`design` it routes straight to `web_figures` (license-clean illustrative
images) → `analyze`, skipping the experiment (`implement`/`execute`) **and**
the whole data-collection chain (`auto_collect_data` → `wait_for_data` →
`data_load` → `web_plots`). `analyze` synthesises the reviewed sources
directly. Survey mode turns on from `engine.survey_mode: true`, from the
"Literature synthesis" research approach in the interview, or automatically
when the clarify step classifies the topic shape as `survey` (a "history of
X" / "evolution of X" / overview topic).

Feedback loops:

| Loop | Trigger | Bound by |
|---|---|---|
| `execute_reflect → execute` | Script crashed (rc != 0 or no `RESULT_JSON`) | `engine.exec_reflect_max_iterations` (default 3) |
| `cross_check → design` | `analyze.next_step == "re_experiment"` | `engine.max_iterations` (default 2) |
| `cross_check → literature` | `analyze.next_step == "broaden_lit"` — re-enters literature with the design's hypothesis folded into the query | `engine.max_iterations` (default 2) |
| `review → design` | `review.verdict == "revise"` | `engine.max_iterations` (default 2) |

## Capabilities

Grouped for skimmability. If you want to know whether FI does X, this
is the index.

### Engine + execution

- **Async LangGraph engine** with 20 nodes and 4 feedback loops; see `core/engine.py:_build_graph` for the actual edges.
- **Per-quest venv with auto-cleanup** — agent-generated Python is installed and run in isolation in `<quest_root>/.venv/`. On successful quest finish the venv is frozen to `.fi/requirements.lock.txt` and then removed to reclaim disk (typically 150–250 MB per quest). The lock file makes the environment reproducible: `python -m venv .venv && .venv/bin/pip install -r .fi/requirements.lock.txt`. Failed or paused quests keep their `.venv/` so you can poke at it.
- **Docker sandbox** — `execution.sandbox: docker` runs the experiment subprocess with network disabled, mounted at `/work`.
- **Provider matrix** — direct HTTP, proxy, CLI exec, and VSCode-extension transports (see provider matrix below).
- **Per-node model routing** via `provider.node_models` (e.g., a cheap model for `clarify`, a strong one for `write`).
- **Pre-flight `clarify` node** — slot survey before `ideate`; off / auto / interactive modes. The slot set includes ``topic_shape`` (``experimental`` / ``survey`` / ``review`` / ``case_study`` / ``opinion``) so the engine recognises when a topic naturally wants a literature synthesis instead of a code experiment — ``survey`` (a "history of X" / "evolution of X" / overview topic) takes the no-experiment, no-dataset survey path. **Agent judgment beats the format heuristic.** Most `clarify_overrides` pinned by the interview are user *preferences* (study depth, venue, output kinds, baseline, metric, budget) and rightly win over the agent's self-answers — but ``simulatability`` and ``topic_shape`` are topic *judgments*. When the agent runs in `auto` mode and its judgment conflicts with the interview's pinned value (which is often just a paper-format heuristic), the **agent's value wins back** for those two slots, so a review-shaped topic the agent flags as no-simulation isn't force-run as a toy experiment by a stale `simulatability: "yes"` override. The hard `engine.no_simulation: true` YAML pin is separate and still absolute; there is intentionally no hard "force simulate" — the engine trusts the agent's "can a simulation actually answer this?" call. When the shape is non-experimental but simulatability still resolves to SIMULATE (the agent itself judged it simulatable), the engine logs a WARNING in run.log and the design stage falls back to a narrow illustrative experiment with weight shifted to literature synthesis (rather than a full comparative benchmark).
- **Execute-repair loop** — agent reads traceback, patches code, retries (`engine.exec_reflect_max_iterations`).
- **Stale-figure purge on re-execute** — every `execute` clears `figures/` before running the experiment. On a `re_experiment` / `broaden` / repair loop the `implement` node rewrites `experiment.py`, which may emit a *different* set of figure filenames; without the purge the previous version's plots linger (they're not overwritten), get counted in `figures=N`, and pollute the paper/slides/poster with a mix of current and stale figures. Only figure-suffixed files are removed — `results.csv` and other artifacts survive.
- **Numeric oracle** — a deterministic, non-LLM comparison of the numbers in `paper.md` against the ones the run actually produced. Every other correctness gate ends in a language model reading text — `claim_check` asks one call whether a number "appears" in the evidence, with no arithmetic anywhere — so a mis-transcription (2.14 computed, 2.41 written) passes all of them. The oracle looks for the *signature of a copy that went wrong*: a paper number sitting near a real result without matching it, where the gap cannot be explained by rounding to the paper's own precision. Digit transposition is reported separately because it is almost never a coincidence. Numbers far from every result are assumed to come from the design or the literature and are ignored, as are figure/table/section references, code blocks and low-precision quotes; results tables are deliberately checked. A hit is reported as an `unverified_number` finding naming the value and the `result_json` path — in the log, in `paper/numeric_audit.json`, and in the human-review panel of the web UI and the VSCode chat — under both the single reviewer and a `review_panel`. It does not force a rewrite: the check is a regex over prose, and a forced revise cycle on a false positive costs more than a flagged number, so the verdict stays with the reviewer. `paper/numeric_audit.json` is written on every run, clean or not, so silence never has to be read as "the check was skipped".

- **Physics-plausibility gate** — the design declares what its outputs may legally be (`result_assertions`: a path, a min/max, a unit and the reason) and those bounds are enforced **in code** against `result_json`. This is the gap the degenerate-run guard cannot cover: that one fires only when every metric is ~0, so it catches a run that produced nothing and misses a run that produced the wrong thing convincingly — a unit error, a factor of two, a sign flip. A violation routes back through the execute-repair loop before any paper is written, and the repair is told which bound broke. A value sitting exactly on a non-zero bound is rejected too when the script itself caps values at that constant (`min(x, 10.0)`, `np.clip`, `if x > 1e6: x = 10.0`): a cap turns divergence into an in-range number the range check could not otherwise tell from a real one. Both halves are required, so a genuine perfect score is left alone. A value that really is out of range should be reported as `null` with a flag saying why, and the implement and repair prompts say so. Assertions state what physics or the definition of the quantity guarantees, never what the design expects to happen; bounding a result to the hypothesis would make the run unable to disagree with it. An absent assertion is not checked — silence means "nothing was claimed", never "everything is fine".

- **Simulation skills** — `engine.skills` lets a quest call tested code instead of re-deriving physics. A skill is a directory carrying instructions (`SKILL.md`), optionally an API surface and executable entry points, an executable `selftest.py`, and provenance including its own range assertions. The envelope follows the [Agent Skills open standard](https://agentskills.io/), so a skill written for another agent works here unchanged: bundled `scripts/`, `references/` and `assets/` directories are read alongside FI's own single-file `api_surface.md` and `skill.py`. Their *contents* never enter a prompt — the block names the files and their paths, and generated code opens what it needs, because a references directory can be larger than the quest itself. A skill shipping only `scripts/` is treated as a tool rather than a library, which is what puts "drive it" instead of "import it" in front of the model. Maturity is derived from which files exist (notes → guided → adapter), so a skill hardens without migrating. **FI ships no skills** — not one, including any its own authors wrote: a skill that arrives with the install is a curated library again, and curation does not compound. Discovery covers `FI_SKILLS_DIR` (default `~/.frontier-insight/skills`, deliberately outside the repo, because skills accumulate per machine rather than being things you commit) and the `fi.skills` entry-point group, so a library can ship its own skill without anyone editing FI. **Two gates stand before use, and both must pass:** the self-test the skill carries must run green, and a person must have approved *that exact content* — approval binds to a content hash, so a skill rewritten by distillation lapses its approval rather than inheriting it. An unattended `--fleet` run therefore cannot adopt capability nobody signed off on; a skill that is not trusted is absent from the prompt, and the quest falls back to generating the physics itself. A **selection step** between literature and design decides which skills a quest actually carries. It reads a catalogue — one line per skill: kind, description, its *when NOT to use* limit, and its track record — and picks what fits, at temperature 0 so the same topic selects the same skills. This is not cosmetic: injecting every trusted skill into the four design/implement prompts cost ~465 tokens per skill per node, so a 50-skill library added ~93,000 tokens to every quest pass — the accumulation mechanism becoming its own largest cost. The catalogue for the same library costs about 13k tokens once per quest — measured on a real published skill, whose 845-character description is carried in full because the phrases that make it findable sit in its later sentences. Still an order of magnitude better than injecting everything, and it is paid once rather than on every pass. Selection can only narrow: a name it invents, or one belonging to an unapproved skill, is discarded and logged, so no model can talk capability into a quest. Choosing nothing is a normal answer and the quest then generates its own code. The chosen skills' instructions, API surfaces and selection reasons go to `design` and the `implement` stages — which may decline one they judge inapplicable, saying why in `method` — and their range assertions join the plausibility gate above. `engine.skills` narrows the candidate set when set, and means "every trusted skill is a candidate" when empty; `engine.skills_exclude` keeps named skills out, which also makes the A/B comparison easy. `python launch.py --why-skills "<topic>"` previews the whole decision without running a quest, and a quest whose review is accepted writes itself into the provenance of the skills it used, under a file lock so parallel `--fleet` runs lose no records. Manage them from the CLI: `python launch.py --skills` lists every skill with the reason it is or is not usable (running each self-test, since a status that did not execute the check would be a guess), and `--approve-skill <name> --approve-as <you>` records approval (`--revoke-skill` undoes it). There is no anonymous approver — the gate exists so a person decides. **All three interfaces carry the whole gate**: the web dashboard's `/skills` page and the VSCode chat panel (`@fi /skills`, `/scan-skill`, `/approve-skill`, `/revoke-skill`, `/import-skill`, `/teach-skill`) list, review, approve and revoke exactly as the CLI does. They render `launch.py --skills --json` and the matching web API rather than reimplementing discovery, hashing, the ledger or the scanner, so the surfaces cannot drift. Each keeps the ceremony intact: the approver is named every time — prefilled in VSCode, typed in the browser, never derived from a session — and a high-severity finding takes a second explicit confirmation. The UI surfaces list without running self-tests, since each can take up to ~2 minutes (a generated selftest's own timeout scales with how many scripts a skill bundles — see `core.skills.registry.run_selftest`), and both say plainly that the statuses shown are as last recorded rather than verified.

  Approval binds to the **whole** skill directory, not a list of named files: everything under it is hashed except `provenance.json` and Python bytecode. That distinction is load-bearing — a rule covering only the files someone remembered to name would let an approved skill's bundled `scripts/` be swapped with the approval intact, which is the human gate guarding the wrong thing.

  Because a skill's `SKILL.md` enters a prompt verbatim and its `selftest.py` is executed, `python launch.py --scan-skill <name>` statically reviews one before you approve it: instruction-injection phrasing and invisible characters in the prose, network access, `eval`, and environment reads in the code, fetch-and-decode chains in shell scripts. Nothing is imported or run — Python is parsed as a syntax tree, everything else by pattern. The scan runs on every `evaluate()`, so hand-authored and entry-point skills are covered as well as imported ones, and a high-severity finding **stops** `--approve-skill` unless `--despite-findings` is also passed, with the ledger recording that it was. The flag exists because approving past a flagged network call is often correct — what it buys is that reading the findings becomes an act rather than an assumption. **Findings never block a skill.** They are heuristics: a skill that legitimately drives a network tool will flag one, and quarantine stays reserved for a self-test that actually failed. For the same reason the report never says a skill is safe — it says how many findings came out of how many rules, because a payload no rule describes is unfound rather than absent.

  Because FI works in any field, the library is not filtered by domain — which would make every installed skill a candidate for every quest, the same accumulation problem one level up (~28,000 tokens for a hundred-odd skills, growing with the library). So the catalogue is **layered**: a skill with no domain tag is general and always a candidate, while tagged ones (`--import-skill --domains genomics,biomedical`) are admitted only when the quest's topic looks related. Relevance reuses the all-MiniLM cosine already used for passage ranking, blended with lexical overlap — no new dependency. Under `FI_OFFLINE` it loads the model from the local HF cache rather than skipping it (no network call either way); it degrades to lexical alone only when the model is genuinely absent — not installed, or not cached under `FI_OFFLINE`. If relevance cannot be computed at all, **every** domain skill is admitted and the selection report says why: selection can only narrow, so a catalogue that is too large costs tokens and is visible, while a silently too-small one changes results with nothing to show for it.

  Two commands teach FI a skill. `--teach-skill <name> --from <module>` drafts one from an installed library, reading its real signatures by introspection rather than generating them, and leaves the judgement calls — when it applies, when it does not, what its outputs may legally be — as TODOs for you. `--import-skill <path>` brings in a skill written for another agent, preserving the front-matter `description` that makes it findable and carrying its bundled directories; `--list-foreign-skills` shows what is available to import. An import **generates** a self-test rather than leaving the skill unusable: it probes that every bundled script is present and answers `--help`, which catches a broken, moved or incomplete install. That is deliberately less than a written test proves. A generated test cannot check that a tool still behaves the way `SKILL.md` describes — the thing a self-test exists for — so the generated file says so in its own text, `--skills` marks the skill, and approval repeats it. The marker lives in the file, so rewriting the test with real checks clears it; a flag in `provenance.json` would have gone stale at exactly that moment. For a prose-only skill with no scripts, the generated test states plainly that passing proves only that the files are on disk.

- **Degenerate-run guard** — `engine.degenerate_run_guard` (default on) treats a script that exits 0 but emits an all-zero RESULT_JSON as a soft failure: the execute-repair loop gets a chance to fix the underlying bug (wrong grid/sampling, a threshold/edge finder returning a zero sentinel, bad normalization) before a paper is written. If the result is still degenerate after repair, analyze flags it and frames an honest failure note instead of reporting silent zeros as findings.
- **Bounded result_json in the analyze prompt** — the full `RESULT_JSON` stays in state at full fidelity (it feeds `results.csv`), but the copy spliced into the analyze prompt is compacted to a ~200 KB budget. A pathological experiment can dump raw arrays/images into its `RESULT_JSON` — one low-k1 DUV quest emitted a 36 MB block that blew past `codex_cli`'s 1,048,576-char turn limit and hard-failed analyze. The compactor keeps the structure **valid and representative**: long lists keep head + tail elements with a count-of-elided marker, long strings are truncated, and dict keys + scalar summary stats (the values analyze actually reasons over) survive intact — so the model interprets summary statistics instead of choking on raw pixel dumps. A WARNING fires when compaction happens, pointing at the real fix (have the experiment emit summary statistics, not raw arrays). Complements the provider-layer input-cap guard, which remains the last-resort net for any oversized prompt.
- **Analyze-driven re-route** — `re_experiment` re-enters design; `broaden_lit` re-enters literature with the hypothesis folded in.
- **Cross-paper check** — per-finding literature search + supporting / conflicting / neutral classification. Optional CoVe-style **verification pass** (`engine.cross_check_verify: true`, default off): a second LLM call per finding re-examines each non-neutral assignment with pointed verification questions and revises the classification — typical revision is "this 'supporting' citation is actually too topically thin, downgrade to neutral". Adds 1 LLM call per finding with non-neutral hits (typically +1–5 calls per quest); skipped when the first pass produced no non-neutral assignments. Verified output replaces the first-pass classification in `state['cross_check']`; the first-pass snapshot is preserved alongside under `first_pass` for audit, and `verification_notes` carries the question/answer trail.
- **Pilot pass** — `engine.pilot_run: bool = False` (opt-in). Off by default because honouring `FI_PILOT` is a prompt instruction the engine cannot enforce: a script that ignores it runs at full scale under a fifth of the timeout, so it times out and warns on every quest. Turn it on once a setup has shown its scripts comply. Before the real run, the engine executes the same `experiment.py` with `FI_PILOT=1` set (the implement prompt instructs the script to shrink whatever dominates runtime while keeping the identical metrics and `RESULT_JSON` keys) under a short timeout (`engine.pilot_timeout_frac`, default 0.2 × `execution.timeout_s`, floored at 30s). `execute_reflect` already repairs a script that *crashes*; the pilot catches the other failure — a script that runs cleanly and answers the wrong question, which otherwise costs the full timeout to discover. Its numbers are **discarded**; only its signal is used, and it never fails a quest: a pilot that crashes logs a warning and the full run proceeds (where `execute_reflect` can repair it with the traceback it needs), and a pilot whose values break the design's own `result_assertions` warns that the **design** is the likely fault (range, units) rather than the code.
- **Design-revision provenance** — `needs/DESIGN_HISTORY.json`. `review` and `cross_check` can both route back to `design`, so a hypothesis can legitimately be rewritten after its results are known. A finished paper looks identical either way, which is what makes the record necessary: entry 0 is the pre-registration (stated before any result existed), and every later entry is flagged `post_hoc` with the trigger that sent the engine back (`analyze.next_step`, or the reviewer verdict) plus whether the hypothesis text actually changed. Nothing is blocked — the record exists so the revision is auditable rather than invisible.
- **Multi-seed replication** — `engine.execute_replicates: int = 3` (default 3). A single run is not a result: one number has no error bar, so reporting it as a finding overstates what the experiment showed. Replication re-runs the generated SCRIPT only -- `implement` is not re-invoked, so it costs **no extra LLM calls**, only local compute. Set 1 to opt out on a slow experiment. When >1, the execute node runs the generated `experiment.py` N times: once normally, then N-1 more times with `FI_REPLICATE_SEED=<i>` set in the env so the script can deterministically seed every RNG it uses (the implement prompt instructs it to read this env var). All N `RESULT_JSON` payloads land in `state['result_json_replicates']`; the analyze node aggregates every numeric leaf — **nested results included**, flattened to dotted paths like `by_h.0.5.RK4.trajectory_error`, which is the normal shape for a parameter sweep — with mean ± sample-std **plus standard error and a 95% confidence interval**. An interval stops at the values its metric cannot pass: 0 and 1 for a metric named as a probability or proportion (`probability`, `fraction`, `share`, `accuracy`, …) whose seeds all lie in [0, 1], and the range the design's or a skill's `result_assertions` declares for it. Metrics that were identical across every seed are omitted from the analyze prompt and counted in a note, so a crossed design cannot crowd out the analysis it is meant to inform and surfaces them to the writer so the paper reports `metric (95% CI lo–hi, n)` instead of a single-seed point estimate. **Line figures are drawn as the mean.** The plot-style bootstrap keeps each seed's lines; after the seeds run, a figure whose panels hold only lines, with the same labels and x values at every seed, is drawn again over the same file as each line's mean shaded with its 95% confidence interval (bounded like the results), by `code/replot_figures.py` in the quest's Python under the house style, and the writer is told the figure is the mean of N seeds. A bar chart, a histogram, or a figure with anything else on it (text, an image, a colourbar) keeps the run that drew it last. The number check and the claim check compare the paper with each result's mean and 95% CI over the seeds as well as with seed 0's values. **Stops early on a deterministic experiment.** Honouring `FI_REPLICATE_SEED` is not the same as consuming randomness: a script can seed every RNG and still compute the same answer every time (integrating an ODE, say). After seed 1 its `RESULT_JSON` is compared against seed 0; if they are identical the remaining seeds are skipped and analyze reports that the experiment is deterministic rather than printing an aggregate of zeroes. Costs at most one extra run to find out, and unlike asking the design to declare itself, it cannot be wrong about what the script did. **Runs after the plausibility gate, not before.** A result that violates the design's `result_assertions` is about to be regenerated by `execute_reflect`, so replicating it first would pay N× for an error bar on a discarded number. Failure isolation: a single replicate failure (NaN, OOM, transient) doesn't abort the rest — the aggregator skips the failed seed; if the *primary* run fails the engine skips replication entirely (fix the script first via the execute_reflect loop). Cost: N executions per design pass. Use 3–5 for variance reporting; 10+ for the rare case where a tight CI matters.
- **Statistical rigor — CIs, effect sizes, multiple-comparison guard** — beyond the per-metric 95% confidence intervals above, when results carry `by_<factor>` strata the analyze payload also gets, computed in pure stdlib (no numpy/scipy): a **95% CI per stratum**, the **pairwise effect size** (Cohen's d + a negligible/small/medium/large label) between strata for each shared metric (strata nest: in a crossed design such as `by_h` → step size → method → metric, every level below the `by_*` key whose children share one shape is compared too, so method A vs method B is reported at each step size under a dotted label like `by_h.0.5`), and a **multiple-comparison guard** — the number of comparisons made and the Bonferroni-corrected α (`0.05 / N`), with a `many` flag when there are more than five. The analyze + write prompts are instructed to report the CI alongside each headline number, quote the effect size when claiming one group beats another, and not over-claim a single stratum difference that wouldn't survive correction; a single-seed run honestly reports "no replication → no CI." A small embedded t-table covers small-n replication exactly.
- **Stratification-by-factor across the implement/analyze/write contract** — when the experiment naturally has categorical strata (clip classes, methods, datasets, seeds, difficulty levels), the engine threads them through end-to-end. The `implement` prompt instructs the generated `experiment.py` to emit ``by_<factor>`` per-stratum breakdowns in `RESULT_JSON` alongside aggregates; the `analyze` prompt surfaces per-stratum findings as tagged bullets (``[by_clip_class:isolated_lines] ...``); the `write` prompt's honesty rules forbid collapsing those findings into an aggregate-only Results section unless the analysis explicitly notes the effect is uniform. Single-condition experiments are unaffected — aggregate-only stays aggregate-only.
- **Ideate self-reflection** — extra LLM call may swap the chosen idea (or `engine.ideate_tournament: true` for pairwise N-way comparison).
- **Design self-critique** — after the `design` node drafts a methodology, a second LLM pass audits it for the same four patterns the methodologist reviewer hard-flags (circular evaluation, single-point eval, weak-baseline retention, dimensionless/grid-only metrics) and emits an amended design BEFORE `implement → execute → analyze → write` spend compute on a bad plan. Failure-isolated: a transient provider error or parse failure on the critique keeps the original draft, never blocks the quest. Strictly advisory.
- **Two-stage implement** — the `implement` step is split into `implement_outline` (writes a Python scaffold with function signatures, constant sources, and the `RESULT_JSON` template — typically 30–80 lines with `raise NotImplementedError` bodies) and `implement` (fills in each function body, consuming the outline as input). Splitting the work lets each LLM call be smaller; on complex topics that previously triggered ~9 min extended-thinking spans on Sonnet 4.6, the outline+body pair lands in 2–5 min total with progress visible between calls. Failure-isolated: an unparseable outline OR a transient outline-call error makes the body fall back to the legacy single-shot prompt (also used on pre-Phase-2 checkpoint resume). The body stage commits to the outline's function signatures, so an outline mistake surfaces at body-write time rather than after execute. Default `provider.node_cli_timeout_s`: outline → 600 s, body/legacy-fallback → 1800 s (the body call typically finishes in 90–180 s once the outline lands, but the same `implement` bucket also covers the legacy single-shot fallback that needs the full extended-thinking budget).
- **Reviewer panel** — N personas in parallel + moderator synthesis (`rigor_score` + `depth_score` axes). The built-in **methodologist** persona hard-flags four common-but-fatal patterns: circular evaluation (optimization objective shares model/simulator/distribution with the evaluation metric — "train-on-test"), single-point evaluation where a sweep is the field norm, admitted-weak baselines kept in the comparison instead of re-run, and metrics in dimensionless / grid-only units without a physical-grounding bridge. Each persona's response includes a ``must_flag_hits`` list (canonical names: ``circular_evaluation``, ``single_point_eval``, ``weak_baseline_no_rerun``, ``pseudo_units``); the aggregator unions hits across the panel. A non-empty ``must_flag_hits`` forces another revise pass **even when** ``engine.review_loop: false`` is set — the operator cannot accidentally short-circuit the design loop the must-flag block exists to gate. The persona must explicitly state non-applicability of each check rather than reach acceptance by silence. **New quests (via the interview, CLI `--new`, or VSCode `@fi /new`) default to a 3-persona panel** (methodologist + statistician + devil_advocate) instead of the cost-conscious single reviewer; the methodologist must fire for the non-bypassable must-flag enforcement to take effect. Single-reviewer mode is still selectable in the interview when cost is the priority.
- **Unified human-in-the-loop (`pauses:`)** — every place the quest stops for a human is one of two interactions — **ANSWER** (it asks; you reply) or **SUPPLY** (it needs files; you drop them) — configured under one coherent `pauses:` section: `pauses.clarify` (off/auto/ask), `pauses.papers` (bool), `pauses.supply` (never/before_build/before_review/both), `pauses.review` (off/ask), plus `pauses.auto_accept_on_pass` and `pauses.timeout_s`. The legacy flags (`engine.clarify_mode`, `engine.human_feedback_gate`, `engine.pause_for_user_input`, `knowledge.pause_for_user_papers`, `engine.auto_accept_on_pass`, `engine.human_feedback_timeout_s`) still parse and are mapped in automatically. Whichever pause fires, the engine writes one **`<quest_root>/NEXT_STEP.md`** — why it stopped, exactly what to do, and the resume command — and deletes it on completion; the Web GUI and VSCode each show a single **Action needed** affordance sourced from it. Resume is always `fi --resume <id>` (or the Resume button).
- **Human-review gate** — `pauses.review: ask` (the default) pauses the quest after the review node and waits for a human to accept / reject / refine the result before finalising. The snapshot includes verdict + score + must-flag hits + suggestions + the accumulated `feedback_history` of every prior refine round (so a later iteration honours every prior ask, not just the most recent). Three interfaces consume it:
    - **Web dashboard** — banner on `/quest/<id>` with Accept / Reject / Refine buttons + a textarea for refine feedback; in-process spawn paths resolve via a Python future, subprocess paths write `<quest_root>/.fi/human_review_answer.json` and auto-trigger a resume.
    - **CLI** — `python launch.py --config <yaml> --interactive` prompts on stdin (`accept` / `reject` / `refine` + one line of feedback). For a headless run that paused, decide in **one command** with the resume flags — `--resume <id> --accept`, `--resume <id> --reject`, or `--resume <id> --refine "your feedback"` (these write `human_review_answer.json` for you, no hand-editing). The pause message prints these exact commands. A terminal **`--accept` / `--reject` is guarded**: it's refused (exit 2) unless the quest is genuinely paused awaiting review (`pause.json` with `kind=review`), and it will not overwrite a *different* decision already staged (e.g. a `refine` just submitted from the web UI). This stops a stray CLI accept from silently bulldozing an in-flight refine and auto-finalizing past it. A **`--refine` is never blocked** — it's the user adding work.
    - **VSCode** — the chat panel renders the verdict + must-flag hits + suggestions; QuickPick collects the action; refine opens a second input box for the feedback text.
  An explicit **refine is always honoured** — `_route_after_human_feedback` routes it to a real revision pass even when `iteration >= max_iterations` (that cap bounds the *unattended* review loop, not the user's deliberate click); the refine runs one design→…→review pass and returns to the gate, so the user can refine again or accept. A finished quest can also be **re-opened for another pass** — the quest page's **Re-run** button (or `fi --rerun <id>`, or `POST /api/quests/{id}/resume?rerun=true`) re-enters the pipeline even when the LangGraph checkpoint is at its terminal state (`next=()`): the engine `aupdate_state`s back in at the human-review gate's edge so the graph re-routes through `design → … → review → human_feedback`, applying any saved `feedback_history` (so a refine that landed past the cap finally runs) and re-running whatever stages an Update invalidated. Without this a finished quest's checkpoint has no pending task, so a plain resume was a no-op.
- **Human-review timeout** — `engine.human_feedback_timeout_s` (default 1800 s; `0` disables) bounds how long a wired callback (web POST, VSCode QuickPick) is awaited. If it elapses, the engine stops waiting and falls back to the headless path (on-disk `human_review_answer.json`, else clean pause-exit with the snapshot saved + a `--resume` hint), so an orphaned UI prompt can never park a quest forever.
- **`--auto-accept-on-pass`** — auto-accept the human-review gate for *clean* papers only (verdict=accept AND no must-flag hits). Flagged or revise-verdict papers still pause for review. Intended for `--fleet` so the production runner doesn't block on every clean quest. Also exposed as `pauses.auto_accept_on_pass: true` in YAML and the engine fixture path used by tests.
- **Multi-model ensemble** — fan out a node's LLM call across multiple models in parallel and merge. Per-node `provider.node_ensemble` with `models` / `merge` (`tournament` | `synthesize` | `vote`) / `moderator`. Interview surfaces four preset profiles (`off` / `cross_check_only` / `ideate_and_check` / `full`, cost multipliers 1.0× → 2.5×). `analyze.merge: synthesize` is rejected at config load.
- **No-simulation decision** — three-tier (`engine.no_simulation` → clarify `simulatability` → legacy `empirical_vs_theoretical`); routes through `auto_collect_data → wait_for_data → data_load → web_plots → analyze`. In this mode the design stage produces an **analytical / observational study** (a derivation, comparison, or synthesis — no executable experiment), and the paper is written as such: it never frames a "planned experiment that wasn't run" or narrates the engine that produced it.
- **Web-derived plots** — `engine.web_derived_plots` (default on) gives the no-simulation path figures even though it runs no experiment: an LLM charts the concrete quantitative data found in the collected web/data sources and writes a self-contained matplotlib script (data inline), run in the same sandbox the simulation path uses; each figure is stamped with its source. It charts **only numbers a source actually reports** — never the model's own categorization turned into a count (no fabricated "4 of 6 → 66.7%" pies) — and emits `NO_PLOT` honestly for qualitative topics with no real numbers, rather than forcing a chart. The script is prefixed with the **Frontier Insight house figure style** (Palatino-style serif, teal-anchored palette, warm off-white ground, hairline grid, no top/right spines) so the charts match the paper / poster / slides identity instead of the default matplotlib look.
- **One downloaded-sources folder** — retrieved sources are written once to `data/literature/` (the citation record, every quest). On the no-simulation path the analysis reuses that folder directly instead of duplicating it; `data/auto_collected/` holds only the *additional* agent-collected evidence (Axon hits, dataset-adapter tables) that isn't part of the cited literature, so the two folders never hold the same files twice.
- **License-clean figure enrichment** — `knowledge.fetch_web_figures` (off by default) embeds up to `knowledge.web_figures_max` (default 2) *illustrative* figures so a study carries a visual point of view beyond its own charts: a real figure from a **cited CC-licensed arXiv paper** (the default arXiv license forbids reuse, so those papers are skipped) plus **Wikimedia Commons** diagrams under CC / public-domain. Only ever embeds free-licensed images (CC BY / CC BY-SA / CC0 / public domain — NC/ND rejected); an LLM relevance gate drops keyword-match misfires; each figure is attribution-stamped (Source + license) and recorded with its caption + license so the writer credits it and the references log its provenance.
- **Pause-drop-anytime** — opt-in user-input gate at one or both of two natural pause points: `pauses.supply: never | before_build | before_review | both` (default `never`). When set, the engine pauses after the named stage (LangGraph `interrupt()` → clean rc=0 exit with the unified `<quest_root>/NEXT_STEP.md` explaining what to drop where), the user drops reference papers into `inputs/papers/` (PDFs/MDs, ingested by the literature node on resume) and/or datasets into `inputs/data/` (CSVs/JSON/Parquet/etc., walked into `state['user_supplied_datasets']` and surfaced in the analyze prompt under the `_user_supplied_datasets` key inside its `result_json` block — no new `$placeholder` in `analyze.md`, so the prompt stays backward-compatible), then runs `fi --resume <quest_id>`. A disk marker at `<quest_root>/.fi/paused_at_<stage>.flag` is the authoritative "already paused here" signal so a re-entry doesn't loop the user through the same drop screen (state-only tracking can't survive a LangGraph `interrupt()` raise — the partial state-list update never lands in the checkpoint). Datasets are picked up by both the design node (on after-design resume) and the analyze node (catches drops staged at after-paper), so the analyze prompt always sees fresh data regardless of which pause stage was used.
- **Auto-collect before pause** — `auto_collect_data` queries Axon with `topic + hypothesis` and drops up to `engine.auto_collect_top_k` (default 5) hits into `data/auto_collected/` before pausing for the user.
- **Dataset adapters** — `engine.dataset_adapters` opts into structured external lookups (`worldbank`, `wikipedia`). Writes evidence into `auto_collected/<adapter>/`.

### Knowledge layer

- **Axon-backed retrieval + write-back** — literature retrieval and cross-quest memory.
- **Web research toggle** — `knowledge.web_search` (interview question **Web research**, default on, independent of the Axon layer) runs a general web search (Brave when `BRAVE_API_KEY` is set, else keyless DuckDuckGo) in parallel with academic retrieval, and `knowledge.web_fetch_pages` (default on) fetches each hit's full page text so the writer can quote it and the plotter can mine numbers.
- **Literature downloaded for every quest** — the literature node writes each retrieved source to `data/literature/lit_NNN_<slug>.md` (provenance front matter + content) for **every** quest, simulation and observational alike — so the collected corpus is always auditable on disk even on the simulation path (which never reaches `auto_collect_data`).
- **Bot-wall handling + open-access full-text cascade** — many academic sources (PMC, MDPI, …) serve a reCAPTCHA / "checking your browser" wall on a `200`, and paywalled publishers (ScienceDirect, Wiley, IEEE, Springer) serve an abstract-only stub; both are detected and discarded (paywall stubs via a schema.org `isAccessibleForFree` / known-paywall-vendor / call-to-action check) rather than stored as content. For an academic source the fetcher prefers the clean open-access full text directly: it resolves the article's `PMCID` / `DOI` / arXiv-id (cross-resolving via Europe PMC when a web result carries only one), then tries, in descending order of text quality, **the PMC BioC API** (clean section-labelled passages, no HTML cruft), **Europe PMC** `fullTextXML`, the **preprint** server (arXiv / bioRxiv / medRxiv), **Unpaywall** (every OA location, published-version + direct-PDF + repository copies first), and finally **Semantic Scholar** / **CORE** (when an API key is set). Whatever is recovered lands as real full text instead of a snippet.
- **Clean main-content extraction** — HTML pages are run through `trafilatura` (when installed) to isolate the article body and drop nav / menus / related-article / reference cruft, falling back to a built-in tag-strip extractor otherwise. Figure captions + image alt-text are appended so the writer is aware of a source's visuals.
- **Relevance-selected excerpts** — full text is fetched and stored uncapped on disk, but each node's prompt receives only the passages most relevant to the quest question (`knowledge.literature_excerpt_chars`, default 4000). Ranking is `knowledge.passage_ranking`: **`auto`** (default) blends sentence-transformer cosine with lexical term overlap so a result stated in *paraphrase* ("death rate" for a "mortality" query) is still surfaced — `FI_OFFLINE` loads the model from the local cache rather than skipping it, falling back to pure lexical only if no model loads at all. `hybrid` and `embed` request the semantic path explicitly (still falling back to lexical if the model is unavailable); `lexical` forces the dependency-free term-overlap path. So a result or number buried mid-document reaches the writer / plotter — not just the abstract that happens to sit in the first 2000 characters.
- **Independent Axon vs external caps** — `knowledge.top_k` (default 8, RAG precision) is independent of `knowledge.external_top_k` (default 20, web breadth). The literature node passes both; ideate/cross_check seeds respect the smaller per-call cap.
- **Audience-aware citations** — `output.audience: "external" | "internal"`. External papers drop FI-internal cross-quest entries from References; internal papers keep everything.
- **Further reading** — web pages are listed apart from the scholarly sources a claim is cited to. The writer's prior-work block numbers papers `[1]`, `[2]`… and labels web pages `[W1]`, `[W2]`…; the engine writes the paper's `## References`, listing the papers the text cites, and a `## Further reading` section listing every web page; a list the writer wrote itself is replaced. Every output labels from one de-duplicated list: claim grounding accepts a `[W<k>]` source, the poster's reference band lists the web pages its text cites as `[W<k>]` with their site name, the slide deck leaves the web pages to the paper, and the pages are exported to `paper/further_reading.bib` / `.csl.json`. The review's depth floor (at least 3 sources discussed by content for a journal-length paper) counts References and Further reading together. Applies to every quest.
- **Axon sidecar auto-launch** — every CLI / `--serve` boots `python -m axon.api` if one isn't already listening. Skip with `--no-axon-sidecar` or `FI_NO_AXON_SIDECAR=1`.
- **Axon endpoint discovery** — the sidecar's port isn't fixed (Axon resolves it as `--port` > `AXON_PORT` > its `config.yaml` `api.port` > `8420`), so FI searches instead of assuming: the running server's own lock file (`<projects_root>/.axon-api.lock`), then Axon's `config.yaml`, then the built-in defaults, probing each until one answers. All three surfaces use the same search, so a sidecar you started by hand is found without configuring anything. `AXON_API_BASE` (or the VSCode `frontierInsight.axonUrl` setting) pins FI to one specific instance — useful for a remote or containerised Axon, and deliberately *not* a fallback, since two Axon instances hold different corpora. When nothing answers, the error names every endpoint tried and where each came from. In VSCode the search also runs patiently at startup — the extension keeps watching for `frontierInsight.axonStartupWaitSec` (10 minutes by default) and stays silent throughout, so starting Axon minutes after opening the editor produces no notice at all; only a sidecar that never appears does.
- **Offline / air-gapped models** — `knowledge.offline` + `knowledge.models_dir` (or `FI_OFFLINE` / `FI_MODELS_DIR` env) load the embedding + reranker weights from a local HF cache with no network call. Produce a shippable cache on a connected machine with `launch.py --export-models <dir>`. Both the in-process layer and the sidecar honour it. See `docs/INSTALL.md`.
- **arXiv request queue** — every connection FI makes to arXiv (full-text HTML and PDFs, abstract pages, figures, arXiv copies found through Unpaywall or Semantic Scholar, and the headless-browser fallback) goes through one queue: one connection at a time, at least 3 seconds apart, as arXiv asks of automated clients. The queue's state is a lock file under the cache directory, so it holds across processes too — the web UI and VSCode run each quest in its own process. A rate limit (HTTP 429) pauses the whole queue for 1, then 2, then 4 minutes; if arXiv is still refusing, that quest stops contacting arXiv and the other sources carry on, and the source failure report says so. Work with a time budget (full-text enrichment has 90 s) gives up on a slot it cannot get in time rather than sleeping through a backoff. Successful responses are cached on disk for 24 hours (`FI_CACHE_DIR`, default `~/.frontier-insight/cache`; `FI_ARXIV_CACHE=0` disables), so a resumed or repeated quest does not download the same papers again.
- **Multi-source literature router** — arXiv / OpenAlex / Crossref / Semantic Scholar / PubMed / CORE / OpenAIRE / DOAJ / Google Scholar in parallel, deduplicated by id and normalized title. CORE, OpenAIRE and DOAJ need no key; they carry the open-access humanities and social-science books, theses and journals the STEM-leaning indices cover thinly, and the router is told to use them for those topics. CORE also accepts an optional `CORE_API_KEY` for a higher rate limit. OpenAIRE and DOAJ require every query word to match, so when a longer query finds nothing FI retries once with its first three words. arXiv is searched through OpenAlex's arXiv source rather than arXiv's own query API, which has been capacity-throttled for everyone since arXiv's move to the cloud; full text still comes from arxiv.org. `knowledge.openalex_api_key` / `OPENALEX_API_KEY` unlocks OpenAlex's full daily budget (keyless is about 100 searches a day, and arXiv searches count against it), and `knowledge.semantic_scholar_api_key` / `SEMANTIC_SCHOLAR_API_KEY` gets Semantic Scholar off its mostly rate-limited shared pool.
- **General web search** — `knowledge.web_search` (default on) adds a general-web layer (Brave when `BRAVE_API_KEY` / `knowledge.brave_api_key` is set, else keyless DuckDuckGo) that runs **in parallel** with Axon + the academic adapters for every quest and is merged + deduped by URL/DOI/title. This is what lets non-academic topics (company financials, markets, current events, culture, how-to) retrieve real sources instead of irrelevant nearest-neighbour papers. Web hits carry their `url` / `site` as citation metadata. With `knowledge.web_fetch_pages` (default on) the result pages' readable text is fetched (not just the snippet) so the writer can quote real content and the plot step can mine numbers from it.
- **Relevance guard** — `knowledge.relevance_guard` (default on) scores the auto-collected sources against the topic and drops confident-but-off-topic hits; if nothing is on-topic it pauses for user-supplied sources rather than writing an honest-but-useless "pipeline failure" paper on garbage. Fail-open on any judge error.
- **Literature relevance floor** — `knowledge.relevance_min_score` (default 0.20) is a cheap, deterministic complement to the LLM relevance guard, applied in the **literature node for every quest** (the guard runs only on the auto_collect path, which survey/simulation quests skip). Each retrieved doc is scored by embedding cosine (the shared all-MiniLM model) against the **topic**, and the off-topic tail is dropped before it reaches analyze/write — so a "sculpture in pop culture" quest no longer carries change-point-math papers. Never-starve: `knowledge.relevance_min_keep` (default 3) always retains the top-scoring docs; fail-open when embeddings are unavailable (FI_OFFLINE); `0.0` disables.
- **Literature screen** — `knowledge.literature_screen` (default on). The embedding floor scores word overlap, so a journal's table of contents, or a paper on another system that shares the search terms, still passes it. After the floor, one batched call (node `literature_screen`, run at temperature 0 like the other gates) grades every retrieved source 0–3 on one question: could the paper cite this for a claim? Scholarly records need a 2 to stay. Web pages are dropped only at 0, because they are kept for the text the writer quotes. The rubric tells the model that for a quest without an experiment, books and chapters count as fully as articles. At least `knowledge.relevance_min_keep` sources survive, best grades first. A failed or unreadable call keeps everything, and a source left ungraded is kept. Sources the user supplied (`knowledge.local_papers`, `inputs/papers/`) are never screened. Kept sources carry `screen_grade`.
- **Foundational works** — `knowledge.foundational_works` (default on). A search engine matches every word of a query, so the original papers and standard textbooks a topic rests on rarely come back: for a quest comparing integrators on a damped oscillator, none of the three facet queries returned Verlet (1967), Hairer, Lubich & Wanner, or Butcher in OpenAlex's first 200 hits, and sorting by citations only pulled in famous off-topic work. After the relevance floor, one call (node `literature_foundational`) asks the model for up to five foundational works; each is looked up by title in OpenAlex (sorted by citations, books and chapters allowed) and kept only when a record's title matches and its year is within two or its authors include the suggested first author. The works that at least two retrieved papers cite (two OpenAlex requests over their reference lists) are added too. Works already retrieved are dropped. The rest join the candidates labelled foundational, and the literature screen grades them with one extra rubric line: a method's original paper or textbook is a 2 when the paper would cite it for something it uses, however old, and a famous work the question does not use is still a 0 or 1. Their `data/literature/` files record how each was found (`foundational:`). A failed call or lookup adds nothing.
- **Topic-aware LLM source routing** — agent picks venues (web + academic) from the source catalog.
- **Citable record types only** — scholarly indices also hold datasets, figure components, peer-review reports, dictionary entries and journal issues, none of which a claim can cite. Crossref, OpenAlex and OpenAIRE searches keep journal articles, conference papers, preprints and reviews. A quest without an experiment (a survey, a history, a humanities or policy question — `no_simulation` resolved on) also keeps books, book chapters and dissertations, because much of that scholarship is published there. The rule follows the resolved run mode rather than a separate subject classifier. Each retrieved record carries its `work_type`.
- **Keyword search queries, three facets** — the literature node does not hand the topic statement to the search engines, because a paragraph-long topic tends to match nothing in keyword-based academic search. One small call (node `literature_query`, routable through `provider.node_models` like any other) turns the topic, the chosen idea and, on a re-entry, the design's hypothesis into three short keyword queries, one per facet: the core subject, a specific angle and the wider frame. A single query reaches only the work written in its own words. The wording follows the kind of quest: methods, systems and measured quantities when there is an experiment; the names scholars write under (works, people, periods, places, movements) when there is not. The facets share one source-routing decision and only the first also runs web search. Their results are interleaved and deduplicated, and legal full text is fetched once, for the sources that survive the relevance screen. DOAJ requests are paced to its two-per-second limit. Any failure falls back to the previous title + topic string. The queries sent are kept on the quest state as `literature_queries`, and the first also as `literature_query`.
- **Local paper feed** — `knowledge.local_papers` pins paywalled PDFs / MDs to the retrieval head. An entry may be a **file or a directory** — a directory is scanned recursively for `.pdf` / `.md` / `.txt`, so a quest can be pointed at a folder that already holds enough research material.
- **Pause-for-user-papers gate** — `pauses.papers` (interview question **Supply paywalled papers**; default **on**, `false` for an unattended run) pauses when a real, resolvable paper (DOI / arXiv-id / PMID or an academic adapter) came back as abstract-only — the cases the open-access cascade genuinely couldn't fetch (SPIE / IEEE / Elsevier …). It writes a single ranked **`needs/WANTED_PAPERS.md`** — most relevant first (scored against the topic + hypothesis), each with a download link, what it's about, and its status — plus per-paper `needs/<slug>.json`. The user downloads the few that matter, drops the PDFs into `inputs/papers/`, and runs `fi --resume`; the literature node ingests them as `source=user_supplied` full text. In the **Web GUI** the quest page shows the wanted list with an upload box + Resume; the **VSCode** extension surfaces the same list with drop-and-resume instructions.
- **Full-text fetch** — `knowledge.try_fetch_full_text` (default on) fetches legal full text for the scholarly sources that survive the literature screen: open-access copies (arXiv, PMC, Unpaywall, …) and publisher PDFs your own network can already reach, with login walls rejected by a content-type and `%PDF` check. The whole batch shares `knowledge.full_text_fetch_total_s`; set `false` for abstracts only.
- **Structured ingest** — title-searchable spine docs + citation-header'd body + topic rollups.

### Outputs

- **Paper PDF** via pandoc + LaTeX — real venue-flavored templates for `generic` / `neurips` / `iclr` / `ieee_access` two-column / `nature_mi`. Preprocessor lifts `# H1` into YAML `title:`, lifts `## Abstract` into YAML `abstract:` and the `**Keywords:**` line under it into `keywords:` (printed under the abstract and set as the PDF's keywords), shifts heading levels by −1, dedupes `"Title. Title."` patterns, sets PDF metadata via `\hypersetup`. The LaTeX engine is found via a 3-tier search: `pdflatex` (MiKTeX/TeX Live) → system `tectonic` → repo-local `tools/tectonic[.exe]`. pdflatex stops at the first Chinese, Japanese or Korean character, so a paper with such text in its title, body or author line compiles with **XeLaTeX + `xeCJK`** in an installed CJK font instead.
  - Font choice: Noto Sans CJK / Source Han Sans first, then Microsoft JhengHei, Microsoft YaHei, Yu Gothic or Malgun Gothic, found through fontconfig or the Windows fonts folder.
  - With no XeLaTeX or no CJK font, the paper goes straight to the HTML fallback.
  - Tables in the two-column `ieee_access` template: LaTeX's `longtable` cannot run in two-column mode, so a table that fits a column is set as a table float, and a table taller than a column gets single-column pages where it breaks across pages.
- **Selectable paper style** — `output.paper_style: latex | briefing` (default `latex`). `latex` keeps the venue LaTeX template (Computer Modern article). `briefing` renders `paper.pdf` in the Frontier Insight **"Research Briefing"** look — warm paper, deep-teal accents, serif display, the brand mark — via the HTML/Chromium backend, so it matches the slides + poster identity. It needs pandoc + a Chromium-family browser (no LaTeX) and falls back to the LaTeX path with a warning when those aren't present; it's single-column regardless of `paper_format`. Selectable in YAML and in the `--new` / `@fi /new` / web interview (the `paper_style` slot). Works in all three interfaces because it's an engine-level config.
- **LaTeX-free PDF fallback** — `output.html_pdf_fallback` (default on) gives a 4th tier: when no LaTeX engine is reachable at all, pandoc renders `paper.md` into a Computer-Modern-styled HTML page (the `templates/paper/_html/latexlike.css` theme, with **Latin Modern Roman vendored + embedded** so the output matches the MiKTeX/tectonic `article` look — flush-left title, "Frontier Insight" byline, centered Abstract, numbered sections, justified body), then a headless system **browser** (Edge/Chrome/Chromium) prints it to `paper.pdf`. No LaTeX, no admin install — just pandoc (already needed) + a browser, which a locked-down machine almost always has; figures and fonts are inlined so the PDF is self-contained. It can't reproduce a venue's two-column class, so it always renders the single-column house style; set `output.html_pdf_fallback: false` to force the strict LaTeX-only path (skip-with-diagnostic when no engine). The pre-flight treats a present browser as satisfying the `paper_pdf` prerequisite, so `require_pdf: true` won't abort a quest that can render via the fallback. **The fallback also fires when a LaTeX engine is present but *errors*** — not just when none is found. A half-present MiKTeX that chokes on something the LLM emitted (a bare `\command` in text mode, an unsupported glyph) used to hard-skip the PDF; now the browser path — which never touches LaTeX — rescues it, so the same `paper.md` still produces a `paper.pdf` while the LaTeX error stays in run.log.
- **Non-scientific paper formats** — `essay` / `report` / `policy_brief` / `whitepaper`, each with a full LaTeX template + per-format writer persona.
- **Author line** — `output.author`, `output.affiliation`, `output.contact_email` and `output.url` (all optional, asked as the last tier-1 interview questions on the CLI, web and VSCode) print under the paper title in every LaTeX template and the HTML render, set the PDF's Author field, go on the slides' title slide (HTML/PDF deck and pptx), and head the poster, whose QR code appears only when `url` is set. Pandoc receives them as metadata, which it escapes for LaTeX, so an `&` in an affiliation or a `_` in an email cannot break the compile. With no author set the byline stays "Frontier Insight". The values go only into the quest's own files. `output.poster_size` (`a1_portrait` default, `a0_portrait`, `landscape_48x36`) picks the poster sheet.
- **Research poster** — `poster.pdf` follows published poster guidance instead of squeezing the paper onto a page.
  - **Header:** the main finding as the headline, the paper's title under it, the author line, and a QR code when `output.url` is set.
  - **Type:** body 26 pt on A1 (36 pt on the larger sheets), headings about 1.5× the body, numbered figure captions, about 60 characters a line.
  - **Content:** the model writes headings, short texts, bullet lists and captioned figures to a word budget for the sheet; the generator writes all the LaTeX.
  - **References:** only the sources the poster cites, at most 8, without raw URLs.
  - **Layout:** whole sections go to columns, and figures fill each column, narrowing to 70% of its width to fit. When one column is planned to end more than 6 cm above the other, the longer column's figures narrow further, down to half the column, until the columns end together.
  - **Checked:** every compile is measured (fonts, overflow, column balance), and the result lands in `.fi/poster_fit.json`. The first plan never cuts content, since the header and band heights are only known once compiled; a compile that measures more room than planned is planned again. The model's reply is kept in `.fi/poster_reply.txt`.
  - **CJK:** Chinese, Japanese or Korean text compiles with XeLaTeX and a CJK font, as for the paper.
- **Slides** — `slides.md` always; `slides.html` / `slides.pdf` (Marp CLI) when available, and **`slides.pptx` always** -- rendered in-process by `generation/_pptx_slides.py` with python-pptx, applying the same `templates/slides/fi.css` design language (warm paper ground, teal kicker rule above each serif slide title, teal list markers, wordmark footer) as the HTML deck. No external binary, so it renders on locked-down hosts; it replaced a `pandoc -o slides.pptx` shell-out that needed pandoc on PATH and produced an unthemed plain-white deck. Output is native, fully editable PowerPoint. Paragraphs and bullets keep the slide's order, and `**bold**`, `*italic*` and `_italic_` carry over (an underscore inside a word, as in `forward_euler`, stays as written). `$...$` math (pandoc's rule, so "$5 and $7" stays text) becomes **native PowerPoint equations** (`generation/_pptx_math.py`: LaTeX → MathML with `latex2mathml` → OMML for rows, superscripts, subscripts, fractions and roots). Each equation carries a readable text form with real superscripts and subscripts for viewers without equation support. LibreOffice, and so the pptx visual check, shows that form. Math outside the supported set is written as that text only. A slide's text layer showing `$...$` or a LaTeX command is also measured as `raw_markup`. `poster.tex` always when `poster` is in `output.kinds`; `poster.pdf` compiles via the same 3-tier LaTeX-engine fallback the paper generator uses (pdflatex → system tectonic → repo-local `tools/tectonic[.exe]`), with a `poster_pdf_skipped.md` diagnostic on skip. Both the paper and poster run LLM-authored content through a shared Unicode sanitizer before pdflatex sees it — Greek/math glyphs become LaTeX commands, emoji are stripped, and **invisible/zero-width format characters** (zero-width spaces, joiners, BOM, soft hyphens, exotic spaces) are stripped or normalized, since a single stray U+200B otherwise hard-errors the compile. `speech` via single LLM call.
- **Consistent Frontier Insight design + branding** — the slide deck, poster, and paper share one editorial "Research Briefing" identity: a serif display face for titles, a system-sans body, a single deep-teal accent, and structure carried by hairline + teal rules rather than boxes. Each surface carries a subtle palette-native teal brand mark — a bottom-left corner lockup on the slides, a masthead lockup plus a reference-band mark on the poster, and a footer mark on the paper — driven from a single glyph asset so the look is uniform across all three.
- **Branded figures (matplotlib house style)** — experiment figures are no longer raw matplotlib defaults. Before the experiment runs, the engine drops a guarded `sitecustomize.py` bootstrap onto the script subprocess's `PYTHONPATH`, so Python applies the FrontierInsight house style at interpreter startup — *before* the generated code imports matplotlib, with zero edits to that code. The look: the brand teal-anchored qualitative color cycle (teal → terracotta → slate → olive → …), despined axes with a hairline y-grid, clean left-aligned editorial titles, frameless legends, and a branded teal sequential colormap (`fi_teal`) for heatmaps. The figure backdrop tracks `output.paper_style` — warm cream for `briefing`, white for `latex` — so figures blend into the paper they land in. Model-independent (it can't be forgotten or done wrong by the LLM) and failure-isolated (any error falls back to the plain environment). The same bootstrap records what each saved figure draws (`.fi/figure_records/<figure>.json`): every panel's title, axis labels, y scale and limits, and each line's or scatter's range, named by its label or by its entry in a legend given only names (`ax.legend(["euler", "rk4"])`), marked **flat** when it spans under 1% of its axis or **not shown** when it lies outside it. The writer and the analysis see that record next to each figure's file name, and before review a script checks every caption against it: a caption naming a series its figure does not show, or one it draws flat without saying so in the same clause ("stay flat at this scale", "near zero", "indistinguishable" say so) (the validation quest captioned a plot "energy drift rates for RK4 and Velocity-Verlet" while both lines lay flat at 0 under Forward Euler's spike) is listed in the review prompt with an instruction to must-flag `figure_caption`, logged, and shown in the human-review panel of the web UI and the VSCode chat. With `execution.sandbox: docker` the record's path is a host path the container cannot write, so no record is made. The implement prompts also steer the model toward figures that *read well* — units on axes, direct labels over boxed legends, small-multiples for per-stratum comparisons — and away from dumping raw arrays into `RESULT_JSON`.
- **Length-aware page fitting** — outputs that pack content onto a fixed page are auto-fitted so an over-long LLM result can't overflow. A slide figure takes only the room left under its slide's text (at most about half the slide, aspect kept), and a caption written on the line under a figure is split into its own paragraph, so neither the figure nor its caption runs off the bottom of the slide. In `slides.pptx` a figure goes 0.2 in under its slide's text by the text's estimated height, and the text shrinks before the figure gets less than 2.2 in. The estimate counts each line at its line spacing times 1.2 times the type size, measured against LibreOffice and PowerPoint on seven slides (within 3.3 pt of LibreOffice, up to 6 pt over PowerPoint); the old 1.0 left a figure 0.1 pt under the last bullet. The **poster** plans its columns from estimated block heights, compiles, and measures the PDF (`generation/_pdf_measure.py`). Sections stay whole where they fit, and the text or list right after a figure stays with that figure; a column that still has to open inside a section repeats the section's heading as "Heading (continued)". A first plan made for the guessed room that came out over its own limit is planned again for the measured room even when the sheet measures clean, since it may have split a section to get close. Content that runs past the sheet or into the reference band first narrows figures, then trims lists and sentences, then drops blocks from the middle; uneven columns are re-split. It stops after at most six compiles and never shrinks the type. The **paper** breaks reference URLs at any character (`xurl` + pandoc's `autolink_bare_uris` + `\urlstyle{same}`) so a long wiki-style link wraps inside the text column instead of running into the right margin.
- **Visual check of every rendered PDF** — `output.visual_check` (default on) runs after the outputs render, on each PDF the pass produced (paper, slides, poster). A resume checks only the outputs it made. Each PDF is measured and screenshotted; the AI step, which sends the screenshots to the provider, runs only with `output.visual_check_ai: true` (default off, about 12,000 tokens a quest).
  - **slides.pptx:** with LibreOffice installed (`generation/_office_pdf.py`, found on PATH or in its default install folder), the pptx is exported to PDF with a fresh LibreOffice profile, so a LibreOffice window the user has open is never involved, and checked as `slides_pptx` with the slides' checklist and measurements. It is checked once, after any slides redo, since it comes from the same `slides.md`. Without LibreOffice the report says the pptx was not checked. `--doctor` lists LibreOffice.
  - **What it sends (with `output.visual_check_ai: true`):** screenshots at 90 dpi (longest edge at most 2000 px) and the `_pdf_measure` measurements go to the configured provider, with a fixed checklist of what only eyes can see: cut-off text, overlaps, unreadable figures, raw markup, broken math, garbled text and empty areas, plus a check or two per output. Sizes, overflow, a figure drawn over a slide's text and a figure starting less than 6 pt under a line of text (`figure_gap`, low severity, never a redo), and a paper page before the last with 35% or more of its text area empty (`half_empty_page`, never a redo) come from the measurements, not the model.
  - **Grounded findings:** every finding must quote text visible where the problem is. A quote that is not on that page (or the page before or after), a check not on the list, or a finding with no region is dropped, and the report keeps it with the reason.
  - **Redo:** the slides and poster are generated again with the findings a new version can fix, at most `output.visual_check_max_redos` times (0–2, default 2). The slides' model writes the whole deck, so its layout findings count. On the poster only text the model wrote counts, since the layout is the planner's. The version that checks best is kept and a worse one is put back file for file. The paper is never rewritten: when its last page holds only a line or two (measured as `last_page_nearly_empty`), it is recompiled once with a text area one line taller (its footer stays where it was), and the better version is kept.
  - **Providers without image input** check from the measurements alone, and the report says so. [docs/PROVIDERS.md](PROVIDERS.md) lists which providers can see images.
  - **Report:** `.fi/visual_check.json`, one entry per output with its attempts, plus the screenshots under `.fi/visual_check/<output>/`. The CLI and the VSCode chat print one line per output, the web quest page shows the same lines (read from the report, so a running quest shows them too), and `frontier_insight_summary.json` carries each output's result in brief. A check never stops the quest.
- **Citations in every output** — the sources a quest actually consulted (web pages carry their URL) are rendered as References across all three surfaces, not just the paper: the engine builds the paper's numbered References section from the papers its text cites, numbered in the order the text first cites them, rewrites the citations to those numbers and drops any citation of a number the prior-work block does not have (the literature is reordered to match, so the claim check, poster, slides, bib and the next write pass use the same numbers); the poster's reference band lists the sources its text cites (at most 8, built from the retrieved literature, so it survives even when the LLM only saw a truncated `paper.md`, and showing a web page's site name rather than its URL); the slide deck ends on one appended **References** slide, in both the HTML/PDF deck and the pptx: the sources the paper cites most (at most 6, as many as fit at a readable size), in reference order, and a line saying how many more are in the paper. Web URLs and paper DOIs are both first-class; FI-internal cross-quest entries are filtered out of external-facing outputs.
- **Claim grounding** — `engine.claim_grounding` (default on) inserts a `claim_check` node between `write` and `review` that extracts the paper's substantive claims and grounds each as **experiment** (it restates a number/result this quest produced), **citation** (it rests on a specific cited `[N]` paper in References, or a `[W<k>]` web page in Further reading), or **unsupported**. For each source the paper cites, the check is shown the passages of its text most related to the citing sentences (up to 1,500 characters), and a citation must quote that text: FI looks the quote up in the source (ignoring case, quote marks and line-break hyphens, at least 25 characters), and a claim with no quote, or a quote the source does not contain, is unsupported. A transparency ledger is written next to the paper — **`paper/claims.json`** (structured) + **`paper/CLAIMS.md`** (grounded-fraction + the unsupported list) — and any unsupported claims are surfaced to the reviewer with an instruction to must-flag them. When a reviewer does raise a must-flag, the revise pass is then **non-bypassable and deterministic** (forced even with `review_loop` off, capped by `max_iterations`) — but note the trigger runs *through* the reviewer reading the unsupported list, not a direct `claim_check → revise` edge, so enforcement is only as reliable as the panel (the methodologist persona owns it; a single-reviewer/empty panel weakens it). When every must-flag is a problem with the text (`unsupported_claim`, `figure_caption`), the experiment stands and only the paper is written again (`review` → `write` → `claim_check` → `review`, with the review, the unsupported claims and the user's feedback in the write prompt); any other must-flag sends the quest back to `design`. Set `engine.claim_grounding: false` to make the node a no-op passthrough (no LLM call, no ledger). The ledger records each citation's quote.
- **Evidence gate** — `engine.evidence_gate` (default on) inserts an `evidence_gate` node between `cross_check` and `write` that weighs the assembled evidence — source count, the cross-check supporting/conflicting balance, whether the run produced real measurements — against the research question **before** any paper is written, and returns a verdict: **sufficient** (write), **broaden** (re-enter the literature loop once more, bounded by `engine.evidence_gate_max_broaden`, default 1), or **insufficient** (write anyway, but the assessment is handed to the writer so the paper frames its thin evidence honestly rather than over-claiming). It **fails open** — any parse error, or the flag off, routes straight to write — and is deliberately calibrated to pass most well-run quests; it exists to stop a confident-looking paper from being authored on evidence that doesn't support the question, not to refuse answerable topics. Set `engine.evidence_gate: false` for a no-op passthrough.
- **Research protocol** — a typed `core.protocol.ResearchProtocol` (research question, `topic_type`, `source_policy`, expected evidence, baseline, success metric, replication, stopping criteria, requires-user-input) consolidates the otherwise-scattered clarify slots into ONE validated contract, derived deterministically from the resolved clarify answers + engine config (no extra LLM call). It is handed to the `evidence_gate` so the sufficiency judgement is **contract-aware** — e.g. a topic whose `source_policy` is `web_current` (markets/current events) is judged insufficient if it has only academic sources, because that policy requires recent web sources; a `survey` (history/overview) topic's `mixed` policy accepts credible web / encyclopedic / museum sources so a humanities corpus isn't judged insufficient merely for lacking peer-reviewed papers. Recorded in `state['research_protocol']`. A declarative `core.protocol.ROUTE_MATRIX` is the single source of truth mapping each `topic_type` to the graph path it expects (`simulation` vs `no_simulation`) and the `source_policy` it implies; it is consulted at the design fork so `topic_type` is a first-class routing input. The resolved `no_simulation` flag stays authoritative (config/clarify wins the actual edge), but when the topic type's expected path disagrees with the resolved route the engine logs a `[route]` WARNING in run.log — bidirectional (it also catches a future build/engineering topic that resolved to no-simulation), complementing the earlier clarify-time `topic_shape`-vs-SIMULATE warning.
- **One entry per work** — retrieved sources are de-duplicated on every identity they carry, not just the strongest id: DOI / arXiv id / PMID / URL, and also a normalized title (case, dashes, punctuation, HTML entities and full-width forms folded). The same textbook appendix printed in three books under three DOIs, or an arXiv preprint returned once with its DOI and once without, is one source in the literature, the merged search results and the References. Titles shorter than three words or generic ones ("Introduction", "Preface", "Book review", …) never count as an identity, so different books' chapters stay apart.
- **Machine-readable citations** — the numbered References (scholarly sources) are also exported next to the paper as **`paper/references.bib`** (BibTeX) and **`paper/references.csl.json`** (CSL-JSON), and the Further reading web pages as **`paper/further_reading.bib`** and **`paper/further_reading.csl.json`**, so a finished quest drops straight into Zotero / Mendeley / a LaTeX or Pandoc workflow instead of leaving citations trapped in the markdown body. Entry types are chosen from the available fields (`@article` when it has a venue/journal, an `eprint`/`archivePrefix=arXiv` entry for a bare preprint, a `howpublished` web entry for a page), cite keys are stable + unique (`firstauthor+year+word`), and BibTeX special characters are escaped. Both files are listed in the quest's file tree in the Web GUI for direct download.
- **On-demand artifact generation** — produce ONE more output format (PDF / slides / poster / talk) for an **already-finished** quest **without re-running the research**. `Engine.emit_artifacts_only()` loads the quest's LangGraph checkpoint read-only and bundles its on-disk `paper.md` + figures (no node re-runs), then only the requested generator fires. Three surfaces: CLI `python launch.py --config <yaml> --resume <id> --emit paper_pdf`; the Web quest page's **Outputs** panel (a ✓/Generate row per format, showing which the quest is configured for and which exist); and VSCode `@fi /generate [<quest_id>] [<format>]`. So a markdown-only quest can get a PDF (or slides/poster/talk) later, on demand, for the cost of one render.
- **Source failure report** — every literature and full-text source (OpenAlex, Crossref, arXiv, PMC, Unpaywall, publisher pages, web pages, figure sources, …) records its failures against the quest that made the request: a rate limit, another 4xx/5xx answer, a timeout, a network error, an unparseable body, or full-text fetches abandoned at the time budget. A 404 is an answer ("not in this index"), not a failure. Each failure is a `[source-failure]` line in `.fi/run.log` as it happens, with credentials redacted, and every run ends with one `[source-failures]` summary line (`none` when clean) plus `.fi/source_failures.json`, written on success, pause and failure alike. The CLI prints `[FI] source failures: …`, the web quest page shows a banner, and the VSCode chat shows the same line. Before this, a quest could lose every arXiv and OpenAlex result and its log said nothing.
- **Skip diagnostics** — every output kind that fails to produce its primary artifact drops a `<kind>_skipped.md` breadcrumb next to where the artifact would have landed (`paper_pdf_skipped.md`, `poster_pdf_skipped.md`, `slides_skipped.md`, `speech_skipped.md`), explaining what was requested, why it couldn't be produced (missing CLI, refused LLM response, render-tool error, …), and how to fix it. The user discovers the failure by opening the quest folder instead of grepping `run.log`. Diagnostics are idempotent: a subsequent successful run of the same kind removes the stale breadcrumb.
- **Quest failure diagnostic** — when a `_node_*` method raises or a pre-graph stage (preflight, endpoint resolution, executor setup) fails, the engine writes `<quest_root>/quest_failed.md` with the exception text, failing-node name (from the LangGraph snapshot when available), provider context, log tail, and a `--resume` command. Any re-run clears the stale file **as soon as it starts** — not only at terminal state — so an in-flight resume that's already running past the node that broke isn't shown as "failed"; if the re-run also fails, the exception handler writes a fresh diagnostic in its place. Same discoverability contract as the skip diagnostics: the failure is visible from the quest directory itself, not just `<quest_root>/.fi/launch.log`.
- **Cite-by-content references** — prior-work block carries author / year / title / venue / DOI, and the engine's References entries carry the same fields. The writer cites only the prior-work block's labels and writes no source list; the prompt forbids fabricating a source or embedding fenced code in the body.

Pinned values land in `engine.clarify_overrides`.

The form pre-fills from the quest's existing YAML (not interview defaults), so unchanged fields round-trip cleanly; `STAGE_INVALIDATION` decides which downstream nodes re-run when an editable field changes. Hand-crafted `provider.node_ensemble` blocks the interview can't classify back to a preset are preserved across update saves. `no_simulation` is hard-locked mid-quest.
- **Status GUI** — FastAPI server at `web/static/index.html`: fleet list, SSE log stream, clarify panel, paper preview, panel-review cards. Tools dropdown with ARIA semantics (`aria-haspopup` / `aria-expanded`) + Escape-to-close + first-menuitem auto-focus on open.
- **Web UI quest launching** — `--serve` spawns `python launch.py --config <yaml>` via `web/quest_launcher.py` (capped at `--max-concurrent`). Detail page auto-refreshes every 3 s. Non-loopback bind logs a WARNING.
- **Web UI "everything" pass** — `/tools/{proposal,critique,digest,portfolio,summarize,analyze,fleet,ingest}`, file browser, zip download, resume button, clarify-resume panel, labels, cost chart, paper iterations, exec edit (gated by `FI_WEB_ALLOW_EXEC_EDIT=1`), trash bin at `/trash`, `/compare?a=&b=`, `/settings`, `/about`. Self-hosted Markdown renderer (`md_lite.js`).
- **Bridge-aware vscode_extension across all serve forms** — `/interview`, `/update/<id>`, and every `/tools/*` form surface `vscode_extension` at the top of the provider picker when a VSCode bridge is reachable. The model dropdown lists **every** chat model VSCode exposes to the extension, tagged with the vendor it came from — Copilot's catalogue, and anything registered by another extension's language-model provider (an Ollama server, a BYOK OpenAI-compatible endpoint). Picking one routes the quest through it. The schema endpoints **TCP-probe the bridge port and IPC-probe the bridge socket** before reporting availability, so a stale or wrong configuration can't lie to the UI. Without a reachable bridge the entry stays hidden — same source of truth as the submit-time 400 guard. Model dropdowns offer "Other (type your own)" with a text-input fallback on every page. The picker's selection is threaded through to the spawned subprocess via a `--<tool>-model` flag for every LLM tool (proposal / critique / digest / portfolio / summarize / analyze), so the picked id reaches `ProviderConfig.model` and the bridge actually routes to the chosen model instead of falling through to the Copilot Chat-picker default.
- **id-first model selection on the VSCode bridge** — `selectChatModels` is queried with `{id: hint}` first, then `{family: hint}`, in both `PersistentBridge` (`--serve` / tools path) and the per-chat-command `Bridge` (`@fi /start` path). The picker stores model **ids** (e.g. `gemini-3-flash-preview`), and Copilot's family is sometimes coarser (`gemini-3-flash`), so filtering by family alone misses every versioned/preview model. Family fallback keeps the legacy `gpt-5` / `claude-opus-4-7` style hints working. When nothing matches, the error dumps the full `id|family` catalog so the next mismatch is self-diagnosing.
- **Per-user IPC PersistentBridge for --serve / --tools** — the FI VSCode extension starts a session-long bridge at activation, listening on a per-user OS-managed address (`$XDG_RUNTIME_DIR/fi-bridge.sock` on POSIX with `/tmp/fi-bridge-{uid}.sock` fallback, `\\.\pipe\fi-bridge-{USERNAME}` on Windows). `--serve` auto-resolves the same path via `core.bridge_path.persistent_bridge_path()` and routes LLM calls through `vscode.lm.*` with no port to wire and no env var to set. Shared-Linux hosts isolate cleanly (each UID gets its own socket); per-chat-command bridges (`@fi /start`, `@fi /digest`, etc.) keep using their existing per-spawn TCP transport. Opt-out via `--no-vscode-bridge`.
- **Bridge stall-timeout recovery** — when Copilot's HTTP/2 stream stalls mid-response, both the TS-side bridge (per-chunk inactivity timer) AND the Python-side `VSCodeBridgeClient.chat` (outer `asyncio.wait_for` against `provider.cli_timeout_s`, default 300 s) surface a `bridge stalled` error. The phrasing is load-bearing: `_TRANSIENT_BRIDGE_MARKERS` in `core/provider.py` matches it so tenacity retries the call. Older `.vsix` builds (no TS-side timer) or a TCP/IPC blip that drops the `lm_error` itself can no longer wedge the engine.
- **CLI streaming + inactivity watchdog** — `claude_cli` is invoked with `--output-format stream-json --include-partial-messages` so Sonnet 4.6's `thinking_delta` events arrive as a steady pulse during extended-thinking spans that otherwise look identical to a hung process (the old `--output-format text` mode buffered the entire response, including 9+ minutes of pre-answer thinking on complex prompts, into one silent stdout flush). The reader resets a soft `cli_inactivity_timeout_s` watchdog (default 180 s) on every stream event, while the hard `cli_timeout_s` ceiling still applies as a last-resort kill; per-node overrides in `provider.node_cli_timeout_s` raise that ceiling for reasoning-heavy nodes (`implement` → 1800 s, `execute_reflect` → 900 s) without bumping the cheap nodes. `Engine._chat` wires a heartbeat callback that logs progress every ~30 s: `[implement] still waiting on LLM — thinking (2400 thinking-token events), elapsed=4m22s, idle=0s`. The **non-streaming CLIs also heartbeat** — `codex_cli` (`last_message_file`, stdout DEVNULL'd) and `copilot_cli` / `gemini_cli` (plain stdout) have no token-level signal, so the `communicate()` path fires the same callback on a ~10 s timer; the line reads `still waiting on LLM — no events yet, elapsed=Ns`, so a long silent codex/copilot call no longer reads as "pending" on the dashboard.
- **CLI output gate registry** — vendors sometimes deliver upstream-state text (rate-limit messages, give-up placeholders, policy refusals) as plain `text_delta` events instead of structured error envelopes. Without protection, the engine aggregates that text and writes it to disk *as* the artifact — observed in production where `paper.md` became literally `"You've hit your session limit · resets 2:30am (Europe/Brussels)"`. `_collect_via_streaming` and `_run_cli` both run the assembled response through `_check_output_gates`, a registry of named gates: `rate_limit_message`, `placeholder_response`, and `refusal`. Each gate has its own marker list and a 500-char length cap so a real paper-length output that mentions any marker in body text doesn't false-positive. The first gate that fires names itself in the raised `_CliTransientError` so retry logs say *which* gate triggered. Tenacity retries (and may escalate the model via the per-node fallback table — see model-escalation bullet).
- **Jittered retry backoff** — every tenacity retry policy in `core/provider.py` (HTTP direct, VSCode bridge, CLI exec) uses `wait_random_exponential` instead of a deterministic `wait_exponential`. A deterministic schedule synchronises N concurrent fleet quests on a shared upstream blip — they all retry at the same wall-clock instant and re-clog the upstream. Random-exponential picks uniformly from `[0, multiplier · 2^attempt]` capped at `max`, spreading retries over a window so the upstream sees a gentler ramp. Eliminates a thundering-herd failure mode that's invisible until you run a busy fleet.
- **Tenacity model escalation on retry** — `provider.node_model_fallbacks` maps node name → fallback model. On retry attempt 2+, `_chat_cli` switches the CLI invocation to the fallback model. Empirical motivation: Sonnet 4.6 + extended-thinking on long code-gen prompts (implement-body, write) reproducibly paralysis-thinks (verified 3× across prompt size and output shape variants, all hit 15-min wall with zero text); Opus 4.7 lands the same prompt in ~5 min. The default fallback map escalates `implement` and `write` to `claude-opus-4-7` so the user's preferred primary model is honoured on first try and degrades gracefully. Set `{}` to disable. Standalone CLI matrix (verified on this very prompt): `claude_cli`+`claude-opus-4-7` works, `codex_cli` works, `copilot_cli`+`gpt-5-mini` works, `gemini_cli` aborts via its own loop-detector, `copilot_cli` default model times out.
- **Wedge fail-fast** — an extended-thinking CLI hang (the model streams thinking for minutes, then closes stdout with **no answer** and won't exit even to SIGKILL) is raised as a distinct `_CliWedgeError` and **bailed after the 2nd occurrence** instead of burning the full 4-attempt budget on the same dead end (~2 wasted multi-minute calls). Observed 4-for-4 on a heavy `claude_cli` code-gen prompt. The reraised error carries actionable guidance — *"the fix is a different provider for this node (e.g. resume with `--config <codex_or_openai>.yaml`)"* — so the `quest_failed.md` tells the user how to recover instead of showing a cryptic "stdout closed" line. (Model escalation happens on retry 2, so the wedge still gets one shot at the fallback model before bailing.)
- **Tenacity retry visibility** — the `_chat_cli` retry loop wires a `before_sleep` callback that logs the caught `_CliTransientError` text + the next attempt's model to `run.log` as a WARNING. Without this, transient retries were silent (caught exception text dropped) and write-attempt-1 deaths showed up only as a sudden `elapsed=1s` heartbeat with no diagnostic.
- **CLI input-cap guard** — a CLI provider with a hard per-turn input limit (`codex_cli` rejects turns over 1,048,576 chars with `input_too_large`) carries a `max_input_chars` on its `_CliSpec` (codex_cli: 900K, sitting under the limit to leave room for codex's own system prompt + tools schema). When a node's prompt exceeds it — e.g. `analyze`/`write` after an evidence-gate **broaden** pulled in many literature sources — `_run_cli` trims the **middle** of the prompt (keeping the task head + the output-format tail, where FI always puts the load-bearing instructions) and logs a WARNING, so the call goes through instead of hard-failing the quest. Trimming is lossy (some literature/result detail is dropped); the warning points at the leaner-footprint knobs (`knowledge.top_k`, `knowledge.literature_excerpt_chars`, `engine.evidence_gate_max_broaden: 0`). **`copilot_cli` carries the same cap for a different reason** — it passes the prompt as a command-line **arg**, so on Windows the whole command line hits the `cmd.exe` ~8191-char limit (`copilot.BAT` fails a long design/write prompt with `rc=1: The command line is too long`); its `max_input_chars` is 7000, well under that. 7 KB is small for a rich node prompt, so copilot trims heavily on long-context nodes — the real fix is a stdin/temp-file transport, so prefer `codex_cli` / `openai` for long prompts on Windows. The stdin-based CLIs (`claude_cli` / `gemini_cli`) have no arg-length limit.
- **Provider fallback chain + circuit breaker** — `provider.fallback: [codex_cli, gemini_cli]` (default empty) lists providers to try, in order, when the primary terminally fails a chat call (after its own retries). Each provider carries a circuit breaker: after repeated failures — or one auth/quota/credit error — its circuit opens and it's skipped, so subsequent calls jump straight to a live provider instead of re-burning the dead one's retry budget every call. The breaker is **half-open**: after a cooldown (`breaker_cooldown_s`, default 90 s, above the retry budget) one probe is let through, and a provider that has recovered rejoins the chain — so a transient blip doesn't permanently drop it for the rest of a multi-hour quest. Fallbacks are built lazily (nothing is resolved and no proxy is spawned until the primary actually fails); `last_model`/`last_usage` track the serving provider so cost accounting stays correct; a `CancelledError` never triggers a fallback. A single provider outage (rate limit, auth failure, proxy crash) no longer forfeits the whole quest.
- **Global LLM-call backpressure** — `FI_MAX_CONCURRENT_LLM_CALLS` (default `0` = unlimited) caps the number of in-flight provider calls across every quest in one process. A `--fleet` of N quests each fanning out a review panel / ensemble can otherwise burst into dozens of simultaneous requests and trip provider rate limits; set e.g. `8` for a large fleet. The slot wraps only one dispatch, so retries/fallbacks re-queue rather than deadlock; single quests see no change at the default. **Scope caveat:** the cap is per-OS-process. `--fleet` runs its quests in one process, so the value is a true aggregate ceiling. `--serve` launches each quest as a separate subprocess, so each gets its own cap and the effective ceiling is `FI_MAX_CONCURRENT_LLM_CALLS × --max-concurrent` — size the value with that multiplication in mind under `--serve`.
- **Retry classification** — the provider retry loops distinguish *transient* failures (5xx / 429 / network blips, and CLI `OSError` / transient markers) from *deterministic* ones. A 4xx (bad key, content policy, oversized body) and an hours-long CLI session/usage/credit-limit or auth failure abort immediately with the original message instead of burning the 4-attempt jittered-backoff budget on an error that can't clear in the retry window.
- **Gates fail open, panels degrade** — a provider blip in the `review` / evidence-gate path can't forfeit a finished paper: a single-reviewer failure degrades to a neutral accept, one panelist raising doesn't abort the panel (the rest still vote, and an all-panelists-fail case falls back to a neutral verdict). `CancelledError` still propagates cleanly so a real cancel isn't swallowed.
- **Deterministic gate routing** — judgment nodes (`evidence_gate`, `review`, `review_panel.*`, `claim_check`, `cross_check`, `relevance_guard`) run at temperature 0 so their routing decision (sufficient vs broaden, accept vs revise, supported vs not) is reproducible run-to-run instead of flipping and triggering wasted broaden loops or spurious revise cycles. Applies wherever the transport honours temperature (HTTP + vscode_bridge); generative nodes keep the 0.2 default. CLI transports that don't expose temperature are unaffected.
- **Per-node HTTP timeout + prompt-size guard** — the OpenAI-compatible transport takes a per-node read-timeout (`provider.node_http_timeout_s`, base `provider.http_timeout_s` = 120 s), mirroring the CLI's `node_cli_timeout_s`: reasoning-heavy nodes (`implement` → 900 s, `write` → 600 s, …) get headroom while cheap nodes keep the tight base that catches a hung server fast. A transport-agnostic `provider.max_prompt_chars` (default `0` = off) generalizes the CLI middle-trim to every transport — when set, a prompt over the cap is trimmed in the middle of its largest message (head + tail kept) with a loud warning, so a runaway prompt can't blow the context window into a hard 400 / stall.
- **Bridge reconnect-on-drop** — a mid-quest VSCode-bridge socket drop nulls the stale transport so the next chat reconnects, instead of leaving a dead writer that wedges the rest of a long `--serve` / `--tools` session. In-flight calls fail with a transient `BridgeError` (retried), and pending awaiters are unblocked rather than hanging.
- **Fleet isolation + memory-cap safety** — in `--fleet`, a quest whose Engine construction fails is isolated (siblings still complete; the runner exits non-zero) instead of aborting the whole batch, and a `--memory-cap-mb` set below the baseline RSS — which would deadlock the fleet (nothing can run to free memory) — is disabled with a warning rather than hung on. `--profile` is rejected with `--fleet` (viztracer can't meaningfully trace N concurrent quests in one process).
- **Resume completes missing outputs** — a `--resume` regenerates only the outputs actually missing on disk: a kind whose final deliverable already exists (`paper.pdf` / `slides.pdf` / `poster.pdf` / `talk.md`) is carried through untouched, so resume no longer re-invokes the LLM for slides/poster/speech that already rendered or clobbers good decks. **Existence isn't trusted blindly** — a PDF must be non-empty *and* start with the `%PDF` magic, and a text deliverable must be non-empty, so a truncated file left by a kill mid-compile is regenerated rather than shipped. Any configured output still missing after the pass is reported. `--emit` stays an explicit force-regenerate path.
- **Resume self-heals a half-built venv** — `VenvExecutor.setup()` reuses a per-quest `.venv/` only when the interpreter actually exists *and* a cheap `import pip` probe passes (CPython writes `pyvenv.cfg` before copying the interpreter and running ensurepip, so a run killed mid-build leaves a `pyvenv.cfg` with no interpreter). A broken venv is rebuilt from clean on the next `--resume` instead of spawning a missing-python `FileNotFoundError` on every retry.
- **Unknown config keys fail fast** — `Config.from_yaml` audits the top level and the six known sub-sections against their real fields and **raises** on an unrecognized key, listing the offending dotted paths. Pydantic's default is to silently drop unknown keys, so a typo like `provider.node_http_timeoutt_s` would otherwise validate cleanly and quietly revert a reliability knob to its default. Legacy pause flags and free-form dict fields (`node_models`, `node_*_timeout_s`, `clarify_overrides`, …) are still accepted.
- **Windows MAX_PATH venv diagnostics** — a deep `output_dir` on Windows can push the per-quest venv's native-extension paths (PIL/matplotlib `.pyd`) past the 260-char limit, silently killing figure generation. `setup()` warns when the venv path already exceeds ~200 chars, and `execute()` sniffs a DLL-load failure in stderr and logs one actionable hint (enable `LongPathsEnabled` or shorten `output.output_dir`) — so even the otherwise-silent web-figures path surfaces the cause.
- **Stuck-quest dashboard surfaces** — `/api/quests/{id}` returns `node_started_at`, `node_elapsed_s`, `node_idle_s`, and `quest_failed: {present, failing_node, what_broke}` derived from `run.log` timestamps and `<quest_root>/quest_failed.md`. The detail page (`web/static/quest.html`) renders a colored chip next to the current-node label (green = active, yellow = idle ≥5 min, red = idle ≥10 min) and an error banner with the failing-node + one-line exception when a `quest_failed.md` is present. The banner clears the moment a resume **starts** — the engine deletes the stale file at the start of every run (not only at terminal state), so an actively-running resume isn't mislabeled "failed"; a re-run that fails again writes a fresh diagnostic. Because that idle chip is driven by `run.log` recency, the **execute node emits a heartbeat** (`[execute] running experiment.py — still running, Ns elapsed`, every 30 s) while the experiment subprocess runs — otherwise a multi-minute parameter sweep, which the executor just blocks on silently, would show as idle/red the whole time even though it's hard at work.
- **"Needs you" is distinct from "complete"** — a paused quest still writes `frontier_insight_summary.json` on its clean rc=0 pause-exit, so a single `_quest_pending()` helper (shared by the dashboard scan and `/api/quests/{id}`) decides whether the quest is actually *waiting on the user* — via the unified `NEXT_STEP.md` / `.fi/pause.json` markers, or a human-review / clarify snapshot with no answer yet. The dashboard shows a **"Needs you"** badge (filterable) instead of "complete", the quest page keeps **Resume** and the right input control live (for older quests too, from the on-disk snapshots), and the engine clears those snapshots **both at the start of every run and on true completion** — so neither a finished quest *nor an actively-running resume* shows a stale pending state. (A refine/resume that continues past a pause used to leave the old `NEXT_STEP.md` / `pause.json` / human-review / clarify snapshot on disk for its whole run, mislabeling a busy quest as "Needs you"; the run-start clear drops those display markers while deliberately keeping the `*_answer.json` files, which are the input that resume is consuming.) **Add papers / data to any quest from the quest page** — a persistent upload writes into `inputs/papers` + `inputs/data` (the generalised `/api/quests/{id}/upload`), picked up on the next resume / refine — so you can feed a quest files from the frontend whenever, not only when a supply-pause fired. Quests with no `config.yaml` (CLI-started before configs were saved) disable Update/Resume with a clear note, since both need the original YAML.
- **Ensemble profile is a tier-1 quest decision** — `Multi-model ensemble` (`off` / `cross_check_only` / `ideate_and_check` / `full`) sits next to provider/model on `/interview` and the CLI's `--new` flow rather than under "Show advanced". Every LLM `/tools/*` form (proposal / critique / digest / portfolio / summarize / analyze) carries the same picker; the form maps the picked profile through `core.interview.ensemble_model_trio(provider)` to a 3-model CSV and passes it via each tool's `--<tool>-ensemble` CLI flag. Default merge differs per tool: `tournament` for the canonical-synthesis tools (proposal / portfolio / summarize / analyze) and `synthesize` for the disagreement-preserving ones (critique / digest). Single-shot tools (digest / portfolio / summarize / critique / proposal) wrap one LLM call via `core.ensemble.run_singleshot_with_ensemble()`; `--analyze` runs a full engine quest and the ensemble lands on `cfg.provider.node_ensemble` for the `analyze` and `cross_check` nodes.
- **VSCode extension** — sanctioned `vscode.lm.*` integration with `@fi /new`, `/start`, `/fleet`, `/resume`, `/summarize`, `/proposal`, `/critique`, `/digest`, `/portfolio`, `/analyze`, `/update`.
- **Accessibility** — `prefers-reduced-motion` honoured on `marketing/index.html` (terminal fade-in + pulse-dot disabled when the OS preference is set).

### CLI tools

- **`--serve`** — local web UI; honours `FI_VSCODE_BRIDGE_PORT` env var for routing LLM calls through Copilot when launched from a VSCode terminal. Refuses `provider=vscode_extension` quests when no bridge is wired (400 at submit).
- **`--resume <quest_id>`** — re-enter the LangGraph from the last checkpointed node when a prior run died mid-pipeline.
- **`--fleet <yaml> ...`** — bounded concurrency, ref-counted proxies (per-provider locks so one provider's proxy warmup doesn't block others), `--memory-cap-mb` (a below-baseline cap is disabled with a warning, never deadlocked on), per-quest construction-failure isolation, and an optional process-wide LLM-call cap via `FI_MAX_CONCURRENT_LLM_CALLS`. `viztracer --profile` is single-quest only (rejected with `--fleet`).
- **`--summarize <folder>`** — walks mixed content, classifies each file, calls LLM once, writes `outputs/<summary_id>/summary.md`. Ingested into Axon.
- **`--digest --days N`** — weekly PM digest with WeekDiff (✅ promoted / 🆕 new / ⚠️ still-in-progress / 🛑 stalled / ❓ dropped) vs prior digest. Ingests as `fi_digest`.
- **`--portfolio`** — all-time cross-quest synthesis: topic clusters, near-duplicate detection, meta-paper candidates, coverage gaps. Ingests as `fi_portfolio`.
- **`--critique <id>`** — adversarial second-pass review (`--critique-provider <name>` to use a different model family). Writes `outputs/<id>/critique.md`. Ingests as `fi_critique`.
- **`--proposal "<topic>"`** — pre-quest planning doc + companion YAML under `outputs/_drafts/`. Companion YAML auto-pins the proposal into `knowledge.local_papers`. Ingests as `fi_proposal`.
- **`--analyze <data-path> --analyze-topic "..."`** — no-simulation quest on pre-staged data. Routes through `auto_collect_data → wait_for_data → data_load → analyze → write → review`. ~6 premium requests.
- **`--ingest <paths>`** — one-shot Axon ingest, no quest. Zero LLM calls.
- **`--install-tectonic`** — drops a self-bootstrapping LaTeX binary (~70 MB) into `tools/`. SHA-256 verified.
- **`--install-tectonic-from <path>`** — airgapped variant: install from a locally-staged archive or extracted binary. No network call. ELF / Mach-O / PE header sanity check.
- **Resumable quests** — SQLite-checkpointed state at `<quest_root>/.fi/state.sqlite`.

## Knowledge layer — three-layer retrieval

```
asearch(query)
  ├─ 1. Pinned local_papers (always first)
  ├─ 2. Axon (your long-term store; falls through on empty)
  └─ 3. External router: agent picks 1–5 sources from the catalog
        ├─ openalex / arxiv / crossref / semantic_scholar / pubmed / core / google_scholar
        └─ (optional) full-text fetch via host network
```

After an **accepted** quest, the write-back lays down a structured
bundle so Axon stays title-searchable and topic-linkable:

| kind | Purpose |
|---|---|
| `fi_paper_spine` | One tight chunk per paper — title / authors / DOI / keywords / abstract / key claims. Title queries hit this directly, and the keywords the writer picked (shown under a scientific paper's abstract, kept out of sight in a report, brief, essay or whitepaper) give later searches the paper's subject terms. |
| `fi_quest_paper` | Full paper body with a 1-line `[Title · Year · Venue · DOI]` citation header on every chunk. |
| `fi_quest_summary` | Structured-findings JSON (hypothesis, key_findings, result_json, verdict, score, model). |
| `fi_topic_event` | One pointer per accepted quest keyed by topic slug — enables "what do we know about X" rollups. |
| `fi_external_ref_spine` × N | Curated card-catalog entries for cited papers. Only refs from *accepted* quests persist. |

## Configuration

See [USAGE.md](USAGE.md) for the full annotated YAML schema. Quick
landmarks:

- `provider.*` — provider name, model, per-node model routing, ensemble.
- `engine.*` — max_iterations, review_panel, ensemble, no_simulation, survey_mode (literature/history synthesis: no experiment and no dataset), and the rest of the research-loop knobs.
- `pauses.*` — the unified human-in-the-loop section: clarify, papers, supply, review, auto_accept_on_pass, timeout_s (legacy `engine.*` / `knowledge.*` pause flags still map in).
- `execution.*` — venv vs docker, timeout, python version.
- `knowledge.*` — Axon config, top_k (RAG) + external_top_k (web), relevance_min_score (literature relevance floor) + relevance_min_keep, local_papers, full-text fetch.
- `output.*` — kinds, paper_format, audience, output_dir, require_pdf.
